# Install and update a pinned reference

Each project adopts an explicit release through a normal reviewed Git change. Preparing that change does not activate a new executor. Projects can adopt releases independently; a shared console still checks each service's protocol compatibility.

## Ownership and lockfile

`factotum.lock.json` records the release version, manifest and payload SHA-256 digests, source commit when proven, and every managed file's hash and executable mode. Commit it alongside the installed files. Only `adopt install` and `adopt update` write it: builders may never change, delete or move it (`workspace.commit` refuses, whatever `policy.allowFactoryEdits` says, including changes the builder committed in its worktree), and status, plan, update and `upgrade apply` refuse an unreadable or invalid lock, a lock that is a symlink or not a regular file, or one whose managed files or prefix differ from what the commit that adopted its release wrote. Deleting the lock is treated as tampering: once a repository's history has a lock, a missing lock, or a lock deleted and recreated at any point in history, stops builder commits, the runtime and every adoption command, and `adopt install` refuses to start over. If a lock was edited or deleted by hand, restore it from the adoption commit (for a deletion still in history, that means rewriting or reverting history on a branch the operator controls; there is no command to do it).

- `factory/`, `VERSION` and `compatibility.json` are upstream-owned. Keep project adapters, configuration and governance outside `factory/`.
- By default the installation sits at the repository root. With `adopt install --prefix <folder>` all four installed paths (`VERSION`, `compatibility.json`, `factory/`, `project/`) live under that one folder instead; see [install under a folder](#install-under-a-folder). `factotum.lock.json` always stays at the repository root.
- `project/` files are seeded during initial installation and become project-owned. Updates never replace them or automatically add new templates.
- Application files and private runtime state remain project-owned. The updater does not open project databases, change services or move an active installation pointer.

The installed `factory/AGENTS.md` states the same ownership policy for project agents, and the delivery template includes it as required governing context. Projects should mirror it in their root agent instructions. Custom integrations belong outside `factory/`; missing core behavior is proposed upstream and adopted through a release, including when the affected file is a supplied adapter. Do not hand-edit generated version/lock records or add startup patches to bypass this boundary.

An update refuses modified/missing managed files, extra files inside `factory/`, file collisions, symlinks and a dirty starting checkout. Port intentional core modifications into project extensions or resolve them explicitly before updating. Initial installation also refuses existing reserved paths rather than overwriting them; a project with its own root `VERSION`, `factory/` or `project/` installs under a prefix instead. This tooling initializes a new locked adoption; an existing manually copied installation needs an explicit baseline audit rather than an invented upstream identity.

## Build a release artifact

From a reviewed reference checkout, preferably checked out at its release tag:

```sh
node starter/factory/cli.mjs release build \
  --source starter --out /private/releases/factotum-0.3.0 --version 0.3.0
```

The output contains `starter/`, `release.json` and `release.json.sha256`. A release never contains test files: the builder refuses a starter holding any `*.test.mjs` (or `.test.js`, `.spec.mjs` and similar) file, so Factotum's own tests, which live in the reference repository's `tests/`, never join an adopting project's test discovery, coverage or lint. The command prints the manifest digest. The manifest includes all payload files, ownership, compatibility and hashes. Its generated `starter/compatibility.json` also supplies the schema/config arrays required by the runtime upgrade commands. The builder changes neither source files nor Git tags and refuses an existing output directory.

A normal release requires the starter's exact bytes and executable modes to match its committed Git tree. Before the first committed release, an explicit development artifact is available:

```sh
node starter/factory/cli.mjs release build \
  --source starter --out /private/releases/factotum-dev-1 \
  --version 0.2.0-dev.1 --development
```

Development manifests record `sourceState:"working-tree"` and `sourceCommit:null`; their content is still pinned by hashes. Do not represent them as tagged release qualification. The printed digest identifies the artifact, not proof of provider quality or publisher authenticity.

For distribution, maintainers should commit/version the starter, publish an immutable tag with release notes, and distribute the exact artifact and its digest through a trusted channel. Transport can initially be a local directory or a separately fetched/extracted release artifact. The tool does not create tags, publish assets, fetch arbitrary URLs or follow a mutable `latest` pointer. The repository is licensed under Apache-2.0, and each release carries that license as `factory/LICENSE`; no release host is configured. Checksums detect changed bytes; a digest obtained from the same untrusted download does not authenticate its publisher.

## Initial adoption

Run the CLI from the release artifact you are installing (`<release>/starter/factory/cli.mjs`), the same as for `upgrade apply`. A reference checkout's working tree is usually past the release tag, so its CLI is a different version from the files it would install; use it only when you built a development artifact from that same checkout. Replace the paths and `MANIFEST_SHA256` with the selected artifact's actual digest:

```sh
node /private/releases/factotum-dev-1/starter/factory/cli.mjs adopt install \
  --root /path/to/project \
  --release /private/releases/factotum-dev-1 --digest MANIFEST_SHA256 \
  --branch chore/adopt-factotum --worktree /private/reviews/project-factotum-install
```

The project must have a clean Git checkout with an initial commit. The command creates a new branch and a separate worktree at its current HEAD, copies the verified starter and writes the lockfile. Configure project-owned files in that review worktree and use the project's normal commit/review/merge process. No commit, push or PR is automatic. Existing branches and review directories are refused. An interrupted preparation leaves its isolated worktree for inspection; it never silently retries or removes that work.

Continue with the [getting started brief](../GETTING_STARTED.md) for commissioning and the first real pilot.

### Install under a folder

A project whose root already has its own `VERSION`, `compatibility.json`, `factory/` or `project/` cannot take a root installation; `adopt install` refuses it as a conflict. Add `--prefix` to put the whole installation under one folder:

```sh
node /path/to/factotum/starter/factory/cli.mjs adopt install \
  --root /path/to/project --prefix tools/factotum \
  --release /private/releases/factotum-dev-1 --digest MANIFEST_SHA256 \
  --branch chore/adopt-factotum --worktree /private/reviews/project-factotum-install
```

This writes `tools/factotum/VERSION`, `tools/factotum/compatibility.json`, `tools/factotum/factory/` and `tools/factotum/project/`, and `factotum.lock.json` at the repository root with `"prefix": "tools/factotum"`. The lock's `managedFiles` stay relative to the installation folder; `adopt status`, `plan` and the review output report repository paths (`tools/factotum/factory/cli.mjs`).

The prefix must be relative and already normalised (no leading `./`, no empty or `.` segments, at most one trailing `/`), must not contain `..`, and must not be absolute or inside `.git`. Each folder name may contain only letters, digits, `.`, `_` and `-`, and may not start with `-`, so printed commands and unit files never need quoting. Every existing folder along it must be an ordinary directory: not a file, not a symlink and not a nested Git repository or submodule. The usual conflict check applies under the prefix (any file the release would write that already exists is refused, as is an existing `<prefix>/factory`), and so does a check that the project's Git ignore rules do not cover any installed path, which would leave it out of the adoption commit. Refusals happen before any branch or worktree is created.

**How later commands find it.** Every command that needs the installation's location reads the prefix from `factotum.lock.json` at the repository root; nobody repeats it. `adopt plan`, `adopt update` and `upgrade apply` install the new release into the recorded prefix (an update cannot move it; passing a different `--prefix` to the library call is refused). `upgrade apply --merge`/`--activate` run `config update --current` and `doctor` with `<root>/<prefix>/factory/cli.mjs`; `service install project` writes that CLI into the unit, and `doctor` checks an installed unit against it. Guidance text the CLI and console print (`node tools/factotum/factory/cli.mjs …`) names it too. Run the project's CLI from the repository root as `node tools/factotum/factory/cli.mjs`; the examples in these guides use the root layout (`node factory/cli.mjs`).

**Paths in project configuration.** Configured paths (governing-context `path`, check `argv` scripts, workflow files) are relative to the repository root, not to the installation folder. The seeded `project/factotum.template.json` already names `tools/factotum/factory/AGENTS.md` and `tools/factotum/project/GOVERNANCE.md`; other paths you add, such as `tools/factotum/project/integrations/fast-check.mjs`, need the prefix too. The other project templates are seeded unchanged and show root-layout paths. Builders may not change `<prefix>/factory/`, `<prefix>/VERSION` or `<prefix>/compatibility.json` (unless `policy.allowFactoryEdits`) or `factotum.lock.json` (never), and workflow definitions may not live in `<prefix>/factory/`. A root-level `factory/` folder in a prefixed project is ordinary project code, and so is a root `VERSION`.

Moving an existing installation to or from a prefix is not supported by the tools; it needs the baseline audit described above.

**Reading history safely.** Builder worktrees share the project's Git directory, so these checks never trust Git's own view of it. They read commits, trees and blobs with `git cat-file --batch` and hash each object against its ID, take parents and tree entries from that verified content, and require the walk to be complete. Git runs with replacement objects, grafts and the commit-graph cache switched off, and a repository with `refs/replace/*` or an `info/grafts` file is refused. Remove replace refs with `git replace -d` and the grafts file by hand.

**Shallow clones.** `adopt status`, `plan`, `update` and `upgrade apply` walk the lock's whole history, so they refuse a shallow clone; run `git fetch --unshallow` first. Everything else works in a shallow clone: the running factory, builder commits, `service install` and doctor. One exception can refuse falsely: a candidate (for example an adopted pull request) that forked from the target below the clone's boundary. Builder protection cannot show that history to be on the target, so it reads the target's older commits as the candidate's own and refuses any that changed the lock or core; the refusal then says so. Run `git fetch --unshallow` and retry. A project without a lock also works there, as long as no lock appears in its visible history (a lock deleted within it still fails closed). Doctor's drift check reads only the lock and the installed files, so it works in a shallow clone too.

**Doctor's drift check.** For an adopted project, doctor reports installed files that differ from `factotum.lock.json` (edited, missing, an unmanaged file inside the installed `factory/`, or files rewritten on checkout by line-ending conversion or a filter) as a blocking reason, and so is a lock whose layout evidence does not rebuild the release it names (see [layout evidence](#install-under-a-folder)); `upgrade apply --merge` and `--activate` run the same check on the live checkout after merging and stop before recommissioning if it fails. A root lock written before dev.87 has no layout evidence: doctor accepts it and warns that it is unauthenticated until the next adoption, and `adopt status` reports `"authenticated": false` with the same warning on standard error (its exit code is unchanged). Once the project's lock has verified by its evidence, a later lock without it is a blocking reason instead (see [no downgrade](#install-under-a-folder)).

**Builder changes and the target.** In a delivery, the upgrade-owned files (the lock, and `factory/`, `VERSION` and `compatibility.json` under the prefix) are checked against the trusted state at three points: each `workspace.commit`, each `workspace.integrate` that does not conflict (including when the target turns out to be merged already), and `forge.publish`. Once the factory has integrated a target, the candidate must contain it and carry the target's versions of those files. Publishing therefore needs an integration first, and publishes exactly what it produced: the workspace `HEAD` must be the head of the last integration that did not conflict, and commissioning refuses a workflow in which any route into `forge.publish` does not come straight from `workspace.integrate`'s `integrated` result through input-preserving steps (review, gate, fast checks, preview; see [project workflows](project-workflows.md#3-commission)). The reference workflows already have that shape. The candidate's own commits (those not in the recorded target, or in the workspace base before an integration) may not change upgrade-owned files at all, even when a later commit puts them back; the factory's merge of the target does not count, because its content there is the target's. So a builder that merges an upgrade branch that is not on the target yet and undoes it is refused at commit, integration and publish, and a builder's committed-then-reverted edit of the core is refused too (under `policy.allowFactoryEdits` only the lock is). Two further consequences are intended: a builder that merges a newer target itself and reverts its upgrade is refused at integration, and a builder that aborts the factory's conflicted merge and commits is refused ("does not contain the recorded target"). Resolve the conflict and conclude the merge instead, or integrate again.

**When an upgrade stops partway (dev.87).** One rule decides whether the units `upgrade apply` stopped may run again: the project checkout verifies, read from the files on disk the way doctor's drift check reads them (the lock and its evidence, the project's anchor, and every installed file hashed from its bytes, not from Git's index), and its lock is authenticated: by its own evidence, as the exact lock a verified release authenticated for this project, or by the release given with `--release` and `--digest`. A root lock written before dev.87 is not: units are not started on it until `upgrade apply --recover --release <the directory of that release> --digest <its digest>` authenticates it, so keep the directory of the release you run now at hand when you upgrade from one. `--merge` and `--activate` check the files (without that last condition, so the first upgrade from such a lock can run) before they stop anything, and refuse to start if it fails ("the project checkout does not verify, so nothing was stopped or changed"; `adopt status --state` and doctor say what is wrong). They move the checkout once, after the units are stopped. Each unit is recorded in the project's state (`upgradeRecovery`) just before it is stopped, with the commit the checkout held; that commit only shapes the instructions below, it is never trusted. The record is cleared when every unit it names is confirmed running.

- **A commit on the remote target changed a `.gitattributes` or `.gitmodules` file** (`--merge`, at any depth): these change how Git checks files out (filters, line endings, submodules) without showing in the reviewed changes, so `--merge` stops before it rebases anything, stops anything or moves the checkout. Prepare the upgrade again on a new branch, so it is reviewed on top of the target.
- **A commit on the remote target changed installed files, or touched what the review changed** (`--merge`): the review branch, rebased in its worktree, no longer verifies or no longer carries exactly the reviewed changes (a reviewed commit skipped as already applied, or a target commit touching a path the review changed). `--merge` stops before anything is stopped or moved and puts the review branch back on the reviewed commit. Fix the target if it is wrong, then prepare the upgrade again on a new branch, so it is reviewed on top of the target.
- **`verify` (after `--merge`) or the pull (after `--activate`) refuses the files:** the checkout is returned to the commit it held (`git reset --keep`; a `rollback` step), checked again from its files, and the units start. If only line endings differ, a checkout conversion such as `core.autocrlf` (or a `.gitattributes` `eol`/`text` rule, or a smudge filter) rewrote them: turn it off for the installed paths. For `--activate`, a commit on the target changed them: fix the target. Then run the same command again.
- **The checkout cannot be returned, or does not verify:** the units stay stopped, and the result has a `hold` step that says why. It asks you first to look at `git -C <root> status --short` and copy anything you want to keep to a private backup outside the repository: do not stash it, since a stash puts untracked files (secrets included) into Git objects. It then gives the exact commands after "To finish, run in order:": `git -C <root> checkout -- <paths>` for the files that differ (this discards their changes), `git -C <root> reset --keep <commit>` back to the commit the checkout held, and `node <cli> upgrade apply --recover --actor operator --root <root> --state <state>`. `git reset --keep` refuses rather than overwrite a changed file ("Entry '<path>' not uptodate" or "would be overwritten by merge"): back that file up outside the repository, restore it with `git -C <root> checkout -- <path>` (or move an untracked one out of the repository), and run the reset again.
- **A unit does not start again:** the result has a `units` step naming it, and the record stays. The step ends with the commands to run: `systemctl --user start <unit>` for each, then `upgrade apply --recover`.
- **The run is interrupted** (a signal, a crash, a lost session): the record stays in the state. `upgrade apply --recover --actor operator --root <root> --state <state>` (add `--release <dir> --digest <sha256>` to let that release authenticate a lock without evidence of its own), or the next `--merge` or `--activate`, finishes it first: it checks the checkout from its files and, if it verifies with an authenticated lock, ends the way a run ends: `config update --current` and doctor with the checkout's own CLI, then the recorded units, started and confirmed, only if both succeeded. If either fails, the units stay stopped and the error says what failed; fix it and run `--recover` again. It does not move the checkout. If the checkout does not verify (an activation killed on a target that does not), nothing is started and the error gives the same instructions as a `hold`. The result of a run that recovered starts with a `recover` step, and an error it ends with says the recovery happened. Preparing an upgrade (`upgrade apply` without `--merge` or `--activate`) is refused while the record is there, with the `--recover` command to run.

A checkout that already holds a merged release whose files differ from its lock (a `verify` failure from a release before dev.87, which did not return the checkout): rerunning `--merge` stops with "the review branch … is already merged into the project checkout, which holds X, but its installed files differ from the lock (verify failed)" and names the files. Restore them from the merged commit (`git checkout -- <paths>`), confirm `adopt status` is clean, push if you were using `--push`, run `adopt cleanup`, then `config update --current` and `doctor` with the project's CLI.

**An upgrade branch the checkout already contains.** `--merge` first checks whether the reviewed commit is already in the project checkout, or in the remote target. If only the remote target has it (its pull request was merged there), `--merge` stops with "already merged into <remote>/<target> … there is nothing to merge" and says to activate it with `--activate`, or, if the lock there names another release, that the upgrade was merged and then undone. If the checkout holds that release, it stops with "already merged … there is nothing to merge", or, when installed files differ from that release's lock, with "already merged … but its installed files differ from the lock (verify failed)" (see the end of the previous paragraph). If it holds another release, the upgrade was merged and then undone, for example by a change that merged the review branch and restored the old lock and core; `--merge` stops with "already contained … but the checkout does not hold release X (its lock names Y)", before anything is stopped. Merging the same branch again would change nothing. Find and revert the change that undid it, or prepare the upgrade again on a new branch and merge that.

**Layout evidence.** Every lock also records the release's template file identities and compatibility: a prefixed lock under `layout`, a root lock under `rootLayout` (from dev.87; releases before it refuse a root lock with a `layout` key, and a root lock must stay readable by an earlier release it adopts). Together with its managed files they rebuild the release manifest whose digest was pinned at adoption, so a changed or added managed-file entry is refused, even when the installed file was changed to match it: by status, plan, update, doctor's drift check, `upgrade apply --merge` and `--activate`. Evidence cannot be added to a lock by hand; only an adoption writes it.

A root lock written before dev.87 has no evidence. It is still accepted, as unauthenticated: doctor and `adopt status` warn, and nothing ties its managed files to the pinned digest until the next adoption, which writes the evidence. Where a verified release directory is at hand, the lock's managed files are checked against that release's manifest instead: always for `--merge`, and for `--activate` with `--release` or when run from the release's own CLI. `--activate` refuses a landed root lock without evidence when it has no verified release directory, before anything is stopped, and says to pass `--release` or to prepare the adoption again with the release's own CLI.

**No downgrade.** The first time a project's lock verifies by its own evidence (doctor, `--merge` or `--activate`), the project's state records it (`adoptionAnchor`, in the state directory, outside the checkout, so nothing written to the target can change it). From then on a root lock without evidence is refused by doctor (a blocking reason), `adopt status --state <dir>`, `--merge` and `--activate`, unless a verified release directory authenticated it: `--merge` always has one, `--activate` with `--release` or run from the release's own CLI. That authentication is recorded too, by the SHA-256 of the exact lock, so doctor and `adopt status` accept that lock afterwards (with the warning that it carries no evidence of its own) and refuse any other. The refusal names both ways forward: prepare the adoption with the release's own CLI, which writes the evidence, or apply it with `--release`. A project whose lock never had evidence keeps the transition behaviour. So does one whose state has no record, such as a state set up on a fresh machine: it warns, and records the anchor at the first lock with evidence. `adopt status` without `--state` cannot see the record: it gives the transition warning and says to pass `--state`.

Both kinds are also checked against Git history, anchored on adoption commits (the oldest commit that wrote each release record): the managed files must match the lock the current release's adoption commit wrote, every adoption commit must name the same prefix, and a lock deleted at any commit fails closed. Adoption (root or prefixed) needs a release in the form `release build` writes.

## Prepare an update

From the adopted project, inspect drift and preview a specific release (in a prefixed project, the CLI is `node <prefix>/factory/cli.mjs`; nothing else changes):

```sh
node factory/cli.mjs adopt status --root /path/to/project --state /private/state/project
node factory/cli.mjs adopt plan --root /path/to/project \
  --release /private/releases/factotum-0.3.0 --digest MANIFEST_SHA256
node factory/cli.mjs adopt update --root /path/to/project \
  --release /private/releases/factotum-0.3.0 --digest MANIFEST_SHA256 \
  --branch chore/factotum-0.3.0 --worktree /private/reviews/project-factotum-0.3.0
```

`status` reports local managed-file drift; it does not check for newer upstream releases. `--state` (optional) checks the lock against the project's record of its authentication too ([no downgrade](#install-under-a-folder)). `plan` reports additions, replacements, removals and conflicts. Both return a nonzero exit code when drift/conflicts are present. Preparation repeats validation in the new worktree and verifies the resulting managed files. The original checkout, project configuration and running executor remain unchanged. Reusing an installed version name with different content is refused; an already installed exact release is a no-op error rather than another update branch.

Managed files that a new release no longer contains are removed (`kind: "remove"` in the plan); only files recorded in the lock's `managedFiles` are ever removed, never project-owned files, `project/` templates or anything else outside the lock. In particular, releases no longer ship `factory/console/console.test.mjs` and `factory/core/contracts.test.mjs`: updating from a release that had them removes both, under the prefix if there is one.

Review the diff, release notes, compatibility declarations and relevant upstream template changes. Adapt new project settings manually, run project checks and commit/review the update normally. Local edits to the core are flagged for explicit resolution; there is no automatic three-way merge that could silently discard them.

After the reviewed branch is merged (fast-forwarded) into the project checkout, remove the review worktree and branch that `adopt install` or `adopt update` created:

```sh
node factory/cli.mjs adopt cleanup --root /path/to/project \
  --branch chore/factotum-0.3.0 --worktree /private/reviews/project-factotum-0.3.0
```

It refuses a worktree that isn't registered on that branch, has uncommitted or untracked files, or whose branch isn't merged into the checkout's `HEAD`. It uses `git branch -d`, never a forced delete.

## Guided update: `upgrade apply`

For a project that runs from its checkout (with or without the units from `service install`), `upgrade apply` performs the update in two explicit steps. It takes no prefix: it updates the installation where `factotum.lock.json` says it is. Run it with the CLI of the release you are adopting, because the project's current CLI may predate the command:

```sh
CLI=/private/releases/factotum-0.3.0/starter/factory/cli.mjs
node $CLI upgrade apply --actor operator --root /path/to/project --state /private/state/project \
  --release /private/releases/factotum-0.3.0 --digest MANIFEST_SHA256 \
  --branch chore/factotum-0.3.0 --worktree /private/reviews/project-factotum-0.3.0
# review the worktree, adapt project files, run checks, then commit there
node $CLI upgrade apply --actor operator --merge --out /private/backups/project-before-0.3.0 [--push] \
  --root ... --state ... --release ... --digest ... --branch ... --worktree ...
```

**The stored configuration is checked first, by the release being adopted.** Before it prepares, stops or merges anything, `upgrade apply` validates the project's stored configuration with the configuration validator of the release itself (`factory/core/configuration.mjs`), loaded from a release directory that has just been verified against the manifest digest you pinned. It is loaded from there whichever CLI runs the command, so the answer is the one the project gets when it is recommissioned afterwards. If that release would refuse the configuration, the upgrade stops with the reason and changes nothing: otherwise the release would land and `config update --current` would then fail, leaving the project on the new code and unable to recommission. Correct the configuration with the release the project runs now (`config show > factotum.json`, edit, `config update --config factotum.json`), then run the upgrade again. The usual case is an `upkeep` or `learnings` block that earlier releases ignored: replace it with a valid block such as `"upkeep": {"mode": "off"}`, or remove it.

- **Preparing and `--merge`** always have the release directory (`--release`), so they always check, and a release whose validator is missing or cannot be loaded is refused.
- **`--activate`** has no release directory of its own: the release is already on the remote target. It checks when a verified one is at hand: the directory you pass with `--release`, or the release artifact the CLI runs from (`<release>/starter/factory/cli.mjs`, the documented way to run it). A `--release` that is not the pinned release is refused. With neither, the check is skipped and the result says so (`configCheck`): doctor, after activation, is then the check. Nothing is ever read or run from the remote target before activation.

1. **Without `--merge`** it refuses unless the project is drained (flows finished or abandoned, attempts reconciled, obligations resolved), then prepares the review worktree exactly like `adopt update`. Nothing else changes; the reviewed commit is your decision.
2. **With `--merge`** it checks that the worktree holds a clean, committed adoption of that exact release and is a fast-forward of the checkout. With `repository.target` configured it first catches up with the remote target: it fetches it, rebases the review branch onto it in the review worktree, and checks that the branch still carries exactly the reviewed changes (the same blobs at the same paths, nothing skipped) and that the worktree still verifies; a target that changed any `.gitattributes` or `.gitmodules` file is refused before the rebase; otherwise it stops for a new review (see "When an upgrade stops partway"). The project checkout does not move yet. It then:
   - stops the project and console units if they are active;
   - confirms the runner is stopped and the project is still drained, and writes a backup to `--out`;
   - fast-forwards the checkout to the review branch (the only time it moves), checks it (`verify`), pushes `HEAD` to the configured target only with `--push`, and runs `adopt cleanup`;
   - runs `config update --current` with the newly merged CLI, then restarts the console unit if it stopped it;
   - runs `doctor` with the newly merged CLI;
   - restarts the project unit (and anything else it stopped and has not restarted), even if a later step failed.

**Targets that only accept pull requests.** If the target is protected (no direct push, squash merges only), land the reviewed adoption through a pull request instead of `--merge`, then activate it: `upgrade apply --activate --root … --state … --digest MANIFEST_SHA256 --out /private/backups/… [--release /path/to/release]`. It checks the drain, stops the project's unit (and the console's only if the console runs from this checkout; a shared console is left running), backs up, fast-forwards the checkout to the remote target, refuses unless that holds the release with this digest and its lock authenticates its files (see [layout evidence](#install-under-a-folder); the lock is read from the target as data and checked before anything is stopped), runs `config update --current`, restarts the console if it stopped it, runs doctor, and restarts the project unit. If the pull step refuses the target, the checkout is returned to the commit it held before the pull, so the units restart on the code they ran before, not on files that were not verified; see [when an upgrade stops partway](#install-under-a-folder). `--when-drained` works with it too. `--merge` also leaves a shared console running now.

**Waiting for a drain.** Add `--when-drained` to either step to have it wait instead of refusing: it pauses admission from the start, including new maintenance jobs (so nothing new starts), clears maintenance runs left stopped and queues them again afterwards, reports what it is waiting for every minute, applies once the project is drained, then lifts the pause it set. It gives up after `--max-wait-hours` (default 72). Run it in the background; nothing else needs to happen meanwhile.

Task flows parked on an open question don't block the drain. They carry over: the recommission step rebinds them, and an unchanged question stays open (no new wake). Only a question whose subject changed is reopened. It prints each step. `ok` is true only when every step succeeded and doctor passed. On failure, the steps show how far it got; admission stays disabled until doctor passes. It does not stage or activate installation roots used by `launch --install`; use `upgrade stage/activate` for those.

**How long the doctor step can take.** The doctor that `--merge` and `--activate` run is the full `doctor` command, so it can legitimately take a long time. It first waits for the machine-wide heavy-work permit if another project's heavy step holds it, or if weighted admission's load or memory limits keep it closed, for up to the permit's hold bound (about 65 minutes). It then probes every role's provider, each configured fallback and each distinct step model (each probe makes three CLI calls of at most 15 s, and a probe that times out is tried once more), prepares the main verification workspace (each `workspace.setup` command at most `workspace.setupTimeoutMs`, 30 minutes by default), and runs every main check at its configured timeout and retries. From dev.85 the upgrade gives the doctor child the sum of those bounds plus a 15-minute margin for doctor's Git and forge calls (each of which has its own timeout), capped at 4 hours, and records it as the step's `limitMs`. `limitCapped: true` means the configured setup and checks alone exceed the cap, so the cap, not doctor's own bounds, can end the step. `config update --current` has 10 minutes. Until dev.84 both had a fixed 10 minutes, so a doctor still waiting for the permit was killed and reported only as `"error": "Provider timeout"`.

**Reading a failed recommission or doctor step.** The step's `error` names the step, the command it ran (`node <prefix>/factory/cli.mjs doctor --state …`) and how it ended: `timed out after N s (its limit is M s)`, `exited with code 1 after N s: <doctor's reasons>`, or that the process could not complete. Further fields:

- `phase` and `lastProgress`: the last thing doctor reported doing, from its `doctor: [<phase>] <detail>` progress lines: `permit wait` (with who holds the permit, or "no recorded holder (pool limits or machine load)"), `probe of <role> (<provider>/<model>)` with the attempt, `forge check`, `checkout check` or `main verification`. A timeout during `permit wait` means the host was busy; run `doctor` again once the holder finishes. A step with no `phase` stopped before doctor's first long phase.
- `reasons`: doctor's own reasons when it finished and printed them. A provider reason names the role, provider and model, the kind of failure, the CLI call and an excerpt of the error (see [running: provider probes](running.md#provider-probes-in-doctor)).
- `elapsedMs`, `limitMs`, `exitCode` and `timedOut`.
- `stdout` and `stderr`: their last 12 lines (at most 1,200 characters each), with control sequences removed and every secret the factory knows redacted, as for a failed workflow command.

Every step row, and the whole result, is redacted with the factory's known secrets (credential environment variables, the scoped GitHub token, secret-named configuration values and the notification delivery file's secrets), so a secret never appears in a command, path, message or excerpt it records.

**What stays down, and for how long.** The upgrade needs the project runner stopped from the backup to the end of recommissioning: the backup must be consistent, and the checkout's code must not change beneath a running service. A console that runs from this checkout is stopped for the same reason, and it comes back as soon as `config update --current` has finished. By then commissioning is cleared, so the console refuses to start flows ("project doctor qualification required") and admission stays held, which is the state a shared console is already in during an upgrade.

The project runner stays stopped until doctor has ended, which can be over an hour when the heavy permit is busy. A running project service would advance a carried-over task flow as soon as its question is answered, whatever the admission pause or commissioning say, so starting it before doctor passes would run flow work on code doctor has not qualified. Because commissioning is required, it would admit no new work anyway. An answer given in the console meanwhile is recorded and acted on when the runner starts.



Admission stays held until doctor passes. Fix what the reasons or phase name, then run `node <prefix>/factory/cli.mjs doctor --state …` directly; the upgrade itself does not need to be repeated.

`config update --current` re-applies the stored configuration, recompiling workflows with the current code, and can be run on its own.

## Activate after review

Source preparation and runtime activation are separate:

1. Keep running work pinned to its original immutable executor. Drain work, reconcile uncertain attempts and obligations, and stop the runner before replacing the checkout it executes from. Do not merge changed runtime files beneath a directly running checkout.
2. Back up private state and any shared operational ledgers. Merge the reviewed update and synchronize the clean project target checkout.
3. Revalidate the selected artifact with `adopt plan` and its trusted digest. Stage that verified release's `starter/` payload with `upgrade stage`, supplying its generated `compatibility.json`. Keep the installation root outside the payload. Actual project configuration, adapters and governing context remain anchored to the registered project checkout/private configuration; do not replace them with the bundle's project templates.
4. Run bounded installation verification and activate with `upgrade activate`. Preserve the prior immutable installation. Stage/activate reject incompatible schema/config versions; no automatic schema migration is provided. (The layout of records inside the unchanged schema is converted by the project service when it starts, after which an earlier release cannot write the state; see [running: record layout](running.md#record-layout-of-the-state-database), which also covers returning to an earlier release. A release declares the layouts it reads as `recordLayouts` in `compatibility.json`.)
5. Re-run `doctor` with the newly selected executor while the runner is stopped, then start it via `launch`. Verify project checks, console compatibility and a scoped smoke task before expanding automation.

The exact runtime commands and verifier format are in [running: upgrades](running.md#exclusive-retention-and-upgrades). Use a starter-layout staging source rather than copying the application's Git database, dependencies or private state into the runtime installation. Changing or rolling back source files does not undo an incompatible data/configuration change. Keep recovery evidence and original executors until the installation's recovery obligations are settled.

Automated reference qualification uses disposable Git projects to install and update across two releases, preserve custom project files, remove obsolete core files, detect local drift/tampering, and exercise the existing immutable stage/activate/launcher path. Real providers, GitHub delivery and production migration remain separate installation qualification.
