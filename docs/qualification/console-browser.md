# Console real-browser qualification

This checklist qualifies the shared web console in a real browser against a real project service. It is part of release qualification and is also run after any change to the console (`factory/console/`), to the dashboard snapshot or detail reads the console renders (`factory/service/dashboard.mjs` and the project service routes), or to how the project service reports flows, attempts, decisions and statistics.

The console's unit tests render views into a fake DOM from fixed data. They cannot see a backend that drops fields on the wire, a page that badges a record differently from its canonical state, a control that is too small to tap, text that overflows at phone width, or an error that only a real browser raises. Each of those has reached a release before. This checklist exists to catch them.

The checklist is run by a browser-automation agent, for example a Playwright-driven Chromium operated by an agent that is given this fixed checklist and an evidence folder. It is not run by unit tests. The agent drives the page as an operator would: it clicks, types and reads what is rendered. It must not intercept, block, delay, mock or modify any request unless a step says so; no step in this document does. An earlier pass that intercepted requests produced a page that said "Project not registered" because of the harness, not the product, and its results had to be discarded.

## Setup

### Release under test

Run everything from the release checkout under test. Record its version and manifest digest (from the built release or `factotum.lock.json` of the fictional project), the browser name and version, the automation tool and version, the operating system, the browser's locale and time zone, and the date. Put these at the top of the results.

### Services

Start a project service and a console from the release checkout, never from an older installation:

```sh
node factory/cli.mjs serve --state /private/qual/project-state --socket /private/qual/project-state/project.sock
node factory/cli.mjs register --state /private/qual/console-state --socket /private/qual/project-state/project.sock
node factory/cli.mjs console --state /private/qual/console-state --port 0
```

The console state directory is new and used only for this qualification. The console listens on loopback; use the URL it prints. State directories stay outside any checkout, and socket paths stay short (see [running](../running.md)).

### Projects

Use fictional projects only. No real project, repository, person or host appears in the evidence.

- **Read-only passes (A, B and D).** The populated demonstration is acceptable: `node evals/run.mjs --serve --ui-demo` starts two fictional rehearsal projects, a stopped and a failed flow, a rejected receipt, an unavailable project and an uncommissioned delivery project, all registered with one console. Some of its records are labelled illustrative. A project that has run real deliveries for a while (with merges, stops, replans, answered and expired questions, to-dos and scheduled checks) exercises more of the checklist; where the demonstration lacks a record a step needs, record the step as "not run" with the reason.
- **Operations pass (C).** The rehearsal workflow cannot be used for the full pass. Its flows reach their only decision ("Accept synthetic rehearsal result?") within seconds, before the console opens, so there is nothing running to stop, and that decision has no pull request, candidate commit or review. The demonstration's delivery project runs with its runner off, so Run doctor never completes there. Pass C needs a fictional delivery project: a small fictional application in a private, disposable forge repository, adopted with the starter and configured for delivery with the project's providers as [getting started](../../GETTING_STARTED.md) and [running](../running.md) describe, served by the commands above, with doctor not yet run. `node evals/live.mjs --create --provision-only` can provision such repositories (see [the live guide](../../evals/LIVE.md)), but the live harness answers the merge question itself, so do not use its delivery run for this pass. Prepare one approved fictional task whose flow will plan, build, review and reach a merge question. This uses real provider calls and a real forge, which needs the operator's authorization.

## Viewports and themes

Every pass runs in four combinations unless a step says otherwise:

| Combination | Viewport | Emulation | Colour scheme |
| --- | --- | --- | --- |
| desktop-light | 1440×900 | none | light |
| desktop-dark | 1440×900 | none | dark |
| phone-light | 390×844 | mobile, touch, device scale factor 2 | light |
| phone-dark | 390×844 | mobile, touch, device scale factor 2 | dark |

In each combination, leave Settings → This browser → Theme at "System" and set the emulated colour scheme. Once per viewport, also set Theme to "Light" with a dark system scheme and to "Dark" with a light system scheme, and capture Overview and Stats: the explicit preference must win, and no panel may keep the other theme's colours.

## Rules for the agent

1. Use a fresh browser context for each pass and keep that one context for the whole pass. If the automation resets, say so in the results and say which steps ran in which context.
2. After each navigation, wait until the header shows "Observed …" and the project's data is on the page. Never record a loading state as an empty one.
3. Use the console for every operation in Pass C. The CLI is used only for the setup commands in this document, for `inbox.publish` where a step says so, and for the read-only `status` comparisons.
4. Do not change the project's configuration, providers or repository during a pass beyond what a step says.
5. Report what is on the page in its exact words. Do not repair or explain a defect; record it.
6. A step that cannot be run is recorded as "not run" with the reason. It is never left out.

## Evidence to keep

Keep one folder per pass (`A/`, `B/`, `C/`, `D/`). For every step keep:

- **Screenshots**, full page, named `<pass>-<step>-<combination>[-<detail>].png`, for example `A-08-phone-dark-stats.png`. Open and look at every screenshot before reporting on it.
- **Measured values** as JSON, named like the screenshot with `.json`: the page heading, the section headings found, `document.documentElement.scrollWidth` and `clientWidth`, and any sizes a step asks for.
- **Browser log** for the pass, `browser-log.json`: every console message with its level, every uncaught page error with its message and stack, each tagged with the step and URL.
- **Request log** for the pass, `requests.json`: method, path, status and duration of every request the page made, and every request that failed without a status.
- **Canonical state**: `node factory/cli.mjs status --state <project-state>` saved as `status-<pass>-<step>.json` before and after each pass, and wherever a step compares the page with canonical state. Use `status --flow <id>`, `--inbox <id>` or `--task <id>` to compare one record.

## Every page, every pass

These checks apply to every page and modal opened in any pass:

1. The page heading reads the tab's name followed by " · " and the project name (or the tab name alone for all projects).
2. The browser log has no uncaught page error and no console error for the step.
3. The request log has no failed request and no response with status 400 or above.
4. `document.documentElement.scrollWidth` is not greater than `clientWidth`. Wide tables may scroll inside their own box; the page itself must not.
5. Times shown to the operator are readable, and the same time is not shown in two different forms on one page.

When `status` lists a hold with `scope: "task"` in `.queueStatus.holds` (a context task whose providers are not qualified, say), Overview counts the held tasks in three places: the Queue figure ("queued tasks · 1 held on its own"), a "Needs attention" item ("1 queued task is held on its own") and a line under "Admission controls". Each has an "Open Queue" link that opens Queue at that task (dev.93, Q3; the Queue figure's link was missing until dev.94, R3). With no such hold, none of the three appears, and the Queue figure's "Open Queue" opens Queue itself. The item and the line say "The rest of the queue still starts." only when nothing else stops admission. With admission paused (or any other hold on the whole queue: recovery, retention, spending, doctor, a stalled launch, a failed claim), they say "The rest of the queue is held too: …" and name it. With a hold on change work only (main verification, a merge in flight, a target sync), they say the change and document tasks wait too. With automatic admission off, they say queued tasks start only when dispatched. Check at least: a held context task alone, then with admission paused.
2. **Inbox.** The toolbar offers "Open", "Resolved" and "All" with counts. Open lists "Decisions and notices" and, when any are owed, "To-dos". Open Resolved and check that every answered item is badged as answered, and that its badge agrees with `status --inbox <id>`. Repeat in all-projects scope. At phone width, in Open and All and in both densities, the page does not scroll sideways (`scrollWidth` ≤ `clientWidth`) even when a card's title or text holds a long unbroken ID, such as a triage proxy's `triage-undelivered-…` notice naming a 75-character thread ID or a 66-character send ID: the ID wraps inside the card, whole. 3. **Timeline.** The window choices "6 h", "12 h", "24 h" and "3 d" each load data. Event markers that overlap in a busy period must be told apart or counted. Check this at phone width too, with every grouped marker closed: measure the box of every marker, single or grouped, and no two may overlap.
   - On the Timeline tab's events lane, a single event is `.tl-ev` (a link to its flow, or a plain marker when it has none) and a group is `details.marker-group.tl-ev-cluster`.
   - In a flow's execution timeline (Pass B), a single event is `.marker` and a group is `details.marker-group.marker-cluster`.
   - Record how many of each were measured. At phone width a busy window can be a single group with no `.tl-ev` at all; that is a pass, not a missing selector.

   **Tapping a flow's bar opens that flow** (dev.94, R1: at 390 px a tap on one flow's bar opened its neighbour). In the phone combinations, at 390 px and again at 320 px, with the 12 h window and touch input (a tap, not a mouse click), tap the visible centre of every flow bar in every slot lane and record what opens. A bar is drawn as `.slot-flow`, and its `data-flow` attribute is the flow it stands for. The drawn bars take no taps. A layer above them (`.tap-layer`) holds the targets: a link `a.slot-hit` for a flow with room for its own target, or a group `details.bar-group.slot-cluster` for flows too close to tap apart. A group's summary shows the count and is labelled "N flows close together; show them below the track", and its list opens in a panel below the lane, each flow a link by title. A tap on the bar's centre opens that flow's detail directly, or opens a group whose list links that flow; then tap that link and the flow opens. Any other flow opening is a wrong-or-misleading finding. Record each bar: the flow expected, the flow opened, and whether it went through a group. Then check the targets themselves, with every group closed. Each is at least 44 CSS px wide and 44 px tall at phone width, and at least 8 px wide on a desktop. Within one lane, no two targets overlap, except that a target beside a flow's bar at least three targets wide may reach into it by less than one target. That wide bar's own centre still opens it. A refresh leaves an open group open. Focus survives it too (review of 3e4fdda, P2). Open a group with Enter, Tab to an entry in its list, and wait for the refresh, every 10 seconds by default. Focus is still on that entry, not on the page body. Check this at 320, 390 and 1440 px, on the Timeline's flow groups and events groups and on a flow's attempt groups. Check it also on a flow's own link (`a.slot-hit`).

   Markers too close to tell apart are one grouped marker whose summary shows the count and is labelled "N events close together; show them". Open it by tap, click and keyboard (Tab, then Enter): it lists each event with its time, and on the Timeline tab each event links to its flow. The open list stays inside the viewport at phone width (no sideways page scroll). On the Timeline tab the list opens beside its group. In a flow's execution timeline it opens in a panel directly below the chart, headed "N events close together:", because the chart scrolls and would clip it (dev.86 K2). Check there, at desktop and phone width, that every event of the list is fully visible without scrolling the chart: the list's box lies outside the `.gantt-scroll` box, inside the viewport, and `document.elementFromPoint` at each item's centre returns that item. Then check that it closes:
   - Enter on the summary closes it.
   - Escape closes it from the summary or from a link in its list (in a flow's execution timeline, also from inside the panel below the chart), and focus returns to its summary. In a flow's execution timeline, inside the detail modal, the first Escape closes only the list and the modal stays open; a second Escape closes the modal. Check this with focus in each place the list can leave it (dev.87 L6): on the summary, on a link in the panel, and after a click on the panel's heading text (focus then leaves the panel). Each time the first Escape closes only the list, focus returns to its summary, and the modal stays open. A click on blank space in the modal, outside the panel, is a click outside the list: it closes the list and the modal stays open (dev.89 M5), so the next Escape closes the modal (dev.90: this step used to expect that Escape to close only the list).
   - A click or tap anywhere outside it closes it, including on another grouped marker (which opens instead) and on a window choice. A click inside the panel below a flow's chart does not.
   - Following an event's link closes the list and opens that flow's detail. Closing the detail returns focus to the group's summary.
   - Only one grouped marker is open at a time. An automatic refresh leaves an open list open.
4. **Tasks.** The task list and its filter. With a filter applied, the count text must describe the tasks shown, not the tasks loaded.
5. **Queue.** "Admission readiness" and "Started from the queue". Every relative time on the page ("Started 24 minutes ago" on each entry of "Started from the queue", a parked flow's "since …" under "Flow slots", and "Last dispatch …" or "Dispatch requested …" with automatic admission off) is a `time` element whose tooltip is the recorded UTC value with "(UTC as recorded)" (dev.87 L7). A hold is explained in plain words with a readable time. A hold that names another flow names it by title and links it, with no bare flow ID left in the text. The "Flow slots" card shows each pool's slots in use and free, the flows parked on an answer (with "Holds a slot" for any beyond the parked limit) and the answered flows waiting for a slot with their position; compare it with `status` (`.queueStatus.capacity`).    A hold on one queued task (`scope: "task"` in `.queueStatus.holds`) appears under "A queued task is held.", never under "The queue is held.", and the task detail never says "Nothing is admitted while the queue is held" for it. 8. **Stats.** For each window (7 days, 30 days, 12 weeks), record the section headings and check that the page does not scroll sideways at phone width; the 12-week charts label at most seven of their bars. Expect "Throughput and speed", "Quality of first attempts", "List-price estimate" (when the project has estimates), "Checks", "Decisions", "Failures and stops", "Models", "Tasks" and "Maintenance". Then check the three sections that depend on fields carried over the wire:

   - The "Accounting coverage" card must be present when the service's stats response has `accounting`.

   Check this on the wire, not only on the page. 9. **Health** (route `records`). "Main health" shows its status, head, check time, "Last run" and, when the project has scheduled-only checks, "Scheduled tier", whose time is a time element like the others (the recorded UTC value in its tooltip; dev.86 K4). "Needs recovery" and "Audit findings" appear only when present, and "Knowledge upkeep" only when upkeep is on, a part is suspended or a candidate is listed (in propose mode it also shows the open docs follow-up, candidates with a task and closed candidates). 11. **Receipts.** The filter offers "All", "Unresolved", "Completed" and "Rejected" with counts that match the list. With nothing submitted, it says so. Repeat in all-projects scope.
12. **Project-only tabs in all-projects scope.** Timeline, Tasks, Queue, Scheduled, History and Health each show the "… is scoped to one project" chooser and nothing else.

## Pass B: flow and attempt detail

Run desktop-light and desktop-dark in full; repeat steps 1, 2, 7 and 8 in the phone combinations.

1. **Open a flow.** From Timeline, select a flow bar; from Overview, select a flow under Work in progress or Recently finished. The detail modal opens over the page with "Copy link" and "Close", and shows "Flow summary", "Controls", "Execution timeline", "Decisions (n)" and "Flow events (n)". The flow it opens is the one selected. For an unfinished change or document flow, "Flow summary" has a "Flow slot" line (step 8).
2. **Execution timeline and attempt panel.** Select an attempt. **Every attempt is reachable by touch** (dev.94, R2: 11 of 43 attempt bars at 390 px and 16 of 43 at 320 px took no tap, because a neighbour's bar lay over them). In the phone combinations, at 390 and 320 px, open a flow with many attempts. Tap the visible centre of every drawn attempt bar, `.gantt-rows .bar[data-attempt]`, and record the attempt the address then names (`attempt=`). Its prepared and running bars both count, and both select the same attempt. The tap selects that attempt directly, through a `button.bar-hit`. Or it opens a group, `details.bar-group.bar-cluster`, labelled "N attempts close together; show them below the track". The group's list sits in the panel below the chart and names each attempt as a button; tap that attempt's button and it is selected. Every bar must reach its own attempt; record the count, for example "86 of 86 bars". Repeat on a desktop with the mouse. The targets follow the rule of Pass A, step 3: at least 44 px wide and tall at phone width, and none overlapping. Keyboard: Tab reaches every attempt's button or group summary. A selected attempt's panel shows status, exit, run time and settlement, "Recorded step result" for the latest attempt of the step, and "Evidence and logs". Every log offered loads and wraps. The log selector offers only artifacts that exist for that attempt (a fast check, gate or other non-model step offers no `provider/` file). An artifact that does not exist shows "… was not written for this attempt"; its request returns 200 with `available: false`, so the request log shows no 4xx or 5xx for it.
   **What each role cited.** Open a flow that was shown a learning (it has a "Learnings shown to agents" card). Under each cycle, the roles listed after "What each role cited:" must match `status --flow <id>` (`.flow.learningCitations`), each role with its step and use: "applied" or "contradicted" for the planner and builder, "followed" or "contradicted" for the reviewer. Check this also for a flow planned before an upgrade, whose citations `status --flow` reads from its results. The card says "No role has cited a learning of this cycle yet." only when `learningCitations` has no entry for that cycle (dev.93, Q1).
3. **A failed check is shown as failed.** Open a flow in which a fast check or gate attempt failed. That attempt must be drawn and badged as failed, never as a green "passed" attempt, and its panel must show "Failed checks" naming the failing check, the rules it enforces and the diagnostics the check wrote, without opening raw JSON. The flow itself is not failed: it went back to the builder. Compare with `status --flow <id>`. If no such flow exists, record "not run".

   **A main verification's checks.** Open a `main.verify` maintenance flow and select its attempt. The panel lists "Main checks": every check of the run with its result ("passed", "failed", "timed out"), how long it ran and its limit; a check the step's time ran out for is listed as "not run". A timed-out check gives the limit it was stopped at, and says when that was the time left in the step rather than its own limit. Compare with the run's `action-result.json` (`mainHealth.checks`, `mainHealth.timeout.notRun`) and with Settings → Repository and checks. If no such flow exists, record "not run".

4. **Decisions.** For each decision in the "Decisions" card: the answer, who answered (the operator, or the orchestrator on the operator's behalf, in which case the relayed words are shown and marked as relayed), when, and the answer's note. For a strict merge, the card says who signed off on which candidate. Compare with the "Flow events" card and `status --flow <id>`. In "Flow events", an "Attempt settled" line gives the attempt's result as its panel does: a build that stopped at its turn limit reads "stopped at turn limit" (amber) and a failed check "failed" (red), never "passed" with a green dot.
5. **Stop reason.** A stopped flow shows "Stop reason". A flow that was stopped and later resumed shows no stop reason while it runs, waits or after it completes; its earlier stop appears in its events.
6. **Workspace and candidate.** The summary shows "Workspace branch", "Created from" (the target head the workspace was made from) and, on its own line, "Candidate commit". The candidate commit equals the head the review and checks were run on in `status --flow <id>`. An unlabelled commit that could be either fails this step.
7. **Deep links and navigation.** With a flow and attempt open, copy the address with "Copy link" and open it in a new tab: the same flow and attempt open. Reload: the same flow and attempt stay open. Escape closes the modal and focus returns to the control that opened it. The keyboard reaches every control in the modal with a visible focus outline.

   Browser Back: choosing an attempt changes the address (`…?flow=<id>&attempt=<id>`) without adding a history entry, because the attempt is a selection inside the flow's window, not a page of its own. So one Back closes the modal and keeps the tab, from the flow alone or after choosing any number of attempts, and the address loses both `flow` and `attempt`. Check it by opening a flow from the page, choosing two attempts in turn and pressing Back once. When Overview offers "Inspect attempt" (an uncertain attempt), check it from there too: the link opens the flow with the attempt chosen, and one Back returns to Overview. A Back that only removes `attempt` and leaves the modal open fails this step.

8. **Flow slot.** Open flows in as many of these states as the project has, and compare each with `status` (`.queueStatus.capacity`: `parked[].holdsSlot`, `waiting[]`, `categoryWaits[]`, and the pool counts). "Flow slot" in "Flow summary" reads:
   - "Working" and "holds a slot" for a flow that is running or waiting on anything but an answer;
   - "Parked on an answer" and "holds no slot" for a flow waiting on its question within the parked limit (policy.maxParkedFlows);
   - "Parked on an answer" and "holds a slot" for one parked beyond that limit;
   - "Answered, waiting for a slot" and "holds no slot", with its position in line ("position 2 of 3"), for an answered flow that found every slot in use;
   - "Answered, waiting on its category" and "holds no slot" for an answered flow held back only by its category's limit (policy.categoryLimits);
   - "Stopped" and "holds a slot" for a stopped flow.

   A flow named in that line is a link to its detail, by title. A finished flow, a planning flow and a task flow have no "Flow slot" line. Record each state the project lacks as "not run".

## Pass C: operations through the page

Run in desktop-light against the fictional delivery project, then repeat steps 1, 3, 4 and 7 at phone-dark on a second task. Keep the request log and Receipts for every submission, and compare each result with `status`.

1. **Commissioning hold and Run doctor.** Before doctor has run, Overview's state reads "Commissioning required", a notice at the top says so with a "Run doctor in Settings" link, and nothing on the page says the project is idle or that admission is open. The link opens Settings → Status, where "Run doctor" is offered. Select "Run doctor". The receipt and the page must distinguish the request being accepted, doctor running, and doctor finished with its actual outcome (passed, or failed with the reason). "Completed" must not appear while doctor is still running. After it passes, Settings → Status says doctor passed for this configuration, and the Overview notice is gone. While doctor is queued or running, the receipt's badge reads "Doctor queued" or "Doctor running" (never "completed"), and then "Doctor passed" or "Doctor failed". The same applies to job requests such as Queue → "Dispatch now" and Tasks → task source "Refresh": the receipt's badge follows the job ("queue.dispatch queued", "running", "finished" or "failed") and the toast says the request was accepted.
2. **Start the task.** Approve and queue the prepared task from Tasks ("Approve and queue", then the confirmation). It is admitted and its flow appears under Work in progress. If the task was approved before its selected workflow changed, its detail says "Approved for another workflow" and offers "Approve again"; confirming it clears the hold, as `task.approve` with the same revision does from the CLI.
3. **Stop a running flow.** While a model step runs, open the flow, write a stop note and select "Stop flow". The flow shows stopped with the note as its stop reason; Inbox shows the stop notice. Acknowledge the notice with "Acknowledge notice".
4. **Resume.** When the running attempt has settled, write a resume note and select "Resume flow". If Resume is unavailable while the attempt settles, the page must say why in plain words. The flow continues from the step after the settled one, without re-running it, and the stop reason is no longer shown.
5. **Answer the merge question from the Inbox.** When the flow waits on its merge question, open the Inbox card. Its "Candidate" section shows "Pull request" (a link), "Candidate commit" (a 12-character SHA), "Review" (the verdict with the findings count by severity, every severity listed even when zero, for example "pass 0 findings (0 critical, 0 high, 0 medium, 0 low)"), "Checks" (the gate results for that candidate; "Fast checks" too when configured) and "Changes" ("View the changes on <host>"). A result recorded for another commit is marked as such. Any additional context text the project supplies with the question is shown unchanged. Follow the pull request and diff links and check they lead to that candidate. Answer merge and confirm. The confirmation names the project, the question and its version.
6. **Completion.** The flow completes; its results show the merge and the cleanup. The completion notice can be acknowledged. Overview, Inbox, Timeline and `status` agree.
7. **Stale answer.** Publish a fictional standalone question with the CLI (`command --actor operator --operation inbox.publish`, see [communication](../communication.md)). Open it in two tabs of the same context. Open the answer confirmation in tab A with one choice, answer with another choice in tab B, then confirm in tab A without reloading. Tab A's answer is refused and the page says the question was already answered; Receipts show one completed and one rejected answer; `status --inbox <id>` shows only tab B's answer.
8. **Pause and resume admission.** On Overview, select "Pause admission". Queue, Settings → Status and a queued task's detail all say admission is paused, and none says the queue will admit the task automatically. Select "Resume admission"; all three return to normal. The queued task's detail says "Nothing is admitted while the queue is held" and names the pause; its holds list says "Admission is held: admission is paused", never only "project held".
9. **Answered questions stay answered after expiry.** Publish a standalone question with `"expiryMs":120000`, answer it in the console, then wait until its expiry time has passed. Inbox → Resolved still badges it as answered, matching `status --inbox <id>`.
10. **Project service unavailable.** Stop the project service for about 30 seconds. The page says the project is unavailable, removes its command controls and does not show its last data as current. Start the service again; the console recovers by itself with the same values.
11. **Console restart.** With an unsent draft in a form, restart the console process. The page reports that the session expired and asks for a reload; it never says the project is not registered. After a reload, the draft and every receipt are back.
12. **Receipts.** Every submission of the pass appears in Receipts with its canonical status, and in History → Commands with the operator as actor.

## Pass D: phone width

Run in phone-light and phone-dark. Measure sizes with `getBoundingClientRect()` and save them as JSON.

1. **Touch targets.** On Overview, Inbox, Queue, Timeline and Settings → Policy, measure the header buttons (Refresh, New task, the availability control), every tab in the tab strip, every action button and the project selector. Each must be at least 44 CSS px tall. The project selector must also be wide enough to show the selected project's name, not only its arrow. List every target below 44 px with its label and size.
2. **Active tab after a link.** Navigate by a link inside the page (for example Overview's "All events", which opens History). The newly active tab must be scrolled into view in the tab strip. Record its left and right edges against the viewport width.
3. **No page overflow.** On every tab, `scrollWidth` does not exceed `clientWidth`, at 390 px and again at 320 px wide. Wide tables and charts scroll inside their own boxes, and those boxes do scroll. Long unbroken IDs in Inbox cards wrap (Pass A, step 2). Long task IDs in banners wrap too: Queue's "A queued task is held." with an `upkeep:context:…` ID, Health's context task notice and the Overview items of Pass A, step 1 (dev.93, Q4). On a flow's execution timeline at 390 and 320 px, no two axis time labels overlap: fewer labels are shown at phone width than on a desktop. Check this in the flow dialog, whose track is much narrower than the page, and on the project Timeline's slot axis. Then, with the flow dialog open, resize the window from desktop width to 320 px and back without reloading: the labels are chosen again for each width and never overlap.
4. **Modals.** Open a flow detail modal and a New task form. Each scrolls to its last element and closes with its Close control. The flow detail modal also closes with one browser Back, with or without an attempt chosen (B-07).
5. **Readable chart and metadata text.** Record the computed font size of Stats chart date labels, Timeline axis labels, count badges, table headings and the "Observed" text. Text below 12 CSS px is a hard-to-use finding. Measure the count badges in the tab strip, the sidebar badges, the chip icons, table headings, the Stats column labels and the "Observed …" text in the header. Repeat this step once with Settings → This browser → Density set to "Compact": nothing may fall below 12 px there either.

Keep one row per step and combination:

| Step | Combination | Result | Evidence | Finding |

Result is "pass", "fail" or "not run". Each finding is listed below the table with its severity, the exact steps, what was expected, what the page showed in its own words, the evidence paths, and whether it reproduced a second time.

Severity uses three levels:

- **Wrong or misleading**: the page states something that is false or that disagrees with canonical state, or leads the operator to a wrong decision. Examples: a failed check shown as passed, an answered question badged as expired, a field the service returns and the console drops, a merge question without the candidate it is about.
- **Hard to use**: the information is correct but hard to find, read or act on. Examples: small touch targets, a tab off-screen, text below 12 px, times without a zone.
- **Cosmetic**: wording, grammar, spacing or alignment that does not affect understanding.

Any wrong-or-misleading finding blocks the release until it is fixed and the step passes again, or until it is explicitly waived in the [qualification record](../qualification.md) with the reason and the person who waived it. Hard-to-use and cosmetic findings are recorded and do not block the release by themselves.

## What this does not cover

This checklist does not measure performance or behaviour under load, a remote or non-loopback console transport, more than one operator using the console at once, browsers other than the one recorded, screen readers, or a full accessibility or colour-contrast audit. It checks what the console shows and sends; whether the project's decisions are correct is qualified elsewhere.
