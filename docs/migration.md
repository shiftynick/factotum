# Commissioning a full migration

A mature installation is a combination of the generic execution kernel, configured policies, trusted project adapters and operational evidence. A shared web console does not replace those contracts. Full migration means every currently owned responsibility has a new owner and qualified recovery path; green fictional examples alone are insufficient.

## Responsibility inventory

Record these in private installation configuration and project-owned documentation:

- Issue formats, parent grouping, state/exclusion labels, dependency syntax, scope, risk and after-merge obligations.
- Governing records/skills and the context each role must receive.
- Builder/reviewer models, effort, allowlists, safe fallback policy, review protocol, strict decision role and attribution.
- Queue ordering, manual pins, category capacity, planning window and cache policy.
- Actual checks, check selection, main verification cadence, registered temporary flakes and permitted evidence reuse.
- Shared host resource pools, weights, load thresholds and every heavy command path.
- Release candidates, free rehearsals, saved-state inventories, deployment lookup, rollback compatibility, product journeys, independent readers and report publication.
- Paid ceilings, allocations, global settlement/review ownership and unknown-charge recovery.
- Notifications, operator presence, acknowledgments, questions, retrospectives and rule proposals.
- Preservation discovery, external archive durability, backup/restore and pinned executor upgrades.

Use [issue profiles](integrations/github.md), [delivery policies](risk-review.md), [operations](operations.md), [durable project workflows](advanced-workflows.md), and [archive retention](archive-retention.md) to implement the inventory. Store real identities, integration credentials, preserved evidence and concrete installation mappings outside this generic repository.

## Policy choices

The default remains conservative: one active change, fresh full reviews, manual merge and no paid adapters. Optional bounded-delta reviews, ordinary followups, weighted capacity and paid integrations require explicit configuration and qualification.

Conservative planning invalidates on the whole input/configuration/context basis. Main-check cache reuse requires exact identities and verified artifacts. Selective cross-head reuse, composite candidate batching and specialized test-row selection belong in trusted project check adapters. Such an adapter must prove which exact candidate/input it checked and must never promote infrastructure uncertainty to green health. Additional checks or serialization can preserve correctness while differing in cost or throughput.

Automatic ordinary merge requires qualified remote target-race protection. Local target reads do not make the operation atomic. Commission the real remote refusal mechanism before enabling it. A project may retain its existing qualified merge/check adapter rather than weakening this condition.

Reviewers use enforced read-only inspection; configured independent gates run executable checks. If a project requires model-selected test execution, it needs a separately qualified constrained execution adapter. Model attestations are retained evidence, not proof that every source line was inspected.

## Cutover sequence

1. Build a private project profile and commission disposable installations with the actual setup/check/adaptor contracts. Exercise strict and ordinary changes, send-back, stopped work, uncertain publication, source/target movement and recovery.
2. Rehearse a full release with saved state, negative preservation/smoke cases, delayed observations and report publication. Keep paid adapters disabled until their real ceiling/receipt mechanisms have separate approval and qualification.
3. Establish one shared resource authority across old and new runners during overlap. Separate lease files do not coordinate. Never give both runners ownership of the same task, branch or release environment.
4. Drain the existing runner. Reconcile attempts, money, PR ownership, retained worktrees, questions and obligations. Keep original state/executors available for their own records and recovery.
5. Back up the old installation and shared resources. Start the commissioned replacement with a new stable project identity. Import open work through the issue profile and approve its canonical revisions; old labels do not grant new execution authority.
6. Run one complete real change with manual merge and one free release rehearsal. Verify notification delivery, history, citations, archival and restore. Then deliberately enable only qualified automation.

There is no cross-engine in-flight resume or implicit state-schema conversion. A drained cutover preserves capabilities without pretending foreign attempts belong to the new executor. Keep historical archives accessible and label their provenance; never convert old timestamps or success labels into new verified receipts.

Archive retention requires a quiet, drained maintenance window. The reference intentionally does not delete concurrently with active flows. An unresolved hold fences admission and canonical mutations; a failed sweep needs explicit same-operation reconciliation. Arrange a maintenance window rather than disabling preservation checks to make a schedule progress.

## Differences to qualify

An installation can preserve its responsibilities while choosing different internal mechanisms. These operating differences still need an explicit decision and evidence:

- **Upgrade availability:** the reference requires a drained project before switching executors. It does not route live flows across mixed executor versions. Keep old executors available for their pinned recovery work; uninterrupted rolling upgrades need additional core execution routing.
- **Host pressure and command coverage:** weighted pools gate configured work using load averages and available memory. They do not measure instantaneous CPU utilization or iowait, and they do not intercept arbitrary Docker commands or agent-selected shell commands. Install and qualify project command/environment guards wherever these controls are required. Every heavy command path, including provider tools and overlapping legacy runners, must use the same resource authority.
- **Repeated-flake escalation:** the built-in main-check ledger retains explicit registered-flake observations and their receipts. It does not automatically create an issue after a recurrence window. A project adapter can scan those observations, apply its configured recurrence policy and publish a deduplicated, unapproved issue under an explicit workflow grant. Qualify the window, evidence mapping, publication retries and grouping/labels.

Production adapters remain installation work. A graph or configuration entry alone does not prove complete saved-state discovery, a free rehearsal of the installed release graph, independent journey interpretation, safe report publication or durable external archives. Exercise each actual adapter and its failure/recovery path before assigning it ownership during cutover.

## Acceptance evidence

Maintain a private capability matrix naming each responsibility, configuration/adapter, successful real exercise, negative/failure exercise, recovery owner and retained receipt. No row is complete merely because an API or configuration field exists. Record exact executor, adapter, CLI and governance identities. The repository [qualification record](qualification.md) distinguishes generic tests from live observations and installation work still required.
