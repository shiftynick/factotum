# GitHub and owned workspaces

The starter implements GitHub through the installed `gh` CLI and Git worktrees through `git`. Adapters use argument arrays, never task-provided shell commands. They are trusted installation code for one local operator; they do not sandbox an agent running as that operator.

## Configuration and credentials

Create the forge with `createGitHub({repository, account, hostname})` from `starter/factory/adapters/github/index.mjs`. Repository and account belong in private project configuration. The adapter resolves `gh auth token --hostname HOST --user ACCOUNT` for each invocation. Ambient GitHub tokens, repository/host overrides and debug output are removed. The selected token is supplied only through the API child's environment. The adapter never switches the global active account or returns tokens in errors.

Delivery Git operations use the same explicitly configured account through `adapters/github/git.mjs`. Each supervised action resolves that account's token in an asynchronous scope. Network fetch/push/remote reads validate the exact configured host/repository and rewrite an approved SSH or HTTPS remote to canonical HTTPS for that invocation; the stored remote is unchanged. A private credential helper releases the token only for that exact HTTPS repository. Tokens reach only network Git child environments, never provider/check/offline Git environments, durable argv or `process.env`.

Factory API calls and credential lookups disable prompting, paging, update notifiers and telemetry. `GH_TELEMETRY=0` and `DO_NOT_TRACK=1` override inherited telemetry settings for those calls without changing global `gh` configuration. Telemetry can launch a separate `gh send-telemetry` process, which must not outlive a supervised action. See [GitHub's environment settings](https://cli.github.com/manual/gh_help_environment).

From dev.78, factory-managed Git mutations also use `-c maintenance.auto=false -c gc.auto=0`. The shared invocation adapter applies them to scoped delivery calls and unscoped workspace helpers, covering commits, integration merges, fetches, pushes and target synchronization. Adoption, upgrade and archive/cleanup Git wrappers use the same options. They override local/ambient settings for the invocation without editing repository or global configuration, preventing Git's automatic maintenance from detaching after an otherwise successful operation.

The supervisor still treats surviving descendants as containment failure; there is no exception for a process named Git or maintenance. Existing failed receipts are not rewritten or automatically resumed. These overrides do not configure Git invoked independently by project checks, providers or user scripts. Arrange any needed repository maintenance separately from active factory work.

Scoped Git ignores global/system Git configuration, disables hooks/signing, and rejects repository-local credential, HTTP, URL-rewrite or alternate transport overrides. Configure `user.name` and `user.email` locally in the adopting repository. Existing SSH remote spelling is accepted only when it identifies the configured repository; delivery does not rely on whichever SSH key or global GitHub account happens to be active. Standalone unscoped workspace helpers remain ordinary local Git utilities; the delivery/commissioning entry points supply the account scope. Setup is an explicit trusted list of argv arrays; it cannot come from issue text.

`ForgeError` distinguishes rate limits, authorization failures, not-found responses, transport failures and uncertain writes. A missing private resource can still be an access failure; do not treat a not-found response as proof that a resource was deleted. The adapter returns uncached reads for admission and merge. A dashboard may cache its own projections but must display observation age.

From dev.76, failed GitHub actions retain structured `errorDetails` in `action-result.json`. These include the HTTP classification/status when available, process failure code (for example `TIMEOUT`, `ENOENT` or `DESCENDANTS_SURVIVE`), and up to 4096 characters of redacted stderr per CLI failure. Selected GitHub tokens and common credential forms are removed before truncation; terminal controls are stripped. Request bodies, command arguments, environment, stdout and stacks are not copied into this diagnostic record. Inspect it as error evidence, not workflow authority.

An ambiguous write retains its original cause even after publication lookup. If that lookup also fails, its error is retained separately as `reconciliation`; the original write stays uncertain. The verified receipt is attached to the uncertain attempt for inspection without settling it or authorizing replay. Generic uncertainty notices include the underlying error classification, while detailed stderr stays in the retained evidence. Marker lookup and explicit reconciliation requirements are unchanged. Errors discarded by older executors cannot be reconstructed by upgrading.

## Tasks and publications

`readTask(issue)` returns a normalized task, including a digest revision. For explicit acceptance and dependencies, put a versioned brief in the issue:

````markdown
```factotum-task
{"version":1,"outcome":"Filter saved items","acceptance":["Only matching items appear"],"dependencies":[],"risk":"ordinary","postMerge":[]}
```
````

**The issue title is the task.** On import the task's `title` is the issue title, and every planner, builder and reviewer brief starts `Task <id>: <title>`. A brief's `outcome`, when it says more than the title, is imported as the task's `outcome` and shown to agents on the next line (`Outcome: …`), followed by the acceptance list; an `outcome` equal to the title adds nothing. The outcome is part of the approved brief: changing it needs approval again. A task imported by an earlier release without its outcome keeps its approved revision until its issue changes; the next import after that includes the outcome. (The factory writes `outcome` itself when it creates an issue, as the issue body's first line.) Prose in the issue body outside the fenced brief is not given to agents; with an issue profile and no brief value for them, only the bullet lists under the configured headings are read (acceptance, post-merge, paths). The body still counts toward the revision, so editing it needs approval again.

The brief may also carry an `originalRequest` (`{origin, source, date, text?}`; see [project workflows](../project-workflows.md)); it is provenance, never approval, and is imported as part of the task brief. The revision covers title, full body, sorted labels, acceptance and dependencies. Without an issue profile, an unstructured issue defaults to strict risk and empty acceptance; workflow admission must require the configured acceptance contract. Forge labels never grant canonical approval.

`publishPlan({issue,operationId,body})` and `createPR({branch,base,title,body,operationId})` attach stable operation and input-digest markers. They search all relevant comment/PR pages before writing. After an ambiguous failure they search again, return an existing matching publication, or report uncertainty. Reusing an operation ID with changed input is rejected. Keep one canonical dispatch intent per operation: marker lookup does not make simultaneous independent writers atomic. A caller must persist an uncertain outcome and reconcile it before authorizing a new write. Removing/editing the markers breaks machine reconciliation and requires operator inspection.

`lookupPublication` supports explicit recovery. `publishCheck({head,context,state,description,targetUrl?})` publishes a commit status tied to a candidate SHA. The caller retains the evidence and only publishes success after validating every owed gate row. A status publication can have duplicate historical rows after recovery; readiness uses its named context and current candidate, not a row count.

`forge.publishPlan` uses `publishReviewedPlan` to maintain one marked reviewed-plan comment per issue. From dev.70, if it records a concrete publication with exit code zero, unchanged local input and only a `descendant-survival` failure, the attempt remains **failed**, but its flow **stops at publication** with the plan and review retained. Inspect the receipt and address the helper, then explicitly `resume` with a note. This prepares a fresh attempt under current authority; the adapter re-reads the marker and reconciles the same comment before advancing. No automatic retry or successful containment claim is made. Changed input, unknown publication, revoked approval and other operations do not gain replay authority through this path. Normal receipt identity/digest checks still apply, and survivors must be terminated before a terminal receipt exists.

An already-terminal flow from an older release is not rewritten. Preserve its evidence and start a fresh approved flow after the normal drained update; the stable per-issue marker avoids creating a second plan comment. Do not edit old receipts or change a failed attempt to passed.

The reference rejects GitHub closing keywords with issue references in PR title/body, merge title/message and every candidate commit message. It closes only the explicitly approved source issue through its separate post-merge disposition. Plain references such as `Task: #1` remain supported. Candidate commit-message validation is bounded to 250 commits, matching the GitHub PR commits endpoint; larger changes require explicit separate treatment. Missing/incomplete commit metadata fails closed. An adopted PR's commits are checked with the same rule and bound (`closingReference`, `readPRCommits`) at its `candidate` step, before any model runs.

## Merge enforcement

`readPR(number)` returns string SHA fields `head` and `base`, named refs `headRef` and `baseRef` (also `headBranch`/`baseBranch`), merge state and the PR's `author` login (or null). `readPRCommits(number, {expectedHead, expectedCount})` returns the PR's commits oldest first, refusing more than 250 or an incomplete list. `merge({number,expectedHead,expectedBase,mode,requiredContext?})` checks the current open PR, expected candidate and target. It supplies GitHub's expected-head `sha` condition on the merge request. An uncertain response is reconciled by reading that same PR; it never opens a replacement PR.

GitHub's merge `sha` condition guards the PR head. It does not atomically compare the target SHA. Manual commissioning therefore returns `residualTargetRace: true` when protection is only local. A manual confirmation does not eliminate that race. See the [official merge endpoint](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request).

Automatic merge is disabled unless the installed project supplies an explicitly qualified `strict-status` mechanism and live protection requires strict up-to-date checks, the named gate context, and administrator enforcement. Pass `qualification:{qualified:true,targetFreshness:'strict-status'}` only after a disposable-repository exercise demonstrates rejection when another actor advances the target after the final local read. `inspectProtection` checks settings; it does not itself qualify behavior. The reference does not implement merge-queue qualification. A project without supported remote protection remains manual-only. Private repositories may need an account plan supporting protected branches; see [protected branch API availability](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection) and [strict required checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## Owned workspaces

`prepare({root,stateDir,projectId,flowId,baseRef,setup?})` creates a deterministic branch/worktree under private state and writes an ownership manifest before Git effects. It returns `{path,branch,base,head,ownershipDigest,manifestPath,setupDigest}`. Repeating the same identity reuses it. Changed setup is rejected. A setup interrupted after its persisted running intent remains uncertain and requires inspection; it is not blindly replayed.

- `inspect({workspace})` verifies manifest, worktree registration and branch; it reports dirty files, head, unpushed work and recorded leases.
- `commit({workspace,message,paths?})` stages and commits inside the owned tree using repository attribution. No-change calls retain the existing commit.
- `integrateTarget({workspace,remote,target})` fetches the explicitly configured remote target and merges it. Conflicts remain in the worktree and are reported for correction; no reset discards them.
- `push({workspace,remote,expectedHead?})` requires a clean owned worktree, optionally checks its candidate identity and performs an ordinary non-force push of the owned branch. A pinned fetch refreshes remote tracking before upstream setup. Non-fast-forward server changes are rejected by Git.
- `release({workspace,preservation,leases?,openPR?,unresolved?,dryRun?})` defaults to inspection. Dirty work, live obligations or absent preservation prevent removal. Supply the canonical obligations from current project state; this adapter cannot infer runner/provider liveness by itself.

`adoptCandidate({root,stateDir,projectId,flowId,attemptId?,number,expectedHead,expectedBase,forge,remote,target,setup?})` validates an explicitly approved open, nondraft PR and its current candidate/target. It fetches GitHub's PR head ref and the target branch into private refs of this attempt's own (`refs/factotum/adoptions/<flow>-<attempt>` and `refs/factotum/adoption-targets/<flow>-<attempt>`), verifies the head's SHA, checks that `expectedBase` is the target's fetched head or one of its ancestors through hash-verified parents (`VerifiedObjects.reaches`, in a checkout without replace refs or grafts; not GitHub's cached `base.sha`, which lags after a push), and creates a new owned worktree/branch from that exact commit. On any mismatch it throws `AdoptionMismatch` with `adoptionMismatch.mismatches` (`{field: state|target|head|base|repository, expected, found, fix}`) and the refs it fetched, before any worktree exists; the reference `candidate` step turns that into a `candidate-mismatch` hold. The `head` row's `fix` says what is known about the cause (dev.84): the approved commit is an earlier commit of the pull request (read with the bounded PR commit list; whether it moved after approval or an earlier commit was approved is not guessed), the approval named a commit on the target, the approval named a commit the pull request does not have (or it was force-pushed since), or, when the commit list cannot be read, that either may be the case. The original branch and PR remain untouched. It returns `{workspace,originalPR:{number,url,head,base,approvedBase,targetHead},adoptionRefs}` (`base` is GitHub's reported base, for the record); the workflow must retain the original PR's disposition as an explicit obligation if it publishes a replacement. The reference workflow also comments once on the original PR when the replacement is published (`repository.adoptionNotice`, default `true`), names the original PR and author in the replacement's body, and reports commits pushed to the original after adoption; see [adoption](../adoption.md#task-to-delivery-commissioning).

Preservation is either `mergedInto`, whose locally available commit must contain the candidate, or an externally stored `archivePath`, whose verified Git bundle contains the candidate. Fetch a successful remote merge before using its SHA as local preservation evidence. An unpushed branch can only be deleted after that explicit preservation proof. Cleanup retains a private receipt, never removes the main checkout, and never deletes remote branches or repositories. A crash after worktree removal reconciles the recorded cleanup intent rather than recreating work. Open PRs and unresolved effects must remain fenced by the owning workflow until their canonical disposition is known.

`tests/forge-workspace.test.mjs` exercises local bare remotes and simulated GitHub responses. Live repository qualification is a separate retained private exercise; no credentials, personal account identities or live repository URLs belong in tracked fixtures.

## Project issue profiles

Set `repository.issueProfile` in private configuration to adopt an existing issue format. Structured briefs may additionally carry `area`, `category`, `paths` and `parent`. Prose extraction is opt-in and reads bullet/checkbox items beneath configured Markdown headings or bold heading lines. It never treats issue text as executable configuration. Imports preserve scope and grouping but always require a separate canonical revision approval.

```json
{
  "acceptanceHeadings":["Checked in the build"],
  "postMergeHeadings":["Checked after merge, by whom"],
  "pathsHeadings":["Files"],
  "proseDependencies":true,
  "ordinaryLabels":["ordinary"],
  "strictLabels":["strict"],
  "blockedLabels":["blocked","needs/operator"],
  "forbiddenLabels":["kind/decision","kind/research","group"],
  "importBlockedLabels":["in-progress","in-review"],
  "areaPrefix":"area/",
  "categoryPrefix":"kind/",
  "requireArea":true,
  "requireParent":true,
  "rejectOpenPR":true,
  "followupLabels":["ordinary","backlog"],
  "lifecycle":{"labels":{"admitted":"in-progress","review":"in-review","completed":"done","stopped":"parked"},"approvalLabel":"approved"}
}
```

`proseDependencies` recognizes issue references after “depends on”, “blocked by” and “waits on”. Dependencies are canonical local task IDs after import; an absent or incomplete dependency remains ineligible. `requireParent` reads the actual GitHub parent relation and rejects a conflicting declared parent. `rejectOpenPR` checks open PR closing references, rejecting incomplete pagination. It does not infer ownership from arbitrary PR prose links. `importBlockedLabels` prevents importing work already under another controller; ongoing source verification does not treat the factory's own progress label as revocation.

`publishLifecycle({issue,phase,operationId,expectedRevision,body?})` uses a stable marked comment and reconciles configured state labels. It preserves unrelated labels and removes the configured approval label on completion. Only managed lifecycle/approval labels are excluded from the content revision; governance, blocked labels, full issue content, grouping and scope changes still invalidate approval. Consequently GitHub approval labels are presentation and cannot grant or revoke canonical authority. Use canonical task approval/revocation commands for authority. Label updates have no atomic compare-and-swap with the source issue; a single canonical writer remains required.

`createFollowup({flowId,reviewDigest,task,findings,prNumber})` reconciles a marked unapproved issue, preserves configured area/grouping metadata, and posts a stable PR comment linking it. It refuses approval labels. Parent attachment uses the GitHub [sub-issue API](https://docs.github.com/en/rest/issues/sub-issues) and reconciles existing parentage before attachment. A conflicting parent fails closed. Marker recovery scans all issue pages, so very large repositories should account for API cost when enabling automatic followups.

Lifecycle hooks run within supervised delivery actions, so interruptions retain the owning attempt and recover the same publication identity. Stopped-flow publication requires a durable operational outbox; configuring a stopped label alone does not cause an external write from the synchronous stop transaction. Labels must already exist in the repository. Commission the complete private issue profile before approving imported work.

`publishReviewedPlan({issue,taskRevision,operationId,body})` maintains one canonical marked plan comment per issue and updates it to the exact reviewed content. A lost create/update response is reconciled by rereading that same comment and comparing the full desired body. Concurrent independent plan writers are unsupported: GitHub comment PATCH has no revision precondition. The delivery graph owns one planning flow per task and revalidates its source before publication.

## Historical external dependencies

A migrated backlog may depend on closed issues that never ran through this factory. Import records these as `source.externalDependencies` facts with repository/issue identity, observed GitHub state, content revision, observation time and `github-issue-state` provenance. A closed historical issue can satisfy that explicit external prerequisite without creating a local completed task or claiming that Factotum verified its outcome.

Numeric dependencies, numeric strings, explicit `github:NUMBER` references and `#NUMBER` references map to the default `github:` task namespace. An optional `issueProfile.dependencyIdPrefix` changes the namespace for imported tasks and their numeric dependencies together; explicit references using that configured namespace are remote prerequisites too. The prefix may not be `upkeep:` in any letter case: that task namespace is reserved for tasks the factory itself writes. Custom local task IDs remain local dependencies. Self-dependencies are rejected. `issueProfile.maxDependencies` bounds discovery (default 32, maximum 100). Missing resources, access failures and unreadable states remain `unknown`, which cannot satisfy admission. Closed issues do not need acceptance briefs to provide a state fact.

Admission may use an exact matched closed external fact. Before planning, building and merging, the source-verification boundary rereads every declared remote dependency and requires it still to be closed. It also checks that retained facts cover every declared remote prerequisite; older imports with missing facts require reimport rather than skipping validation. Reopened or unavailable prerequisites stop execution; historical facts do not authorize work after their state changes. Fresh observations are retained with the action's evidence. GitHub cannot atomically fence a dependency state against a later model or merge operation, so these are bounded fresh checks, not a transaction across GitHub resources.

Reimporting unchanged dependency state/content preserves its original observation identity so a no-op import does not revoke canonical task approval. A changed dependency state or revision changes the imported brief and requires renewed approval. To resolve an unknown/open fact, reimport the current source and approve its new canonical revision; do not manufacture completion records for historical work.


## Merge method and preserved history

`repository.mergeMethod` accepts `merge` (default), `squash`, or `rebase`. Every method uses the exact reviewed PR head, the same target checks and the same qualified automatic-merge requirements. Rebase delegates commit identity rewriting to the forge and does not supply a merge commit title/message.

**Commit titles on the target.** With `merge` and `squash` the factory titles the commit `<task title> (#<PR number>)`, as GitHub titles squash commits, so `git log --first-parent` reads by task. The title is one line without control characters, at most 100 characters (a longer task title is shortened with `…`), and falls back to `Factotum delivery (#<PR number>)` if the task title would read as a GitHub closing reference. The message is `Approved and independently verified candidate.` followed by `Task: <task id>` and `Factotum flow: <flow id>`, so the flow stays traceable from history. With `merge` the builder's own commits keep their messages on the second parent. `rebase` adds no factory commit: GitHub replays the candidate's commits, whose messages the factory wrote as the task title and `Factotum flow: <flow id>`. Releases before dev.82 titled every merge `Factotum delivery <flow id>`; `git log --grep <flow id>` finds a flow's commit in both.

**Remote branches.** The factory never deletes remote branches: each delivered flow leaves its `factotum/…` branch on GitHub. Turn on the repository setting *Automatically delete head branches* to have GitHub remove them when their PR merges, or delete them yourself. Cleanup works from the local branch, and squash and rebase deliveries are preserved in a local bundle first, so removing the remote branch after the merge loses nothing the factory needs.

**The reviewed-plan comment.** `forge.publishPlan` keeps one comment per issue, rendered as Markdown: the plan summary, steps, files, checks, risks, the risk assessment (threat model and stop conditions for strict work), departures, unverified acceptance and open questions, then the plan review's verdict, summary and findings, and the flow ID. Plan and review text comes from models, so it is escaped: no raw HTML, no links or images formed from model text, and every `@` is followed by a word joiner so nobody is mentioned. Each field and list is bounded (at most 40 items, longer lists say how many more) and the comment stays under 60,000 characters. Nothing reads the comment back. The complete plan and review are the plan and plan-review attempts' `action-result.json` (the console shows attempt artifacts, or read them under `<state-dir>/attempts/<attemptId>/`). Releases before dev.82 posted the plan and review as JSON; the next publication on that issue replaces it.

Squash and rebase do not prove that the original reviewed branch is an ancestor of the target. Before cleanup, the factory creates a complete Git bundle of the exact owned reviewed head under private `archives/workspace-commits`, verifies its refs and full history, writes a checksummed scope receipt and fsyncs the bundle and containing directories. Only then may the owned worktree and branch be removed. Missing, changed or invalid archives keep the checkout for inspection. Interrupted cleanup reuses the same verified archive and receipt; it never recreates a deleted worktree. These bundles are part of the project's preserved state and backup inventory.

## CLI quiescence and plan-publication recovery

Both API calls and Git account credential lookups disable GitHub/extension update notifications, interactive prompts, pagers, forced TTY and color output. API CLI invocations also use a bounded, owned subprocess group; timeout, output overflow or surviving descendants are ambiguous transport failures rather than successful leader exits. The outer supervisor’s descendant containment rule remains in force. Private CLI stderr is classified without exposing its contents.

A successful remote write does not make a failed containment receipt successful. Preserve the original receipt and external publication evidence. A terminal failed flow cannot use `resume`, which is for stopped flows. After correcting the executor and performing drained activation/recommissioning, a fresh `flow.start` may be requested under current task approval and admission policy. It re-verifies the source and replans as needed; it does not mark the old attempt successful.

Reviewed-plan publication owns one stable comment marker per source issue. An exact payload match reconciles without a write; a different newly reviewed plan updates that same canonical comment. The per-flow operation identity is included in its input marker but does not create a new plan-comment identity. Multiple matching canonical comments fail closed for inspection. This upsert contract is specific to reviewed plans; do not assume every external publication can be restarted under a new flow ID.
