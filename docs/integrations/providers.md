# Subscription CLI providers

The starter includes Codex and Claude Code adapters in `starter/factory/adapters/providers/index.mjs`. Projects select provider and model identifiers explicitly. Metered API and third-party gateway routes are refused. These adapters run locally and do not require T3.

`preflight(spec)` checks the installed executable, required flags and subscription authentication before invocation. `invoke(spec, { signal })` repeats preflight and returns a complete, locally schema-validated receipt. The spec is `{ provider, model, role, prompt, cwd, artifactDir, schema?, sessionId?, timeoutMs, readOnly?, maxTurns?, effort?, allowedModels?, allowFallback?, fallback? }`. Roles are `planner`, `builder`, `reviewer`, `auditor`, `reader` and `scoreboardOwner`; the exported `PLAN_SCHEMA`, `BUILD_SCHEMA` and `REVIEW_SCHEMA` define the built-in contracts. An integration may supply a schema within the documented validator subset. Sessions may resume only for builders. Every independent planner or reviewer starts fresh.

The normalized result is `{ provider, model, family, sessionId, result, usage, permissions, billing, started: true, final: true }`. The provider family is `openai` or `anthropic`. A zero-exit process alone is insufficient: a successful final turn, session identity, usage and valid complete structured output must all be present. Fallback is off by default. An explicitly configured `allowFallback:true` with one `fallback:{provider,model,...}` permits one alternative only after a positively unstarted preflight or executable-spawn failure. Invalid billing, allowlist, schema or cancellation never triggers fallback. A reviewer may come from the same model family as the builder, so a same-family reviewer launches its own configured primary; fallback is never used to switch family. A resumed builder never changes provider. Once a model process has started, quota messages, malformed output, transport loss and timeout remain uncertain and never trigger fallback. A started failure in which the provider reported its usage limit reached is raised as `USAGE_LIMIT` (still started, uncertain and never a fallback); see [Usage limits](#usage-limits). The receipt names the actual provider/family and records fallback provenance. After the model process has started, malformed output, transport loss, timeout and cancellation are conservatively marked `started: true` and `safeToRetry: false`; callers must reconcile effects before a new invocation. Preflight refusals are marked as not started. The retired `independenceFamily` and `allowSameFamilyReview` spec fields are ignored. The delivery review records the builder and reviewer provider, model and family (`pairing`) and marks `independence: same-family` or `different-family`.

## Authentication and configuration

Authentication remains in each CLI's private credential store. Do not put credentials in project configuration or persisted attempt specs. The adapter constructs an allowlisted environment shared by preflight and invocation, removing API keys, custom endpoints, cloud-provider routing, inherited agent hooks and Node injection variables. Home/config-directory paths needed to locate existing subscription credentials are preserved; their contents are never copied into the project.

Codex must report ChatGPT authentication. Invocation selects the OpenAI provider and ChatGPT login method, ignores user configuration and policy rules, and explicitly selects the sandbox and model. Claude must report authenticated `claude.ai`, first-party routing and a recognized subscription account type. Claude runs with safe mode, empty user/project/local setting sources, strict empty MCP configuration, explicit tools and no interactive permission prompts. `--bare` is intentionally unsuitable because it excludes subscription OAuth authentication.

Managed machine policy and credential-store ownership remain operator responsibilities. CLI login and invocation are separate processes, so replacing credentials or executables between them is outside this single-operator trust model. Never enable a gateway, API-key helper, account extra-usage policy or other billing route under the assumption that this adapter provides an account-level spending ceiling.

`billing.mode: subscription` identifies the verified authentication route. `billing.actualMicros: 0` records no metered API charge attributed by this adapter; it is not a valuation of subscription tokens, a subscription allowance guarantee or proof that an account's extra-usage settings cannot charge. Provider-reported token usage is retained separately. Subscription quota exhaustion fails the attempt; it never triggers a metered API fallback.

## Usage limits

Subscription plans have usage windows. The adapter reads what each CLI reports in its own output while a model step runs and attaches it to the invocation record as `limits: [{window, utilization, resetsAt, status, source, plan?}]`; nothing extra is run to ask for it.

- **Claude Code** (`stream-json`) emits `rate_limit_event` messages with `rate_limit_info.status` (`allowed`, `allowed_warning`, `rejected`), `utilization` (0 to 1), `resetsAt` (epoch seconds) and `unifiedWindows` per window (`five_hour`, `seven_day`, …). A refused request carries `api_error: "usage_limit_reached"` with `api_error_params.rate_limit_info`. The plan comes from `auth status --json` (`subscriptionType`).
- **Codex** (`exec --json`) reports no usage percentages in its event stream (observed with 0.169.0). Its usage-limit error arrives as an `error` / `turn.failed` message ("You've hit your usage limit…"), whose reset time is localized text and is not parsed. A `rate_limits` object (`primary`/`secondary` with `used_percent`, `window_minutes`, `resets_at`, plus `plan_type`) is read if a future stream includes one.

The factory keeps the latest report per provider (one CLI login per provider on the host) in project state:

- At `policy.providerLimitNoticePercent` (default 90) of a window, the operator gets one notice per window (`provider-limit:<provider>:<window>:<reset>`).
- When a provider reports its limit reached, or a window reaches `policy.providerLimitHoldPercent` (default 100), new work that would start that provider is held until the reported reset (the latest one when several windows are exhausted), or for `policy.providerLimitDefaultHoldMs` (default 5 hours) from when the limit was observed when no reset time is reported. A reset that has already passed when the report is recorded (a delayed settlement) holds nothing. A refusal reported both as a typed signal with a reset and as error text without one counts once, with the typed reset. A malformed or out-of-range reset reads as not reported for that signal only. An automatic hold lasts at most 8 days; a reported reset further away is held to that bound and the hold notice says so (the operator can extend with `provider.hold`). Flow admission (queue, `flow.start` and `task.restart`, checked against the routes the run would pin: saved defaults, the task's model choice and run overrides) shows `<provider> usage limit hold until <time>: <reason>` as a queue reason; a running flow's next model step waits (`flow.providerHold`), and a step prepared before the hold is fenced at dispatch at zero cost. Running work is never interrupted. A step whose route could start a provider that is not held is not held: a step routed to another provider, or one with a configured fallback, which the adapter then uses after refusing the held provider before start (`USAGE_LIMIT_HOLD`, positively unstarted). A resumed builder session never changes provider, so it waits.
- The hold clears by itself at its time. `provider.hold {provider, action: "clear" | "extend", until?, note}` lets the operator end it early or extend (or start) one; both are recorded with the actor and note.
- An attempt that ended on the limit stays `uncertain` (the reconciliation contract) with `classification: "limit-exhausted"` and `limit: {provider, model, window, resetsAt, source, errorCode}`. It is never retried automatically and never re-run on another provider; reconcile it with `attempt.resolve`.
- Stats → Provider limits and the console overview show current windows, holds and limit-exhausted attempts.

These are reports, not guarantees: a provider can refuse work before a threshold is reached, and the factory cannot see usage from other clients sharing the login until its next model step reports it.

## Permissions and process ownership

Codex planners and reviewers use its enforced read-only sandbox. Builders use its workspace-write sandbox. Claude planners and reviewers have only `Read`, `Glob` and `Grep`, combined with restricted mode and plan permissions; they cannot run Bash or invoke an editing tool. Claude builders have a restricted explicit tool set with `Read`, `Glob`, `Grep`, `Edit`, `Write` and `Bash`. Shell execution is not an operating-system filesystem sandbox. The returned permission label distinguishes Codex's `provider-sandbox`, Claude's read-only `provider-tool-allowlist`, and Claude builder `provider-restricted-tools`. Use an external sandbox if shell containment is required by project policy; reject unsupported modes rather than treating the label as proof of isolation.

**Project scripts that workers run.** Inside the Codex Linux sandbox (observed with codex-cli 0.169.0 and Node 26, in both read-only and workspace-write mode), Node's `spawnSync`/`execFileSync` returns `EPERM` whenever the child's stdin is a pipe — Node's default, including `input: ''` — even though the child runs and exits successfully. Commands run through the provider's own shell are unaffected. Project helper scripts that planners or builders are expected to run (readiness checks, path classifiers, generators) should spawn children with `stdio: ['ignore', 'pipe', 'pipe']` (or `'inherit'` for stdin) unless they genuinely need to write to the child's stdin. Otherwise a worker reports the step as unverified or blocks on it.

Every invocation owns a new child process group. Timeout and cancellation terminate that group, escalating to SIGKILL; they never signal the caller's group. The factory supervisor still owns the outer attempt and reconciles interruption. `timeoutMs` is mandatory. Claude accepts optional `maxTurns` (passed as `--max-turns`); Codex has no claimed provider turn cap in this adapter (`codex exec` takes none), so a Codex step is bounded by its timeout only.

**Turn limits** (dev.84). Every Claude model step runs with a turn limit: the route's `maxTurns` when set, otherwise 60 for builders and 16 for planners, reviewers and other roles (`DEFAULT_MAX_TURNS` in `adapters/providers/routes.mjs`; before dev.84 every role, builders included, got 16, which is where a strict build's end "after 17 turns" came from: Claude counts the turn on which it stops). Set it per role with `providers.<role>.maxTurns`, or per step with `stepModels.<workflow>.<step>.maxTurns` next to that step's `model`; both must be whole numbers from 1 to 500. A flow pins its routes when it is admitted, so a changed limit applies to flows started after the change. When Claude stops at the limit it ends with a final result of subtype `error_max_turns`, `is_error: true`, `num_turns` and `total_cost_usd`. The adapter raises that as `MAX_TURNS` (still `started: true`, never a fallback) with `turnLimit {provider, model, subtype, turns, maxTurns, costUsd, sessionId}` and the usage it reported, instead of the generic `INVALID_RESULT`. The factory treats it as a known end, not an uncertain one: a builder's turn limit becomes a build question whose `retry` resumes the session with the reviewed plan; a planner's or reviewer's settles the attempt as failed (`classification: "turn-limit"`) and stops the flow at that step for `resume` (see the [running guide](../running.md#build-questions)). Any other unsuccessful Claude end stays `INVALID_RESULT`, and its message now names the subtype, the turn count and the reported cost, and that the output is in the attempt's provider `stdout.jsonl`. Output capture is bounded. Prompts travel through stdin rather than command arguments.

The supplied artifact directory must be private and outside tracked source. It receives schema, stdout JSONL, stderr and normalized result files with private modes. Traces may contain source text and provider account metadata: do not publish raw traces or use them as committed fixtures. Apply the factory's evidence retention policy. Cancellation can produce no complete trace; absence of a final artifact is not proof the provider did no work.

## Schema support

Local validation supports `type` (including nullable type arrays), `properties`, `required`, `additionalProperties`, `items`, `enum`, numeric `minimum`/`maximum`, array `minItems`/`maxItems`, string `minLength`/`maxLength`, and descriptive `title`/`description`. Unsupported keywords fail closed. No remote schema references or general JSON Schema implementation are claimed.

## Qualification

Run deterministic provider contract tests with `node --test tests/providers.test.mjs`. These use explicitly synthetic protocol messages and fake transport to exercise routing, permissions, resumptions, malformed/partial output, schema validation and rejection. Process tests use real disposable subprocesses for timeout and cancellation. Synthetic tests cannot prove real provider auth, billing or isolation.

Run a deliberately authorized subscription smoke using `node evals/provider-smoke.mjs codex MODEL` or `node evals/provider-smoke.mjs claude MODEL`. Each creates its own fictional temporary Git repository and private artifacts, reads a known file and validates a structured review. It does not modify an existing project or contact GitHub. The model must report a sentence available only in that fixture file. Real smokes were exercised against Codex CLI 0.163.0 and Claude Code 2.1.308; those observations do not promise compatibility with arbitrary later versions. Every invocation still probes required installed capabilities.

The contracts follow [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode), the [Claude CLI reference](https://code.claude.com/docs/en/cli-reference) and [Claude authentication documentation](https://code.claude.com/docs/en/authentication). Installed help and live fictional smokes qualify the actual local flag and output behavior.

## Role policy and reports

Each configured role may set `effort` and an `allowedModels` array. The selected model must be in that array when supplied; a fallback uses its own allowlist or inherits the original role allowlist. Codex receives `model_reasoning_effort`; Claude receives its capability-probed `--effort` option. Omit unsupported effort values rather than assuming different CLIs interpret them identically. Commissioning checks all configured roles and enabled fallbacks. Optional audit, interpretation and journey-owner roles can use distinct models without changing development roles.

The migration delivery graph uses `DELIVERY_BUILD_SCHEMA`, `RISK_PLAN_SCHEMA` and `CHANGE_REVIEW_SCHEMA`. Worker reports retain departures, unverified checks, explicit questions and rule pushback. Delta reviews retain scope and prior-finding disposition evidence. Legacy exported schemas remain available for integrations that use their narrower contracts. Role names do not grant extra tools: all non-builder roles default to read-only tools; project journey/deployment adapters own any authorized product interactions.

Shipped starter defaults (`starter/project/factotum.template.json`): planner and builder `claude` / `claude-opus-5-5`, reviewer `codex` / `gpt-6.1-sol`, and `claude-fable-5-2` in the Claude roles' `allowedModels` for the most important or complex work. These are the identifiers passed to each CLI's `--model`; Claude Code also accepts its short aliases, which resolve to a version the CLI chooses, so the template pins full identifiers. Existing project configurations are not changed.

Example private role configuration:

```json
{"provider":"codex","model":"approved-builder-model","billingMode":"subscription","effort":"high","allowedModels":["approved-builder-model"],"allowFallback":true,"fallback":{"provider":"claude","model":"approved-alternative-model","allowedModels":["approved-alternative-model"]}}
```

Allowlist entries are project policy, not a claim that the illustrative model names exist. Positive metered ceilings remain disabled unless separately implemented and commissioned.
