# Trial R5: external pull request adoption

The dev.81 readiness trial adopted outside pull requests with `flow.start` and `candidate {number, head, base}`. The normal path worked end to end (candidate → integrate → fast-check → publish → review → gate → operator merge → cleanup). It found four defects on that path and one related admission race. This records each problem, the change, compatibility and tests. It is a local implementation record, not a release, activation or live qualification claim. No real GitHub call was made: dispatch-level tests use a fake `gh` executable, adapter-level tests use the existing fake forge transport (`createGitHub({transport})`).

## 1. A closing keyword in an adopted commit was rejected only at merge

**Problem.** An outside commit "Tidy docs whitespace. Fixes #11" went through candidate, integrate, fast-check, publish (replacement PR opened), a review model call and gate. The operator answered `merge`, and `forge.merge` refused it ("GitHub closing references require explicit task disposition; use plain task references"). The flow ended terminally `failed` with the generic notice "Change workflow failed; inspect retained attempt evidence", the replacement PR stayed open, and the factory cannot reword an outside commit.

**Fix.**

- The rule is now one function in the GitHub adapter: `closingReference(text)` returns the matched reference (for example `Fixes #11`) or null; `assertNoClosingReferences` uses it, so PR prose, merge messages and commit messages are checked exactly as before. The merge step's commit enumeration moved into `readPRCommits(number, {expectedHead, expectedCount})` (same 1–250 bound, same completeness checks) and merge calls it.
- The `candidate` step (`workspace.adopt`) now first reads the PR and its commits through those two functions (`workflows/adoption.mjs`, `adoptionCommitCheck`). This runs before any worktree is created, before integration, publication and any model call.
- On a violation it returns `route: "held"` with `adoptionHold: {kind: "closing-reference", number, head, commits}` (a privileged field of `workspace.adopt` only). The engine stops the flow at `candidate` (not `failed`), records `flow.adoption-held`, and the stop notice says which commit and keyword, why, and the options: ask the author to reword with a plain reference (for example `Refs #11`) and push, or re-create the commit yourself; then `flow.abandon` and `flow.start` with the new head. A PR with more than 250 commits (which merge could never validate) stops the same way with `kind: "commit-limit"`.

**Could the merge-time rule be satisfied another way for adopted candidates?** Evaluated: with `repository.mergeMethod: "squash"` the factory writes the squash commit's title and message itself, so the outside commit messages never reach the target and could not close an issue through it. Merges into a branch that is not the repository's default branch do not close issues either. Either could justify relaxing the commit-message check for adopted candidates. Neither is done: the merge adapter checks commit messages for every merge method and target, the merge method is project configuration rather than a per-flow choice, and switching it for adopted flows would change what history the target keeps. Merge semantics are unchanged. Operator decision (after review of this record): keep one rule for every merge method and target.

**Compatibility.** The reference graph and its digest are unchanged (no reapproval). The adoption step makes two more GitHub reads (the PR and its commits). Flows already past `candidate` are unaffected; a closing keyword in a commit the factory's builder adds later is still refused at merge as before. A PR with more than 250 commits now stops at `candidate` instead of failing at merge.

**Tests** (`tests/external-pr-adoption.test.mjs`): the adapter finds `Fixes #11` in the second of two commits and the merge step refuses the same commit (one rule); a plain `Refs #11` passes; the real `workspace.adopt` dispatch path returns the hold with no worktree created and no forge write; settling that result stops the flow at `candidate` with the specific notice and the `flow.adoption-held` event. The existing adoption test in `tests/delivery.test.mjs` now gives its fake PR a commit count and commit list.

## 2. A commit pushed to the adopted PR while its flow ran was dropped silently

**Problem.** A second commit pushed to the original PR 14 s after `flow.start` was never delivered. The flow merged the approved, pinned head, closed the task and ended `completed`; nothing said so, and the `original-pr` obligation ("Review and close the superseded original PR") would discard the commit if followed.

**Fix.** Pinning stays. The drop is made visible:

- `observeOriginalPR(forge, candidate)` reads the original PR through the forge adapter. Unchanged head: `status: "unchanged"`. Moved head: `status: "moved"` with the commits after the adopted head (up to 20 listed, with a count), or `rewritten: true` when the adopted head is no longer in its history. A failed read: `status: "unknown"` with the error; it is never reported as unchanged.
- **Merge question.** For an adopted flow, the effect that leads straight into a merge question (gate, or preview when configured; review in document workflows; any step in a project-owned graph) gets `observeOriginalPR` in its intent (`actions.mjs`, `leadsToMergeQuestion`), and dispatch adds `originalPRObservation` to its result. The engine keeps the latest on the flow (`flow.originalPRObservation`). The merge question's `context` always says what is known: unchanged since adoption (with the time checked), moved with the commits not included and the PR link, could not check, or not checked.
- **Merge and completion.** `forge.merge` and `postMerge` read the original again. When it moved, or could not be read, the completion notice of the flow starts "The adopted head … was merged." and lists the commits not delivered, with the PR link.
- **Obligation.** The `original-pr` obligation now reads "Review and close the superseded original PR after replacement delivery. If commits were pushed to it after adoption, they are not delivered: do not close it without handling them (adopt it again with the new head, or ask the author)." After merge, `postMerge` records it again with the drift text when the original moved (see item 3 for automatic resolution).

**Compatibility.** New flow field `originalPRObservation`, new result field of the same name, new question fields `context` and `originalPR` on adopted merge questions. The question's subject digest is unchanged, so an observation never invalidates an open question. One to two extra GitHub reads per step that leads into the merge question, and per merge and post-merge step, on adopted flows only. Non-adopted flows are unchanged.

**Tests:** observation of a moved PR lists exactly the new commit; unchanged gives no drift text; a transport error gives "Could not check …"; a rewritten history is named. The real `gate` dispatch path with `observeOriginalPR` returns the observation, and without it does not. The merge question names the head move, the commit not included and the link; an unknown observation and a missing one are each stated. A completed adopted flow whose original moved leaves a completion notice naming the commit.

## 3. The outside author got no signal

**Problem.** Nothing was posted on the original PR; the replacement PR's body did not name the original; the `original-pr` obligation stayed pending even when GitHub already showed the original merged.

**Fix.**

- **Comment on the original PR.** When the replacement is published, `forge.publish` comments once on the original PR: "This pull request was adopted for delivery. Its commits up to <head> are carried unchanged in a replacement pull request: <link>. Review and merging happen there. Commits pushed here after adoption are not included automatically; the project's maintainers decide how to handle them." It is marked like other factory publications, so a retry does not post twice. Configurable with `repository.adoptionNotice` (boolean, default `true`), following the existing `repository.*` boolean pattern (`closeTasks`, `rerunFailedChecks`); validated, shown in Settings → Repository and in the starter template. A failed comment is recorded as `originalPRNotice: {status: "failed", error}` on the publish result and never fails the publication.
- **Replacement body.** For adopted flows the body adds "Adopted from pull request #N by <author> (<link>): its approved head <head> is delivered here unchanged." `readPR` now returns `author` (the PR's `user.login`), captured at adoption.
- **Obligation resolution.** After merge, `postMerge` resolves the `original-pr` obligation (`status: "passed"`, `resolution`) when GitHub already shows the original merged or closed and its head is the adopted one. When it has extra commits it stays pending with the drift text from item 2; when the read fails it stays pending with "Could not check …". An obligation the operator already resolved (`obligation.resolve`) is not reopened by this automatic record (engine: a result obligation whose stored record has `resolvedAt` is skipped).
- **Sanitising.** Both texts are model-free. The author login goes through the plan comment's `markdownText` (Markdown/HTML escaped, `@` followed by a word joiner), so the replacement body never mentions anyone. The comment on the original PR contains no login, no `@` and no closing keyword; it lives in the author's own PR thread. `#N` in the replacement body is a link to the original PR, not a mention of a person.

**Compatibility.** One more GitHub write (the comment) per adopted publication unless turned off. Existing configurations without the key get the comment. The replacement PR body gains one line for adopted flows only; `createPR` still refuses closing references in it. GitHub can take a moment to mark the original PR merged after a commit-preserving merge, so the obligation may stay pending right after a merge that just happened.

**Tests:** the real `forge.publish` dispatch path posts the replacement body with "Adopted from pull request #1 by outside\-dev (…)" and no `@outside`, and one marked comment on the original with the replacement link and no mention or closing keyword; `adoptionNotice: false` posts none; a failing comment is recorded and publication still succeeds. The real `postMerge` path resolves the obligation for a merged original, keeps it pending with the drift text for a moved original, and pending with "Could not check" for a failed read. An operator-resolved obligation is not reopened.

## 4. The orchestrator could answer an adopted PR's merge question

**Problem.** `answer merge` as `--actor orchestrator --instruction 'trial'` was accepted and merged. The question's role was `operator`, but default delegation of operator answers applied. SETUP_CHECKLIST, project-workflows.md, the workflows skill and adoption.md say adopted PRs stay with the operator and always need manual adjudication.

**Fix.** Enforced the way strict sign-off is enforced, in the `answer` command before any state changes: for a merge question (`mergeDecision`) of a flow with `candidate`, any actor other than the operator is refused with "an adopted pull request's merge question is answered by the operator only; a recorded instruction or delegated operation does not apply. The question stays open for the operator". The check comes before delegation is evaluated, so no setting widens it: `policy.delegatedOperations` (including `answer`), `onBehalfOf`, `policy.mergeDecisionRole: orchestrator` (already excluded adopted candidates) and `policy.strictDecisionRole: orchestrator` (an adopted strict question now opens with role `operator`, and `strictReviewRequirement.requiredRole` says `operator`). `autoMerge` already excluded adopted candidates. The refusal is an ordinary rejected command: the question keeps its status and version, no authorization is recorded. As a recheck, `verifyDecision` (run before the merge step prepares) refuses a merge authorization of an adopted flow whose actor is not the operator, which covers an authorization recorded before this change on a flow still in flight.

**Compatibility.** The whole adopted merge question is operator-only, including `send_back` and `stop` (the orchestrator can still use `flow.stop`). Non-adopted merge questions keep their delegation. Docs updated: commands.md (the delegation table and the kept checks), project-workflows.md, SETUP_CHECKLIST.md, the factotum-workflows skill and adoption.md.

**Tests:** with `delegatedOperations: ["answer"]` and `mergeDecisionRole: "orchestrator"`, the orchestrator's `merge` without an instruction, `merge` with one and `stop` with one are each refused with that message; the question stays open at the same version with no authorization; the operator's answer then succeeds; `verifyDecision` refuses an orchestrator authorization on the adopted flow. A strict adopted candidate with `strictDecisionRole: "orchestrator"` opens for the operator and refuses the orchestrator. A non-adopted merge question still accepts the orchestrator on instruction.

## 5. Admission while a merge was in flight

**Problem.** A flow admitted at 12:53:28.443, during another flow's merge attempt (12:53:25.155–12:53:29.609), stopped at `source` with "main is not verified for source admission … then resume this flow". Nothing held admission during a merge, so with more than one slot this produced stopped flows that needed a manual resume.

**Fix** (`operations/merge-hold.mjs`), fitted to the existing hold model (G5 tiers, target-sync holds, provider waits):

- **Admission.** `mergesInFlight(store, target)` lists open, unstopped flows whose current step is a `forge.merge` for the target (answered `merge`, preparing or running). While any exists, `admissionReasons` adds `<target> merge in progress (flow …); new work waits for it and its post-merge verification`, and `queueStatus` shows a `merge` hold. After the merge settles, the existing health rules hold admission until the post-merge verification is green (merge settlement already sets health `unknown`).
- **Flows already admitted wait at source instead of stopping.** `sourceWait` returns a wait when a merge into the target is in flight, or when the target's health is not fresh green (and not red) and a `main.verify` for it is queued or running. The engine checks it in three places: before preparing a `source.verify` attempt; in the dispatch transaction (a prepared attempt is recorded `not-dispatched` at no cost instead of the previous stop); and when a `source.verify` result reports the target moved. In each case the flow is `waiting` with `targetWait {kind: merge|verification, reason, target, since}` and events `flow.target-wait` / `flow.target-released`; an unchanged wait writes nothing, so parked questions are not woken. When the target is verified green and no merge is in flight, the next tick prepares source verification by itself; no resume is needed. Source visits are not consumed while waiting.
- **Not changed.** A red target, a target needing verification with none queued or running (for example `autoQueue` off), and a pending or held target synchronization keep their documented stop-at-source behaviour. Stopped flows at a merge step (for example an uncertain merge) do not hold admission.
- **No history scans.** Both reads use the verified live sets from `core/records.mjs` (`store.live('flow')`, `store.live('job')`), filtered in JavaScript: open, unstopped flows whose current step's operation is `forge.merge` for the target, and queued or running `main.verify` jobs for it. No new code reads `records.data` with SQL JSON functions. (Before main's idle-history change was merged, these were two direct SQL queries; they were switched during that merge.)

**Compatibility.** `flow.start` and queue dispatch are refused while a merge into the same target is in flight (one more admission reason). A flow at source with a verification on its way now waits rather than stopping, which also covers a verification requested after the target moved outside the factory. New flow field `targetWait`, new events, new queue hold kind `merge` (the Queue tab lists holds generically). docs/operations.md describes it.

**Tests:** admission refuses with the merge reason and the queue status shows the hold, both clear when the merge flow finishes; a flow at source waits for the merge (and stepping again records no new event), then for the queued post-merge verification, then prepares source verification by itself once main is green; a `source.verify` result reporting a moved target waits while a verification is running, and still stops without one; a prepared source verification is not dispatched when a merge starts meanwhile.

## Review fixes

The independent review (GPT-6.1 Sol) of `4d00854` found no authority bypass and rejected it on one blocking liveness finding.

**Blocking: source flows could wait forever on a stopped verifier.** `pendingVerification` trusted a `main.verify` job's `running` status without looking at the flow executing it. Stopping that maintenance flow leaves its job `running`, so `sourceWait` kept promising automatic progress: the source flow waited indefinitely with "Waiting: main verification is running …" and nothing told the operator.

- **Judged from the worker's actual state.** A flow counts as progressing only if it is not finished, not stopped, not asked to stop (`stopRequested`), not held by a decision, and its current attempt (if any) is not uncertain. A running `main.verify` job counts as on its way only if its verifier flow is progressing. A queued one counts only if it can start: not behind a stopped maintenance flow that holds the maintenance slot, and not under a maintenance hold (`pause` with `holdMaintenance`). The in-flight merge check uses the same rule: a stopped, stop-requested, decision-held or uncertain merge flow no longer holds admission or source flows.
- **Chosen: stop, not wait-and-notify.** When the verification cannot proceed, the source flow stops at `source` (`resumeStep: source`, event `flow.target-wait-blocked`) with a reason naming the job, the verifier flow and its state, and the recovery: resume the verifier (`resume`) or abandon it (`flow.abandon`) and run `main.verify` again (or doctor), then resume this flow. Why stop: a stopped verifier is an operator-level event, and the existing stop path already gives a deduplicated, delivered notice, keeps the flow's slot and claim, and resumes by repeating the step. It also matches the documented stop-at-source behaviour for an unverified target. Waiting with a separate notice would need a new notice lifecycle (opened, kept current, resolved when the verifier recovers) for little gain. The cost is that recovery takes two resumes: the verifier, then the source flow. The resumed source flow then waits for the verification and continues by itself.
- **Liveness, not a timer.** The check runs every time a waiting source flow is stepped (each engine tick), at dispatch and at settlement, so a wait lasts only while some flow is actually doing the work it waits for. A running verifier or merge is bounded by its own attempt timeout and supervisor; anything that stops it ends the wait with the stop notice above. No time bound was added, so a long verification is not cut short.
- **Stopped maintenance flows hold the maintenance slot: not new.** `canStart` in `workflows/maintenance.mjs` lets one non-integration maintenance flow run at a time and counts every unfinished one, stopped included. That rule is identical on `main` and on this branch's base (`d41696d`); this branch does not change it. A queued verification behind such a flow is now reported as unable to proceed (above) instead of being waited on. Abandoning a maintenance flow already settles its job (`flow.abandon`, plus the operations loop's repair of jobs left `running` after their flow finished).
- **Found while fixing: the dashboard's queue status missed merge holds.** The dashboard snapshot calls `queueStatus` through a projecting store view whose flow records keep only list fields (no `workflow`, `stopRequested`, `decisionHold` or `integration`), so on `4d00854` the Queue tab never showed the `merge` hold. The merge-hold reads now take candidates from the live set by their listed fields and read just those flows whole by primary key (a plain `kind`/`id` read, no SQL JSON function); a view without `changeToken` is read without caching.
- **Cached reads (non-blocking finding).** The live flow and job sets are read once per database state and shared by every source-flow check until something is written (`Store.changeToken`, two constant-time reads). Only merge-step flows and the verifier's own flow and attempt are read individually.

**Tests** (4 new, plus one fixture updated): the reviewer's case with the real operations tick admitting the verifier and the real `stop` command: the source flow stops naming the verifier and recovery, with a notice and the event, while the job still says `running`. Recovery: resume the verifier, resume the source flow, it waits on the running verification, and once main is verified green it prepares source verification by itself. Abandonment: the job settles `abandoned`, nothing is promised any more, a new `main.verify` is admitted (slot free), and the resumed source flow waits on it. Unit cases: a queued verification behind a stopped maintenance flow is blocked; stopped and decision-held merge flows are not in flight. The earlier settlement test now gives its running job a real verifier flow (a `running` job without one is correctly judged blocked). A new assertion checks that the dashboard snapshot's queue status shows the merge hold. Fail-before: with `merge-hold.mjs` and `engine.mjs` from `4d00854`, 5 of the 23 tests fail (the 4 new ones and the admission test with the dashboard assertion) and 18 pass.

Results after the review fixes: `node tests/run.mjs tests/external-pr-adoption.test.mjs` 23 pass, 0 fail; `npm test` 980 tests, 980 pass, 0 fail, 0 cancelled, 0 skipped; `npm run eval` exit 0; `git diff --check` clean.

### Round 2

The re-check of `cee1203` confirmed the stopped-verifier fix (resume, abandon, reverse order, shared verification, long verifications) and found no authority or protection regression. It rejected on one blocking finding.

**Blocking: rolled-back state could stay cached.** The merge-hold cache was keyed by `Store.changeToken()` (`data_version` and `total_changes()`). `total_changes()` also counts writes that are rolled back, and a rollback on the same connection does not change `data_version`. So a token read inside a transaction after its writes equals the token read after that transaction rolls back, although the data is back to what it was. Repro: a completed merge flow is set back to its merge step inside `store.tx`, `mergesInFlight` fills the cache, the transaction throws; afterwards the stored flow is completed but `mergesInFlight` still returned it.

- **Fix, in the token itself.** `Store` counts rollbacks on its connection (`markRolledBack()`, called by `Store.tx` on every rollback and by `executeCommand` after its savepoint rollback), and `changeToken()` includes the count. A token read inside a transaction that rolls back never equals a later one. This was simpler than tracking transaction state in each cache, and it covers every user of the token.
- **Other users of `changeToken()`.**
  - Engine parked questions (R3 wake): the tick and the question step read their token outside any transaction ("read before the transaction"). A rollback after such a read only makes the next token differ, which steps the flow once more (a spurious wake). A missed wake would need a changed state with an unchanged token; a commit always changes `total_changes()` (this connection) or `data_version` (others), so that cannot happen. Not affected before or after the fix.
  - `queueInboxDeliveries` (notifications): it remembers the token of a pass that found nothing to queue and skips later passes with the same token. If that pass ran inside a transaction after the transaction's own writes (for example a delivery written there) and the transaction then rolled back, the next pass would have been skipped although the rolled-back delivery was missing. That only delayed the delivery until the next write, but it was a wrong skip; the rollback count fixes it too.
- **Non-blocking, fixed: other non-progressing slot occupants.** A queued verification was judged blocked only behind a *stopped* maintenance flow. It now uses the same rule as a running verifier: any unfinished non-integration maintenance flow in the slot that is not progressing (stopped or asked to stop, held by a decision, or with an uncertain attempt) blocks it, and the reason says which state. Integration workflows' maintenance flows do not take that slot (as `canStart` in `workflows/maintenance.mjs` already treats them).
- **Stub labelled.** The older settlement test's verifier is a maintenance flow record whose copied graph has no `run` step; it is never executed, only its state is read. The test now says so; the real verifier lifecycle is covered by the operations-tick tests above.

**Tests** (2 new): the reviewer's rollback repro (the flow is seen inside the transaction, the token changes on rollback, `mergesInFlight` and admission no longer report it afterwards); and a queued verification with a progressing occupant (waits), a decision-held occupant and an uncertain-attempt occupant (blocked, naming the state), and an integration flow (not an occupant). Fail-before, with `merge-hold.mjs`, `store.mjs` and `project.mjs` from `cee1203`: 3 of 25 fail (the two new tests, and the earlier occupant test, whose expected wording now names the occupant's state); 22 pass.

Results after round 2: `node tests/run.mjs tests/external-pr-adoption.test.mjs` 25 pass, 0 fail; `npm test` 982 tests, 982 pass, 0 fail, 0 cancelled, 0 skipped; `npm run eval` exit 0; `git diff --check` clean.

## Decisions and follow-ups

Operator answers to the questions this record first raised:

1. **Closing references under squash or a non-default target:** keep one rule for every merge method and target. Adoption follows the merge step's rule unchanged.
2. **A closing keyword in the original PR's own description:** not verified. When a commit-preserving merge makes GitHub mark the original PR merged, whether GitHub then closes issues linked from the original's description is unknown; this change does not check or prevent it.
3. **Re-checking the `original-pr` obligation later:** not done for now. It is evaluated only right after merge, and GitHub can mark the original merged a little later, so the obligation may stay pending. A later automatic re-check (for example at cleanup) is a possible follow-up.
