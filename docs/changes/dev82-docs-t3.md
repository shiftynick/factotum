## Needs runtime code, not documentation

All eight are fixed in runtime code, with the docs above updated to match: see [dev82-trial-code-items.md](dev82-trial-code-items.md).

- **F8:** importing an issue drops the brief's `outcome`. Either import it (as the title or a description the brief shows) or refuse it, so writers are not misled.
- **F10:** the merge commit title should carry the task title and PR number; there is no setting.
- **F11:** the reviewed-plan comment should be rendered as readable text.
- **F20:** doctor's "local root equals remote main" check makes a `git pull` a standing manual step; consider checking only that the local root contains no unpushed work.
- **F21:** a flow question's answer note should be on the answered inbox item (standalone items already have `answerNote`).
- **F24:** a narrower CLI read (`status --inbox/--flow/--task`, or the compact snapshot) so agents do not need `jq`.
- **F33:** `delivery.ack` on an open question should not move a longer reminder earlier; flow questions could carry choice labels; the payload could say a wake is a presentation-end wake.
- **F36:** pass the task's declared paths to checks (an environment variable) or flag out-of-path files to the reviewer, so a scope check does not need a project-wide approximation.

## Review fixes

Independent review of `65b33b7` (GPT-6.1 Sol): approve with fixes. All fixed, plus the operator's ask-prompt decision and a merge of `main`.

- **Setup order (blocking).** The handling guide and the state filter are now installed, committed, merged and pulled (step 8) before `notifications.configPath` is set (step 9), because delivery starts at once and does not wait for them (`operations/notifications.mjs` `deliverDue`). "Before you start" states that doctor needs a clean operator checkout whose HEAD equals the remote target (`workflows/commission.mjs:77`).
- **State filter dropped needed state (blocking).** `factotum-state.example.jq` now keeps `settings.holds` (pause, recovery, retention, spending, provider holds), `queueStatus.holds`, `recoveryHoldReason`, `health` (operations fault, notification health), the spending summary, main health with scheduled-tier evidence, recent fault events, a summary of every open inbox item, and for the flow its effective risk, decision roles, attempt, workspace, visit budgets, per-step evidence (route, attempt, head, review verdict and findings, check results, merge and cleanup) and its last five attempts. It names the reads still needed before a merge decision (the PR diff, and the review attempt's `action-result.json` when the summary is not enough). On the trial's 1.6 MB final status it prints about 6.5 KB. `tests/t3-guide.test.mjs` builds a snapshot with each of these (retention, spending and recovery holds with cause, an ordinary and an integrity operations fault, paused notifications, two open questions, a strict flow with a review finding and a failed gate) and asserts they survive; it fails on the `65b33b7` filter.
- **`accepted: false`.** Step 10 lists network errors, timeouts, an unreachable T3 and a refused request; a URL or secret mismatch is one possible cause.
- **Events and commands in `status`.** `running.md` and the T3 guide say `status` shows the latest 100 events and commands by default (`core/store.mjs` `events`, `commandHistory`), not the full history.
- **Child prompts were not seen.** The guide now says visibility failed in the trial environment: the operator said they never saw the child prompts.
- **Operator decision (2026-11-15): ask prompts off until a route is verified.** Both T3 files say the orchestrator does not present questions through the ask prompt by default; questions stay in the inbox and console. The confirmation procedure (now also checking that a prompt disappears when its question is answered in the console) is the gate for turning it on. The separate top-level asking thread is described as a route being tested, adopted only if the operator sees its prompts and withdrawal works; it is not described as working. The checklist says the same.
- **Merge of `main`.** Conflict only in `docs/integrations/t3.md`: main had updated the old "A setup that works" paragraph (delivery file problems pause delivery; enabling delivery sends only open items; notification level) that this branch replaced with the setup steps. Resolved as a union: the steps keep this branch's structure and carry main's behaviour, including the notification-level guidance. Text on this branch that described the pre-fix behaviour (backlog flood, recovery hold, `restored state requires reconciliation`) was updated in the T3 guide, the handling guide, the checklist and this record.
