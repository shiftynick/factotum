# A root installation's lock authenticates its files

**Finding** (recorded in [upkeep-slice2.md](upkeep-slice2.md), "Pre-existing finding, not fixed here: a root installation's lock does not authenticate its files"). `factotum.lock.json` pins a release by `manifestDigest` and `payloadDigest` and lists each managed file's SHA-256. A prefixed lock carries layout evidence (`layout`: the release's template identities and compatibility), and `readLock` requires its files, owners and layout to rebuild the pinned manifest (`layoutMatches`). A root lock carried none, so nothing tied its `managedFiles` to the digests. Replacing a managed file and writing its new SHA-256 into the lock, digests unchanged, passed `upgrade apply --activate` (the `pull` step), `--merge` (`liveAdoption`), doctor's drift check (`adoptionDrift`) and `adopt status`; recommission, doctor and the restarted units then ran the substituted code. It needs write access to the target outside the factory (a direct push, or a pull request merged by hand); the factory's own flows cannot do it.

## Fix

Option (1) of the write-up, with option (2) as the transition for root locks written before this release. `starter/factory/distribution.mjs`, `operations/upgrade-apply.mjs`, `workflows/commission.mjs`, `cli.mjs`.

- **Every new lock carries layout evidence.** `newLock` writes the same evidence for a root installation as for a prefixed one, under `rootLayout` instead of `layout`, and requires it to rebuild the release manifest (a release in the form `release build` writes; every built release is). The separate key keeps the new root lock readable by earlier releases: their `readLock` refuses a root lock with a `layout` key but ignores other keys, so a release adopted after this one (a downgrade) still reads the lock this one wrote. Checked: the base code (`9c4fe70`) reads a root lock with `rootLayout` as clean.
- **Every reader checks it.** `readLock` (split into `validLock`, the lock on its own) requires a root lock's `rootLayout`, when present, to rebuild the manifest it names, exactly as a prefixed lock's `layout`. A root lock with `layout`, or a prefixed one with `rootLayout`, is invalid. Status, plan, update, doctor's drift check, `--merge` and `--activate` all read the lock through it. The history walk also compares `rootLayout` with the adoption commit's, so evidence cannot be added, changed or removed by hand on a same-release commit.
- **With a verified release directory, the lock is checked against its manifest.** `adoptionStatus({ root, release })` checks that a lock naming that release lists exactly its managed files (path, SHA-256, mode) and its release record. `--merge` passes its release to the worktree check (before anything is stopped) and to `verify`; `--activate` passes the release it already resolves for the configuration check (`--release`, or the release artifact its CLI runs from). This authenticates root locks without evidence, and is a second check for every other lock.
- **`--activate` checks the landed lock before anything is stopped.** It reads `factotum.lock.json` from the fetched target commit with `git show`, as data (nothing there is run), and, when it names the pinned digest, `authenticateLandedLock` requires its layout evidence to rebuild the manifest or, for a root lock without evidence, the verified release to match it. Without either it refuses and says to pass `--release`. The repro is now refused here, before any unit is stopped and before the checkout moves. A lock that is unreadable or names another release is left to the `pull` step, which refuses it in its own words as before.
- **A refused pull returns the checkout.** Before, a `pull` step that refused (a managed file differing from a genuine lock, say) left the checkout fast-forwarded to the unverified target, and the units were restarted on it. The checkout is now returned to the commit it held before; the review fixes below extend this to `--merge` and make it survive an interruption.
- **Status and doctor report authentication.** `adoptionStatus` returns `authenticated` (true for every lock with evidence, or checked against a release) and, for a root lock without evidence, a `warning`. `adoptionCheck(root)` returns doctor's `{ reasons, warnings }`; `adoptionDrift` keeps returning the reasons. Doctor adds the warning to its warnings, not its reasons. `adopt status` prints the result (with `"authenticated": false`) and the warning on standard error; its exit code still follows `clean` only.

The `runnerLock` handle in `mergeUpgrade` and `activateUpgrade` is renamed `unlock`; it shadowed the verified `release` the new checks need.

## The transition for existing root locks

Both current adopters run a root installation whose lock has no evidence. Such a lock is **accepted, unauthenticated**:

- doctor passes (no new reason) and shows the warning: "factotum.lock.json (release …) is a root lock written before dev.87, without layout evidence: … It stays unauthenticated until the next adoption …";
- `adopt status` is clean with `"authenticated": false` and the warning;
- `adopt plan`, `adopt update` and `upgrade apply` read it as before, and the adoption they prepare writes a lock with evidence;
- `--merge` authenticates it against the verified release it always has;
- `--activate` authenticates it against a verified release directory and refuses it without one, before anything is stopped.

So the first release with this fix is adopted the normal way and the warning disappears with that adoption. Refusing old locks instead would stop doctor, and with it admission, on both adopters' services the moment they ran this release's code, and they could not leave that state without the adoption the refusal blocks. Accepting them loses nothing that worked before: what an old lock does not prove, it never proved.

**A lock without evidence after one with it** is refused once the project's state records the evidence (review fix 3, below). Before that record exists, someone who can write the target can still land an adoption commit whose root lock has the earlier shape and a substituted file with its hash: doctor and `adopt status` then only warn, because nothing in such a lock can be checked without the release, and `--merge` and `--activate` refuse it (they are where the operator's pinned digest is applied). A doctor running substituted code cannot be relied on in any case, since the substitution can include `distribution.mjs`.

## Action needed

For root installations (both current adopters). Prefixed installations need only items 5 and 6.

1. **Adopt this release with its own CLI**, as `upgrade apply` is documented: `node <release>/starter/factory/cli.mjs upgrade apply …`. Preparation writes the evidence (`rootLayout`) into the new lock; review it with the rest of the adoption. A lock prepared with an earlier release's `adopt update` lacks it, which works but stays unauthenticated until the next adoption.
2. **Until then, doctor shows one warning** about the unauthenticated lock. It is expected and needs no action; doctor still passes.
3. **`upgrade apply --activate` on a lock without evidence needs the release**: pass `--release <release directory>` or run it with the release's own CLI. Without either it is refused before anything is stopped. `--merge` always has the release and needs nothing.
4. **After this adoption, every later adoption must keep the evidence.** The first time the lock verifies by its evidence (the upgrade's own verify step, or doctor), the project's state records it. From then on a lock without evidence is refused by doctor (admission stays held), `adopt status --state` and both upgrade commands, unless `--release` authenticated it. If that happens: prepare the adoption again with the release's own CLI, or apply it with `--release`. Do not add the evidence by hand; only an adoption writes it, and a hand edit is refused.
5. **Pass `--state` to `adopt status`** (`adopt status --root … --state <state directory>`) where you use it as a check: without it, it cannot see the project's record, so it gives the transition warning for a lock without evidence and says so.
6. **An upgrade now stops units only on a checkout that verifies from its files, and starts them only on one that verifies with an authenticated lock.** `--merge` and `--activate` refuse to start if the project checkout does not verify (run `adopt status --state` and doctor, and fix it first). `--merge` catches up with the remote target only in the review worktree, and stops for a new review if the target changed a `.gitattributes` or `.gitmodules` file, or if the rebased branch no longer carries exactly the reviewed changes or no longer verifies: prepare the upgrade again on a new branch. When `--merge`'s `verify` or `--activate`'s pull refuses the files, the checkout goes back to the commit it held (a `rollback` step) and the units start once it verifies. When the checkout cannot go back or does not verify, the units stay stopped (a `hold` step); when a unit does not start, the record stays (a `units` step). Both end with "To finish, run in order:" and the commands, the last being `node <cli> upgrade apply --recover --actor operator --root <root> --state <state>`. Before running them, copy anything you want to keep out of the checkout to a private backup outside the repository; do not stash it. After an interruption (a signal, a crash), run `upgrade apply --recover`: it runs `config update --current` and doctor and starts the units only if the checkout verifies and both pass. Preparing an upgrade is refused while a recovery is pending, with the `--recover` command to run. The old recovery steps for a failed `verify` (restore the files in the merged checkout, then `adopt cleanup`, `config update --current` and `doctor` by hand) no longer apply; see [updates](../updates.md#install-under-a-folder), "When an upgrade stops partway".
7. **Keep the directory of the release you run now while you upgrade from a root lock without evidence** (both current adopters, for this first upgrade). If that upgrade fails and the checkout is returned to the earlier lock, the units stay stopped, because nothing authenticates that lock; the `hold` step names `upgrade apply --recover --release <the directory of release X> --digest <its digest>`, which starts them once that release authenticates the lock. A successful upgrade writes the evidence and needs nothing.

## Review fixes (GPT-6.1 Sol review of 335f9af)

The review confirmed the digest authentication: every forgery variant tried (evidence, template, compatibility, an extra file, mode, symlink, case-only rename) was refused on all four paths, the digests are recomputed, the genuine, prefixed, earlier-shape and older-reader cases pass, and the preflight runs nothing from the target. It found two P2s in recovery and recommended building the anchor of open question 2; the operator agreed. All three are fixed in `operations/upgrade-apply.mjs`, the new `core/adoption-anchor.mjs`, `distribution.mjs`, `workflows/commission.mjs` and `cli.mjs`.

1. **P2-1: `--merge` restarted the units after `verify` rejected the merged files** (open question 1; reworked by the second re-check, below: the sync no longer moves the project checkout). Repro: prepare a genuine upgrade, push a change to a managed file both releases share without its lock entry, run `--merge`. The sync rebased, `verify` refused the file, the checkout kept it, and the units were started on it. Now the trusted commit is the checkout as it was **before the sync**; if anything fails before `verify` passes, the checkout is returned to it (`git reset --keep`, then confirmed on that commit and clean) and the result records a `rollback` step, and only then are the units started. A failure before any unit is stopped (the sync's rebase, the drain check, an "already merged" refusal) also returns the checkout and says so.
2. **P2-2: the rollback did not survive an interruption.** Repro: SIGTERM right after the fast-forward left the checkout on the unverified commit with the units stopped; a retry saw `HEAD` already at the target (`before === remoteHead`), skipped the rollback and, failing, started the units on the rejected files. Now:
   - Before the first unit is stopped and before `HEAD` first moves, `--merge` and `--activate` write `upgradeRecovery` to the project's state (the last verified commit, the commit being moved to, the units stopped; each unit is recorded before it is stopped). Verification moves the trusted commit forward; the record is cleared when the units are back.
   - The next `--merge` or `--activate` finishes a pending recovery before anything else: the checkout is returned to the recorded commit (or, with none recorded, must verify as it is), the units the interrupted run stopped are started, and the record is cleared (a `recover` step; a later error says the recovery happened). If the checkout cannot be returned it does nothing else and says what to do. Preparing an upgrade is refused while a record is pending.
   - The units stay stopped whenever the checkout neither verified nor could be returned. (The case of a checkout that already held the rejected commit, with no earlier verified commit, was a `hold` here; the second re-check replaced it with a refusal before anything is stopped.)
3. **Decision (b): no authentication downgrade** (open question 2). `core/adoption-anchor.mjs` keeps `adoptionAnchor` in the project's state. Doctor, `--merge` and `--activate` record `evidence` (manifest digest, version, time) the first time the project's lock verifies by its own evidence. After that, a root lock without evidence is refused by doctor (a reason), `adopt status --state`, `--merge` and `--activate`, unless a verified release directory authenticated it; `--merge` and `--activate` then record `releaseVerified` with the SHA-256 of that exact lock, which doctor and `adopt status` accept (still with the "no evidence of its own" warning) while refusing any other lock in that shape. The refusal names the recovery: prepare the adoption with the release's own CLI, or apply it with `--release`. A project that never had evidence, or whose state has no record (a fresh machine), keeps the transition behaviour. `adopt status` gains `--state`; without it, or with a state that cannot be read, it warns and says what it did not check. A state of another project is refused.

This also settles the stranding concern recorded earlier: an adoption prepared with an earlier release's CLI after the anchor is not stuck, because applying it with `--release` authenticates and records it.

## Third re-check fixes (GPT-6.1 Sol re-check of b484ab5): simpler recovery

The re-check confirmed the earlier repros, the refused merge substitution, SIGTERM in both service states, the downgrade guard and that no worktree leaks, and found three P2s. As directed, they are fixed by simplifying: recovery no longer trusts anything it recorded, and one check gates every unit start. `operations/upgrade-apply.mjs`, `cli.mjs`, `core/command-help.mjs`.

1. **P2-1: recovery started units without verifying anything.** The recorded "trusted" commit could be a HEAD that never verified, and recovery checked only that `HEAD` matched it and `git status` was clean: a checkout carrying a substituted file was restored and started, a managed file modified behind `--assume-unchanged` started, and a planted record succeeded. Now `checkCheckout` is the one gate: `adoptionStatus` without the history walk, with the project's anchor (and the release, where one is at hand), which hashes every installed file from its bytes on disk. `--merge` and `--activate` require it before they stop anything; every unit start after an upgrade step (the end of the run, and the console after recommissioning) requires it; recovery requires it. When it fails, the units stay stopped and the message says why. The record keeps only the stopped units and the commit the checkout held, and that commit is used only to write the instructions: recovery never moves the checkout. `upgrade apply --recover` accepts `--release` and `--digest`, so a verified release can authenticate a lock without evidence of its own.
2. **P2-2: the automatic rebase could silently drop reviewed project changes.** Repro: the review branch restricts `project/GOVERNANCE.md`; the target applies the identical patch and then a permissive rule; `--merge` skipped the reviewed commit as already applied and completed with the permissive rule. The simple stop (refuse whenever the target moved) was not taken: it breaks the documented normal path, where `--when-drained` waits for running flows whose pull requests then merge into the target, so the target has nearly always moved by the time `--merge` runs (the test "apply catches up with work merged on the remote while it waited" is that path). Instead the rebase stays, and `--merge` stops for review whenever it changed the reviewed diff in any way: the branch's `git diff --raw --no-abbrev --no-renames` against its new base must equal the reviewed branch's against the commit it was prepared on (every path, mode and blob, managed or not). A skipped or altered commit, or a target commit touching a path the review changed, fails it. Nothing is stopped or moved, and the review branch is put back on the reviewed commit; prepare the upgrade again.
3. **P2-3: the instructions recommended `git stash push --include-untracked`,** which puts untracked files, secrets included, into Git objects. The instructions no longer stash. They ask the operator to look at `git status` and copy anything worth keeping to a private backup outside the repository, then give `git checkout -- <paths>` for the files that differ (named; this also restores a file behind `--assume-unchanged`), `git reset --keep <commit>`, and `upgrade apply --recover`. They name the refusal ("Entry '<path>' not uptodate" or "would be overwritten by merge") and what to do: back the file up, restore it with `git checkout -- <path>` or move an untracked one out, and run the reset again.

**Removed recovery code:** the recovery tracker (`recoveryTracker` with `unitsStopped`, `beforeMove`, `verified`, `settle`, `restarted`, `done`); `returnCheckout` and its `git status` cleanliness test, the stand-in for verification that P2-1 defeated; the `trusted` and `target` fields of the record and every update of them during a run; the automatic reset during recovery; the stash command in the instructions; the special pre-stop check and message for an activation whose checkout already holds the target (the general pre-stop gate covers it). What remains: `stopUnits` (records each unit before stopping it), `checkCheckout`, `finishUnits` (return the checkout if the upgrade's own check failed, then the gate, then start and confirm), `recoverInterrupted` (the gate, then start and confirm) and the instruction text.

**Tests.** `tests/upgrade-recovery.test.mjs`, 8 tests, all failing at `b484ab5` on their assertions (run there from a copy of its `starter/` with this file and the fixtures added):

- a substituted file pushed to the target stops `--merge` before any unit stops or the checkout moves, also under SIGTERM, and the review branch is back on the reviewed commit;
- P2-2: the governance repro stops `--merge` for a new review, with the checkout and the review branch unchanged;

## Fourth re-check fixes (GPT-6.1 Sol re-check of 1357eb5)

The re-check found every earlier regression test passing and ignored extras, executable bits and symlinks rejected, and found four P2s. The operator set the scope: fix the first three, defer the fourth and the core commissioning gap as runtime follow-ups. Changes are kept minimal (`operations/upgrade-apply.mjs`, `cli.mjs`).

1. **Recovery restarted an unauthenticated legacy forgery.** Repro: a root install without evidence and without an anchor, `factory/core/configuration.mjs` substituted with its hash in the lock, a planted record; `recoverUpgrade` without a release saw `clean: true, authenticated: false` and started the console. Now a unit start, in recovery and at the end of a run (also the console after recommissioning), needs an authenticated lock: its own evidence, the exact lock a verified release authenticated for this project (the anchor's `releaseVerified`), or the release given with `--release` and `--digest`. Otherwise the units stay stopped and the message names `upgrade apply --recover --release <the directory of release X> --digest <its digest>`. The check before anything is stopped keeps the transition rule, so the first upgrade from a lock without evidence can still run; if it fails and the checkout is returned to that lock, the units stay stopped until `--recover --release` (Action needed 7).
2. **Recovery started services before recommission and doctor.** Now recovery ends the way a run ends: after the checkout check it runs `config update --current` and doctor with the checkout's own CLI, and starts the recorded units only if both succeeded. Otherwise the units stay stopped, the record stays, and the error names the failing step and the `--recover` command to run once it is fixed. The `recover` step reports `recommissioned: true`.
3. **A target `.gitattributes` change could alter checked-out bytes without changing the raw diff.** Repro: an existing reversible `gov` filter, and the target adds `project/GOVERNANCE.md filter=gov`. Now, if the target commits the sync would bring in change any `.gitattributes` or `.gitmodules` file, at any depth (`git diff --name-only` between the checkout and the fetched target), `--merge` stops before the rebase, before anything is stopped or moved, and says to prepare the upgrade again so it is reviewed on top of the target.

**Deferred** (recorded in [runtime follow-ups](../runtime-followups.md) with the reviewer's repros): a concurrent writer can replace a file in the checkout between the check and the unit start (time of check to time of use); and the core's `authorized()` does not require commissioning, so a carried flow advanced to a prepared `forge.closeTask` effect while `commissioning` was null and admission paused.

**Threat model.** The checks in this change are against what is committed to the target and what the checkout holds when they run. A process that writes to the operator's checkout concurrently with `upgrade apply` (between a check and the unit start) is outside the guarantee; so is anyone who can write the project's state directory or the operator's Git configuration.

**Tests.** Three more in `tests/upgrade-recovery.test.mjs` (11 in all), each failing at `1357eb5` on its assertions:

- item 2: an interrupted merge with the old `commissioning.ready` left in place: recovery runs `config update`, then doctor, then starts the console; with doctor failing, the console stays stopped and the record stays;
