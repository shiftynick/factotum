# Triage proxy thread guidance

Documentation, starter templates and tests only; no runtime code changed. Not a release. Source: the operator's request of 2026-11-15 for "a proxy thread for triaging these things before sending to the main thread", for factory webhook callbacks and for the orchestrators' timer checks, with aggregate figures from operator measurements over about 30 days of recorded orchestrator sessions (4,625 turns). The guide cites only those aggregate figures.

## Claims and the code they were checked against

- **Payload fields** (`projectId`, `deliveryId`, `kind`, `inboxId`, `version`, `event`, `status`, `resolution`, `actor`, `presentationEnded`, `presentationId`, `taskId`, `flowId`, `eventSequence`, `eventAt`, `taskRevision`, `approvalVersion`, `sessionDeliveries`, `sessionDeliveryLimit`, `observedAt`): `starter/factory/operations/notifications.mjs` `deliverDue`, and the new guide test.
- **Re-sends reuse the delivery ID; a reminder, a retry and a presentation-end wake are not marked in the payload**: the delivery ID is `digest({inboxId, version, channel})` (`queueDeliveryInTransaction`); `claimSessionSendInTransaction` gives a re-send after an accepted send a new ordinal, while a retry of a send that was not accepted keeps its ordinal; `countSessionDeliveryInTransaction` counts an acceptance for the session the send was dispatched to, and a late one after a rebinding goes to that session's reset record. Resolution and state deliveries are re-sent at the reminder interval until acknowledged (`deliverDue`, `interval` for `kind === 'state' || event === 'inbox.resolved'`).
- **Superseded and orchestrator resolutions are already suppressed at `essential` and `actionable`**: `suppressInbox`. The rules still absorb them because they arrive at `all`.
- **Only notices become `acknowledged`; `inbox.ack` by the orchestrator is allowed except on `operatorAckOnly` items**: `core/project.mjs` `inbox.read`/`inbox.ack` case.
- **Operator notices**: provider usage holds (`operations/provider-limits.mjs`), idle queue (`operations/queue-diagnostics.mjs`), session resets (`operations/orchestrator-session.mjs` `recordReset`), workspace cleanup (`operations/workspace-cleanup.mjs`), decision holds and relayed answers (`core/decisions.mjs`), standalone notices (`core/communication.mjs`, `role: 'operator'`). Flow notices: `core/project.mjs` `flowNotice` (ID `flow-notice:<flowId>:<outcome>:<digest>`, `outcome`, `terminalReason`, `cleanupOutstanding`, the default completion sentence, "Corrected on the way" and cleanup notes appended to `context`).
- **`actionable`'s check is stronger than the narrow read**: `flowNeedsAttention` and `routineFlowSuccess` read obligations, review history, worker reports, `taskSnapshot.postMerge`, attempts and unresolved decisions; `stateView` shows evidence (route, findings, checks, merged, released) and the last five attempts only. Hence the clean-completion rule is off by default, and there is no target-sync rule (sync evidence is not in the read).
- **Narrow read and compact read**: `operations/state-view.mjs` `stateView` (`project.session` from `orchestratorSessionView`, `item`, `flow.evidence`, `attempts`, `task`, `queue`) and `service/dashboard.mjs` `dashboardSnapshot` (`paused`, `recoveryHold`, `health`, `mainHealth`, `commissioningRequired`, `flows` with `state`, `step`, `attemptId`, `orchestratorSession`).

## Session binding: recommendation

The orchestrator thread binds `orchestrator.session` with its own thread ID, as setup step 2 already says; the proxy never binds. The count measures deliveries accepted by the endpoint whichever ID is bound, so binding the proxy would not make it more accurate, and it would point the handoff question at the one thread whose context does not grow. A proxy that bound itself would supersede the orchestrator's open handoff question and reset its count, and alternating bindings would trigger the reset notice. With the orchestrator bound, the narrow read gives the proxy its forward target (`project.session.sessionId`), so a handoff needs no change to the proxy, and the webhook stays on the proxy. The cost is that absorbed deliveries count toward the orchestrator's handoff limit, so the question comes early; the guide says the operator may raise the limit by the measured forward share.

## Runtime follow-ups

Not fixed here (documentation and templates only):

1. **No marker for a re-send.** A reminder, a retry after a failed send and a presentation-end wake carry the first delivery's `deliveryId`; nothing but `presentationEnded` tells them apart. The proxy needs its own memory of delivery IDs to tell a reminder from a first delivery. A payload field such as `send: "first" | "reminder" | "retry"` (or the delivery's attempt number) would let a stateless rule do it.
2. **No "safe to auto-acknowledge" marker.** Factotum's own routine classification (`routineFlowSuccess`, `flowNeedsAttention`) is computed only at `actionable` and only to suppress. A payload or narrow-read field (for example `routine: true` with the reason) at every level would let a proxy absorb clean completions and syncs with the core's own check instead of a weaker copy.
3. **The narrow read lacks what a routine check needs**: obligations and their status, `taskSnapshot.postMerge`, worker reports and unresolved decisions for the flow, and a maintenance flow's operation and sync result (`contained`, `conflict`). Without them a proxy cannot recognise a clean target sync at all.
4. **Delivery status is not in the narrow read.** The proxy cannot see whether a delivery is `accepted`, `acknowledged` or how many times it was sent; `status --inbox` could include the item's current delivery row (status, attempts, `acknowledgedAt`).
5. **The handoff count cannot tell forwarded from absorbed deliveries.** A consumer-side count (for example `delivery.ack` with `{"forwarded": false}`, or a separate "forwarded to session" acknowledgement) would let the handoff question count only the wakes the orchestrator actually received, instead of the operator raising the limit by hand.
6. **The handoff question's text says to "move the notification binding"**, which with a proxy is wrong (the webhook stays on the proxy). The guide and handling-guide template say so; the core text in `raiseHandoff` could say "move the notification binding, unless a proxy forwards to the bound session".
7. **The narrow read lacks a merge question's pull request and forge checks.** `stateView` returns the item and the flow evidence, but not `mergeQuestionContext` (`operations/merge-context.mjs`), which the compact view already attaches as `mergeContext`. A proxy forward therefore cannot carry the PR link or its check state; it says so. `status --inbox` could include `mergeContext` for an open merge question.
8. **Factotum's idle-capacity notice misses a slot held by a stopped flow.** `observeQueue` (`operations/queue-diagnostics.mjs`) raises "Queued work is not starting although slots are free" only with a free slot and `policy.autoQueue` on; a stopped flow keeps its slot (`activeChange` counts it), so approved queued work behind it is never reported. The starter timer checks this itself; core could report it too, naming the flow that holds the slot.
9. **A main hold's "verification in progress" is known only from its text.** The timer recognises it by core's wording in `mainHealthReason` ("verification in progress (job …)"). A structured field on the `main` queue hold (for example `verifying: {jobId}`) would make that robust to wording changes.

## Review fixes

The independent review of `b98d159` rejected it with five blocking findings and one minor one. The principle behind all of them, now stated in the guide and the proxy guide: the proxy is never the reason an item a person needs goes quiet; when in doubt it forwards and proposes no action.

| Finding | Fix |
| --- | --- |
| 1. Forwarding treated as handling: a confirmed forward made every later reminder `absorb` with a proposed `delivery.ack`, which left an open question quiet for at least four hours at a time | The `reminder` and `duplicate` absorb rules are gone. Delivery-ID memory now only recognises re-sends. A re-send for an item the narrow read shows open is forwarded again (`reminder`, with when it was first forwarded) and proposes nothing. A re-send of a forwarded resolution (item closed) is absorbed with **no** action and forwarded again every fourth re-send, so the orchestrator's own acknowledgement is what ends it. A re-sent state delivery is forwarded again. An attention delivery for an item the read shows closed or newer is `stale-version`, whatever the memory says. Without a readable state, an attention delivery is forwarded. Tests: three reminders of a confirmed forward are all forwarded with no actions and the delivery stays unacknowledged; resolution re-sends absorb with no actions and re-forward on the fourth. |
| 2. Unsent timer findings and digests were consumed | Each timer finding and digest is kept in `pending` in the state file with what it commits (the timer baseline, `lastDigestAt`). Only `--sent <sendId>` commits it; an unconfirmed one is produced again by the next run, which replaces it, and a superseded send ID is refused. Other forwards without a delivery get a `notice:` send ID so they are counted. Tests: a recovery hold found and not confirmed is reported again; a superseded finding cannot be confirmed; a digest is produced again until confirmed; a stall is reported again until confirmed. |
| 3. Timers missed actionable conditions | The timer compares a set of conditions from the compact view: pause, recovery hold with cause, operations fault by message and start time, notification delivery not `ok` with its problem, commissioning required, main health not `green`/`unknown`, spending hold, each provider hold, and every `queueStatus.holds` kind except a merge in flight and a wait for a fresh main check (unknown kinds included). Raised and cleared are both reported, and the first run reports what is already wrong. Tests use real `dashboardSnapshot` output: a recovery hold present on the first run, then retention, money, notification paused, a fault and red main health, then a different fault replacing the first. |
| 4. Malformed and unknown input could be absorbed or crash | `validatePayload` checks the whole schema per kind and event before any rule: required IDs, whole-number `version`/`eventSequence`, known kind, event, status and resolution, a resolution matching its status, no foreign or unknown fields (relaxed in round 2: unknown fields are now ignored). Any failure is `forward` with no actions; `decide` and `timerCheck` catch everything and forward. Unknown kinds, events and item kinds are forwarded; only known ruleless state events are `unsure`. Tests cover each repro from the review (superseded without inbox ID or version, unknown resolution by the orchestrator, object-valued version, `timerCheck({})`, `null` and `{flows:{}}`) and more. |
| 5. Shared state not concurrency-safe or corruption-tolerant | Every recorded run holds an exclusive lock file for its whole read-decide-write (stale-lock takeover when the holder has exited or the lock is over two minutes old, bounded 30-second wait), writes `state.json` through a unique temporary file and an atomic rename, and appends to the log inside the lock. A corrupt state file is renamed aside, replaced, and the run forwards a note saying so; a lock timeout or any other failure prints a forward with no actions. The guide and proxy guide say the runs share state and are serialised. Tests: 60 concurrent runs leave 60 log rows, 60 remembered deliveries and no stray files; a stale lock is taken over; a corrupt file is kept aside and the run forwards; garbage on stdin forwards. |
| 6. Session-count wording | The guide now says a retry of an unaccepted send keeps its `sessionDeliveries` number and a re-send after an accepted one gets a new number, and that an acceptance counts for the session it was dispatched to, a late one going to that session's reset record. |

**An adopter's existing watcher, for comparison.** One adopting project already runs a similar watcher thread on a small model. Its runs on 2026-11-15 show two of the same lessons: it acknowledged deliveries it had forwarded (finding 1), and it absorbed a target-sync completion on `route: pass` alone, a weaker check than `actionable`'s. One of its replies reported a forward failing with `thread_not_found` against a hard-coded target; the project found no such failure in its records, so that is not confirmed. (Corrected in round 2: the first version of this note stated it as fact.)

## Review fixes, round 2

The re-check of `dbadb90` confirmed every round-1 repro passes, the lock timeout forwards with no actions, and authority is unchanged. It rejected three new findings.

| Finding | Fix |
| --- | --- |
| 1. Stale-lock takeover let two runs own the lock: (a) age alone overrode a live owner; (b) a waiter that inspected an abandoned lock could, after another waiter had replaced it, delete the new owner's lock; and release unlinked unconditionally | The lock file now records host, PID and a unique token and is created whole and exclusively (temporary file, then `link`). Age never counts. A waiter removes a lock only if its owner ran on this host and that PID no longer exists, and only while holding a second lock (`<log>.lock.takeover`) that serialises takeovers and is never taken over itself; under it the waiter reads the lock again and removes it only if it still has the token first inspected and its owner is still gone. Release removes the lock only if it holds the caller's token. The argument is written above `acquireLock`. A lock from another host, an unreadable lock, or a takeover lock left by a process that died inside its read-and-unlink window are never taken over: every run then forwards after 30 s with no actions, and the guide says how the operator clears it. Tests (hooks inject the interleavings): a live owner with a days-old lock is never entered; another host's lock and an unreadable lock are never taken over; a waiter that inspected an abandoned lock leaves the lock of the waiter that took it over meanwhile; a second taker cannot take over while the first holds the takeover lock; release leaves another token's lock alone. |
| 2. Excluding every `main` queue hold hid real failures | `main` holds are reported (key `queue-hold:main:<target>`), except one whose text says a main verification is in progress, which is tracked as a wait and reported only if it lasts past the stall limit. Merge holds stay excluded: `mergesInFlight` lists them only while the merge is making progress. Tests with real `dashboardSnapshot` output: the secondary target `next` red, and main green but last verified in 2020 with automatic queueing off, both forwarded; a running `main.verify` job quiet, then reported after the stall limit. |
| 3. An unsent timer finding disappeared when its condition cleared before delivery | Each pending timer forward keeps its findings. A later run carries every unconfirmed finding it does not report afresh, marked "raised at …, cleared again before delivery" (or "cleared …, raised again"), and the new forward replaces the old pending one with all of them. Test: a recovery hold raised, not sent, cleared; the next two runs still forward it; confirmed once, then quiet with nothing pending. |

**Decisions applied.** (a) Closed resolutions re-forward every fourth re-send, now configurable (`--reforward-every`, `reforwardEvery`); open items and state deliveries forward on every re-send. (b) Unknown fields are tolerated: the webhook has no schema version and payloads grow additively. Every known field is still checked strictly wherever it appears (a malformed `taskId` on an inbox payload is refused), and unknown kinds, events and resolutions are still forwarded. An older payload without `kind` is read as an inbox payload, as the guide already said. Tests updated.

**Lessons from the adopter's watcher.** Over about a day it made 63 runs: about 22 forwards and 26 absorbs, and about 15 of the forwards needed real action. Its noise, roughly a quarter of the forwards, came from races with work in flight or stale state: an approval revoked by the orchestrator's own edit and then given again, a target-sync completion read while the flow was still cleaning up, a main refresh blocked because the target moved during verification, and a verification that gave up waiting for a machine-wide lock or ended uncertain during a release. Folded in:

- **Wait and re-check.** The script returns `decision: "recheck"` with `delaySeconds` (60) for a flow notice whose flow still reads as active or has an attempt in flight, and for a revoked approval. The proxy waits, reads state again and runs the script once more; the second run decides, and still forwards when unsure. A revocation restored by then is absorbed (`approval-restored`). The blocked-refresh and uncertain-verification races have no rule yet; their notices are forwarded. Tests: a flow notice re-checked then forwarded, or decided normally once the flow finished; a revocation forwarded after the re-check, and absorbed when re-approved.
- **Forward target with no session declared.** `forwardTo` is the bound session, else the thread configured with `--forward-to`, else the last session seen, and `forwardSource` says which. If there is none, or a send to a configured or last-seen thread fails, the proxy stops, says so and acknowledges nothing. Test: no session, then configured, then the bound session winning.
- **Merge forwards are actionable.** For an open flow question whose answers include `merge`, the forward carries the inbox ID, version and subject digest, the risk, the review verdict and findings count, the gate checks passed and not passed, and whether review and gate saw the same head. The PR link and forge check state are not in the narrow read; the forward says so (follow-up 7). Test with a fictional merge question.
- **Slow timer for signals that never fire.** The timer reports approved queued tasks with no running or ready flow for 10 minutes (`--idle-minutes`), once per episode, naming the flows that hold slots. Factotum's idle-capacity notice does not cover a slot held by a stopped flow, or a project without automatic queueing (follow-up 8). Test with a stopped flow holding the slot.
- **Prefer narrow reads.** The guide now has a short "Read narrowly" section: most of that watcher's measured cost came from writing the full `status` on every run.

## Round-2 re-check and root fixes

Re-check (GPT-6.1 Sol) of `c31b58f`: reject on two findings. The three earlier findings were confirmed fixed (lock ownership including an unrelated live PID, partial lock contents and a crashed takeover lock with the real 30-second timeout; main holds including secondary-target stalls and failures; pending cleared findings), as were paused admission and the configurable re-forward cadence. Both findings were fixed by root:

- **Shared scratch files could replace an unhandled wake.** The proxy guide wrote every wake's payload and state read to `DIR/payload.json` and `DIR/read.json` before the script took its lock, so a concurrent wake could overwrite them and the first wake's open question would be neither forwarded nor recorded. Each wake now makes its own directory (`mktemp -d DIR/wake.XXXXXX`), keeps it through its recheck and removes it when finished.
- **An unknown resolution on a state event could be acknowledged.** State-event validation checked the resolution's type, not its value. Factotum's state payloads carry no inbox fields, so a state payload with `resolution`, `actor`, `status`, `inboxId` or presentation fields is now invalid and forwarded with no actions. Two cases were added to the malformed-payload test; it fails with the script change removed and passes with it.
