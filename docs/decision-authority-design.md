# Durable decisions and scoped operator authority

Status: **design for independent review; not implemented or qualified**. Plans **7/8**, with interfaces to **5** (request provenance), **6** (decision reports) and **2** (automatic merging). Audited baseline: `5f72162a04f211e81b5eb6345064158d5c4d4abf`, runtime `0.2.0-dev.20261022.78`. This document changes no runtime, adopter settings, release record or programme progress.

The [strategy](one-factory-strategy.md), [progress record](one-factory-progress.md) and [architectural contract](design.md) govern this proposal. D3 and D4 are settled:

- Delegated brief approval and disposition of operator-owned decisions require stored, operator-issued grants covering the exact scope. Direct operator approval remains valid. Ordinary operational delegation remains separate.
- Collect other new user-visible product choices for substantive operator review before release. Explicitly operator-owned or conflicting decisions require earlier resolution and cannot merge unresolved. Delivery, acknowledgment and silence are not review.

The proposed minimum is a task-linked decision ledger, an exact-scope grant ledger, and one shared authorization evaluator called at every protected boundary. Inbox cards present those records; they do not own their lifetime. Decision reports and release review add versioned evidence to these primitives, rather than a second approval system.

## 2. Invariants

1. **Presentation is not obligation.** No expiry, withdrawal, inbox acknowledgment, delivery acknowledgment, stop, failure, abandonment, replan, task edit, new flow, candidate substitution or restart resolves a decision.
2. **Stable identity, exact authority.** A decision belongs to a project and stable task identity, with immutable origin revision and versioned applicability. An unresolved obligation follows successor revisions by default; an answer/grant never silently follows them.
3. **No authority from prose.** Original requests, notes, `onBehalfOf`, worker reports, report receipts and workflow role labels cannot mint operator grants. A batch brief approval does not authorize any product answer.
4. **Resolution is substantive.** Selecting a permitted exact answer, rejecting the proposed change, canceling the affected work, or superseding it with a recorded replacement can dispose of a decision. “Discuss,” “seen,” “retry” and “defer” leave it unresolved. A cancellation cannot simultaneously authorize delivery of the canceled scope.
5. **Current authority at the boundary.** A successful check at preparation or answer time does not authorize later dispatch. New holds, revoked/expired grants, changed reports and revised scope are read under the same serialization as dispatch state change.
6. **Operation semantics beat graph names.** Custom names, task/document graphs, already-satisfied paths, direct completed terminals and integration jobs share the relevant checks. Graph flags may strengthen but never remove them.
7. **Facts survive loss of authority.** A dispatched merge may complete after revocation. Record and reconcile it; do not falsify it as prevented, retry it blindly, or let it erase the remaining decision/release obligations.
8. **Report review is scoped.** Release clearance binds exact report versions and included task/feature revisions. A later included choice invalidates affected clearance; acknowledgment or an empty legacy report cannot substitute for review.
9. **No implicit capacity change.** Decision holds add reasons, not permits. Existing stopped/waiting flow ownership, resource leases and spending reservations persist under current rules.
10. **Cooperative authority only.** Actor checks govern factory commands for a trusted OS account. They are not cryptographic operator authentication, malicious-agent isolation or a fence around arbitrary shell commands.

## 3. Minimal canonical records

Use the existing `records(kind,id,data)` store and transactional events. Introduce one small `core/decision-authority.mjs` module for validation, lookup, dispositions and the pure authorization evaluator; callers supply the transaction. Avoid a general policy language. Record schemas have an explicit `schemaVersion`; mutable projections also have an integer `version` for compare-and-swap. All identities include project identity where exported.

| Record | Required content and purpose |
| --- | --- |
| `taskRevision` | Immutable `{taskId, revision, brief, requestRefs, createdAt, previousRevision}`. First migration captures only facts available, with `historyIncomplete` where necessary. Never invent earlier content. |
| `decisionObligation` | Stable ID, project/task ID, origin revision, version, owner (`operator`), source reference, bounded question/rationale, scope descriptor and digest, exact options and option-set digest, required boundaries, applicability entries, current disposition reference. Flow/attempt/candidate references are provenance, never the sole owner. |
| `decisionDisposition` | Immutable ID, obligation ID/version, exact applicability revision(s), scope/options digest, selected answer or cancel/supersede payload, rationale/evidence, authority-use reference, command ID, timestamp. Supersession names replacement obligations and explains removed scope. |
| `operatorGrant` | Immutable authority payload plus versioned revoked/usage projection: issuer attribution and issuing command, grantee role, enumerated scope entries, operations/dispositions, validity interval, consumption limits. No wildcard future revisions or prose scope evaluation. |
| `authorityUse` | Immutable use ID, grant ID/version or direct-operator command, semantic operation, exact subject digest, permitted disposition actually used, command ID, downstream authorization references and consumption key. Resolving a decision does not itself grant merge or release permission. |
| `decisionReport` (#6) | Immutable versioned report body/digest, task revision, producer attempt/model, candidate/plan identity, declared choices and evidence, completeness/schema marker, links to obligations and preceding report. Supersession never deletes history. |
| `releaseReview` (#6) | Exact release-scope manifest and digest, included task/feature revisions and candidate/artifact identity, report ID/version/digest set, explicit reviewed dispositions, current authority-use reference and revocation state. It is neither deployment permission nor a read receipt. |

A decision's scope uses bounded structured identifiers (task, requirement/choice ID, optional feature ID and paths as descriptive context). Initial scopes can be opaque IDs with canonical payload digests; no natural-language containment inference. Grant matching uses equality of enumerated revision/scope/option identities. A decision that spans tasks has explicit applicability entries for each task/revision; begin with one-task decisions and explicit linked obligations if that keeps the first implementation smaller.

An obligation has `requiredAt` from a closed set: `build`, `merge`, `complete`, `release`. Every unresolved operator-owned/conflicting product decision includes `merge` and `complete`; include `build` when implementation depends on the answer. New choices requiring only collected review belong in reports and release clearance, not automatically in early blocking decisions. A producer may add holds, never remove them or downgrade their owner/required boundary. Unclear classification is held for triage, not automatically labeled reviewed.

Applicability is monotonic until authorized disposition: task edit from R1 to R2 appends an unresolved R2 binding while retaining R1. It does not rewrite the origin or transfer a grant for R1. Existing resolved decisions are retained as context but require explicit applicability confirmation on a changed revision before serving as clearance; the confirmation itself needs direct operator authority or a grant enumerating that R2 scope. Candidate replacement at the same revision keeps the hold; a candidate-specific disposition loses coverage when its bound candidate changes. Each applicability entry has an explicit state (`pending`, `requires-confirmation`, or covered by a current disposition); both pending states block the required boundaries even if the obligation has a historical resolved disposition. Reintroduced canceled scope needs a new unresolved binding, not reuse of the cancellation as clearance.

Do not identify a new task with an old task solely by matching text. Source import uses the stable source task identity. An explicit replacement-task command must transfer obligation references atomically. Copying scope to an unrelated task ID cannot be detected reliably from arbitrary prose; source provenance, report review and the cooperative trust boundary remain relevant.

### Lifecycle and substantive dispositions

`unresolved → resolved` requires a permitted exact answer and rationale. `unresolved → canceled` requires recorded removal/cancellation of affected work and prevents that scope from completing as delivered. `unresolved → superseded` must atomically create/link replacement obligation(s), or record an authorized scope removal tied to a revised brief; replacement holds remain active. Reject cyclic supersession and dangling successors. A new obligation can reopen a previously settled choice, retaining the old disposition and requiring new authority.

`resolved → unresolved` happens only by explicit operator revocation of the active disposition (see §4, direct authority revocation and ratification); the revoked disposition is retained as inactive history. An inactive disposition (revoked, or whose grant expired or was revoked) is never reactivated in place: it is replaced by a new disposition version created by direct ratification or a fresh grant-backed answer.

Do not provide a generic “clear hold” command. Withdrawing a question can end reminders for that presentation, but the unresolved decision remains in Tasks, Queue and Decisions and may receive a newly versioned presentation. Do not immediately recreate a withdrawn card in a notification loop. Pending presentation is separate from pending obligation, so reminder policy and quiet notifications can be changed without changing authority.

Creation, carry-forward, disposition and revocation each update a per-task authority revision. A release scope similarly has an authority/report-set revision. Revisions are useful cache invalidators; actual record validation remains authoritative. Missing/corrupt references fail closed with a repair reason.

## 4. Stored grants and command authority

Proposed commands: `grant.issue`, `grant.revoke`, `decision.open`, `decision.present`, `decision.dispose`, `release.review`. Names are provisional; semantics and shared validation are mandatory. `answer` is an adapter onto `decision.dispose` for bound questions, in one transaction. Operator-owned decision creation may be requested by the orchestrator or derived from validated worker output; issuance of operator authority may not.

A grant contains a bounded list of entries, for example:

```json
{
  "schemaVersion": 1,
  "id": "grant-example",
  "issuer": "operator",
  "grantee": "orchestrator",
  "notBefore": "2026-11-13T15:00:00Z",
  "expiresAt": "2026-11-14T15:00:00Z",
  "entries": [
    {
      "entryId": "approve-example",
      "taskId": "task-example",
      "taskRevision": "<exact revision digest>",
      "workflowDigest": "<exact selected workflow digest>",
      "operation": "task.approve",
      "disposition": "approve",
      "maxUses": 1
    }
  ]
}
```

A decision-disposition entry additionally pins obligation ID/version, scope digest, option-set digest, and exact allowed answer IDs with their structured payload digests. Cancel/supersede are separate permitted dispositions with exact cancellation scope/replacement payload. Free text may explain an authorized answer; it cannot change its product semantics. A plan-consent grant pins plan, task, context, workflow and base identities. Release-review delegation, if supported, requires the exact manifest and per-choice dispositions selected by the operator; initial implementation can restrict `release.review` to direct operator commands.

Batch approval is a list of exact task revision/workflow entries, each consumed independently. It is never `all current tasks`, `future tasks`, `answer any question`, or a prefix match on product text. Grants contain no executable code. Set conservative bounds (initially at most 100 entries and 32 KiB serialized; individual statements use existing bounded text rules) and validate aggregate command size against the service's 64 KiB limit. Changing a grant's scope requires a new grant, not editing history.

`grant.issue`/`grant.revoke` require `actor === 'operator'` and reject delegated issuance, including `onBehalfOf`. Put them outside `DELEGABLE`, and explicitly reject adding them to `policy.delegatedOperations`. A role named operator by an agent with the same account remains a cooperative attribution claim; stronger authentication requires separate credentials/identities and isolation, outside this proposal.

Do not let delegated `config.update` or `settings.update` disable the new checks, widen grant-management access, reclassify protected operations as operational, or alter authority-bearing policy without a direct operator command. Compare effective normalized policy, including defaults, `replaceLive`, catalog/integration authority declarations, recurrence approval templates and delegation settings. Existing live-setting protection alone is insufficient for full configuration replacement. Ordinary commissioned operational edits can remain delegated; grant records never live in replaceable config.

Keep existing strict-review, spending-cap and integration constraints as additional requirements. A stored grant cannot override a human-only restriction or weaker forge qualification. Existing merge-role or auto-merge policy continues to authorize its mechanical merge decision where allowed; it cannot answer an operator-owned product question. For operator-role answers, use explicit question purpose: ordinary operational retry/repair may retain existing delegation, whereas product/brief/plan/release consent uses exact grants. Legacy ambiguous operator-role answers require direct operator action or explicit classification; do not infer purpose from answer text.

### Consumption, revocation and replay

Add an explicit envelope authority reference, e.g. `authority: {grantId, entryId, expectedVersion}`. Preserve `onBehalfOf` as optional attribution only. Include both in `executeCommand`'s digest, receipt and console journal; reject altered authority under the same command ID. Return the canonical earlier receipt for identical replay, even after revocation, without reapplying effects or claiming current validity. A rejected command also replays its rejection; a corrected command uses a new ID.

Consume an entry only when the protected operation commits successfully, inside the application savepoint. Wrong project/revision/scope/answer, expired or revoked grants, stale UI preconditions and application failure consume nothing. New command IDs cannot reuse a one-use entry. Concurrent uses serialize through SQLite. Compound commands such as `task.restart` carry a shared transaction authority context: operational restart permission cannot approve a new revision, and nested approval consumes its one approval entry exactly once. Reject the whole restart if any required semantic authority is absent.

Consumption prevents creating another approval/disposition; it does not make the resulting proof unusable for the authorized flow. Subsequent dispatch validates the recorded `authorityUse`, its exact derived authorization, and the grant's current validity/revocation. Expiry or revocation prevents future reliance on that proof, including prepared intents. Keep the historical answer visible but mark clearance inactive; direct operator ratification or a new grant-backed disposition is required for future effects. Revocation does not undo already performed effects. This conservative lifetime rule must be explained in grant UI before issue.

A direct operator approval/disposition creates `authorityUse` without a delegated grant. It remains valid for its bound revision/scope until explicit revocation or input change. Grant revocation invalidates derived approvals/clearances and requests stops/cancellation for affected work, while leaving receipt collection/reconciliation available. Consumption and revocation state survive restart, backup and restore; restored state stays under existing recovery hold until outstanding effects are reconciled.

## 5. Enforcement across the lifecycle

Implement `evaluateAuthority(store, {task, flow, operation, candidate, preparedIntent, releaseScope, now})` returning structured reasons and an evidence binding, with a throwing wrapper at mutation boundaries. Avoid adding all holds to `authorized()` unconditionally: an unresolved merge question must not prevent answering it, read-only inspection, receipt settlement, stops or accounting.

| Boundary | Exact checks |
| --- | --- |
| Admission and queue selection | Current approval including authority provenance; revision/workflow; durable holds applicable to admission/build; existing main-health/capacity rules. Expose merge/release-only holds without falsely saying all useful planning is impossible. |
| Automatic merge question creation | No unresolved applicable early decisions; current policy/risk/qualification; exact diff/base/target path evidence from #2. Missing path or authority evidence means manual/held, never automatic. |
| Answer/disposition acceptance | Inbox and obligation versions, current task/scope/options/candidate, expiry, role, exact grant entry if delegated; atomic consumption; merge/satisfied/complete holds; recompute current automatic path/policy eligibility when accepting a policy answer. “Merge” is not also an answer to unrelated product obligations. |
| Preparation | Operation-contract checks plus plan consent and applicable obligations; assemble exact agent evidence. Record current authority binding in intent; pin operation and target. |
| Prepared-to-dispatch transaction | Reload flow/task/attempt and canonical records; check stop/recovery, task approval, identity, all applicable obligations, authority uses, grant validity, plan consent, merge/satisfied evidence, current auto policy/path eligibility, release clearance. Compare cached intent authority digest to the freshly derived binding. Only then mark dispatching and record authority revision/use IDs. |
| Terminal completed and task close | Guard `forge.closeTask` before external closure and every `end` with outcome completed, for every flow kind and graph shape. A successful merge receipt is necessary evidence for a change, not a substitute for resolving an outstanding early decision. |
| Release write | Check complete included-scope manifest, exact report set, explicit substantive review and release permission immediately before integration dispatch. Read-only candidate verification and reconciliation can continue while held. |
| Settlement | Retain verified facts and costs even after authority changes. Ingest declared choices/holds before permitting the next step; never mint a disposition from model output. Stop further protected progression if new obligations apply. |

A stale prepared intent must not be silently patched after hashing. Mark it `not-dispatched` with reason and zero cost, clear its ownership, and prepare a new intent after deliberate revalidation (or leave the flow waiting/stopped with a concrete reason). No supervisor launch occurs for that intent. If a new authority revision changes nothing relevant, an implementation may prove equality of the exact evidence binding; otherwise rebuild. Agent-bound approval evidence changes also require fresh input, not merely a fresh dispatcher check.

When a hold arrives before dispatch, the serialized transaction fences it even if `writeIntent` already created files. When it arrives after `dispatching` commits, the effect is potentially in flight, even before a launch acknowledgment. Cancellation is best effort; preserve the uncertain-attempt protocol. Reconcile remote PR state with expected candidate/target and retained intent/receipt identity. Record `merged` as fact if proved, retain the unresolved decision, block release and further protected progression, and surface that the hold arrived too late to prevent the merge. Do not reopen the merge as a new attempt or treat remote success as operator resolution.

The dispatcher may validate the passed dispatch proof and candidate again, but a static proof cannot observe future revocation. The enforceable local linearization point is the engine transaction; remote branch-protection/expected-head checks remain separately necessary. A late direct external merge cannot be prevented by this core.

### Custom graphs and alternate completion

Add operation-derived guards, not checks for nodes named `decide` or `merge`. Catalog/contract validation rejects attempts to mark guarded operations unguarded. `forge.merge`, `outcome.satisfied`, `forge.closeTask`, applicable `provider.build`, and release integration writes are protected independent of node name. A `task` graph's “done → close → completed” and “done → completed” both check obligations. Failed/stopped terminals can retain unresolved obligations without claiming delivery; administrative abandon cannot cancel the underlying work decision.

Known external writes in commissioned extension adapters must declare semantic effects, including release/merge, with pinned definitions. Trusted arbitrary argv is already outside a semantic proof of what the command does: it cannot be certified as an enforced merge/release path merely by labeling itself read-only. Installation qualification must identify and replace such release entry points with protected adapters, or explicitly report them unenforced. Do not claim sandbox isolation.

## 6. Requests, plan consent and reports reaching agents

**Request provenance (#5).** Add `requestRefs` through task validation/import, immutable revision snapshots, task views and action inputs. A request record contains origin kind (operator/source/incident/schedule), source identity/date, verbatim text when actually available, and digest; never fabricate an operator quote for maintenance. Keep derived acceptance separate. Requests do not grant authority, even when their prose says “approved.” Changing meaningful request provenance requires a new revision; source status churn retains the current stable-brief exception. Historic missing text is `unknown`, not reconstructed verbatim.

**Plan consent.** Baseline `provider.planReview` and `forge.publishPlan` do not record operator consent. Add a plan-consent decision purpose when the project requires it, pinning plan body/report digest, task revision, governing context, workflow and base identity. Initial approval authorizes planning within scope; it is not approval of a plan that did not yet exist. The operation guard before `provider.build` applies even to a custom graph without a consent node. A new presentation can be created from canonical pending consent. A replan, materially changed context, changed task, or changed base invalidates consent; do not let `followTarget` carry it across a base change by merely mutating the plan identity. Keep any future consent-equivalence relaxation separate.

**Direct authority revocation and ratification.** `task.revoke` keeps its current meaning (task approval only) and never revokes decision or release-review evidence. Add two operator-only commands, neither delegable nor grantable:

- `decision.revoke {obligationId, expectedObligationVersion, dispositionId, reason}`. Preconditions: the obligation version matches and the disposition is its active one. Transition: the obligation returns to `unresolved` with a new version, the disposition and its `authorityUse` are marked inactive (never deleted), and the task's authority revision increments. Downstream: derived clearances become inactive, prepared intents fail the prepared-to-dispatch fence, queued admission re-evaluates, and effects already dispatched are reconciled and reported as an authority race rather than claimed prevented. Revocation of a release review follows the same pattern on the release scope's authority/report-set revision.
- `decision.ratify {obligationId, expectedObligationVersion, inactiveDispositionId, rationale}`. Preconditions: the obligation is unresolved, the named disposition is inactive and belongs to it, and the current task revision, scope and options digest still match what that disposition answered. Transition: a new disposition version with a direct-operator `authorityUse` and the same selected answer, bound to the current revision and scope; the old disposition stays inactive history. If scope or options changed, ratification is rejected and the operator must answer anew.

Both are recorded in the command receipt and console journal like other authority changes, replay to their canonical receipt, and require fixtures for revocation before dispatch, after preparation, and after a dispatched effect, plus ratification after grant expiry and rejection of ratification across a changed scope.

Projects with an existing structured consent requirement map it explicitly at commissioning. A requirement found only in governing prose must be surfaced and recorded, not silently treated as executable policy. New starter projects keep consent optional unless commissioned; there is no new universal plan-approval step. This does not weaken a project's already-required consent. A grant for task approval cannot authorize plan consent; the grant must enumerate the actual plan identity.

**Worker input.** `actionSpecification` supplies a bounded `authorityContext` to planner/builder/reviewer prompts: original request references/text, exact task approval and source, active decisions and selected answers, required but missing consent, permitted scope, applicable grant-use evidence, and report-review state. Resumed sessions receive the same current delta explicitly. This is read-only context; workers cannot issue grants. Pin its digest in the attempt and record delivered references alongside existing context records. If required evidence cannot fit bounds, fail preparation with a useful diagnostic or provide deterministic bounded artifacts; do not silently truncate authority out of a prompt.

**Reports (#6).** Extend `RISK_PLAN_SCHEMA` and `DELIVERY_BUILD_SCHEMA` in `adapters/providers/index.mjs` with a versioned bounded choice report. Each choice has stable local ID, chosen behavior/options, rationale, user-visible scope, relation to request/acceptance, owner/classification and unresolved conflicts. Schema validation and `Engine.settle` ingest append-only report versions keyed by attempt and local ID, linking explicitly declared operator/conflict choices to durable obligations. Do not deduplicate by title alone; cross-attempt linking needs stable identity plus scope/content checks. New content is a new version; duplicates from receipt replay are no-ops.

Capture valid reports from blocked results as well as ready/implemented results. Failed/malformed output cannot establish clearance: retain evidence and mark coverage unknown pending repair. Model declarations are not proof all product choices were found. Explicit operator-owned choices cannot be erased by a later empty array, revised report or lower-risk declaration. Other declared user-visible choices may proceed toward merge but remain in the collected pre-release review. Present structured choices and evidence, not only a completion notification.

## 7. Release review and external enforcement boundary

A release scope manifest identifies repository/target, exact candidate or artifact digest, included feature/task revisions, and the exact latest applicable report versions. Feature IDs are descriptive grouping; task revision and content digests remain authoritative. Resolve included scope using a commissioned integration with verifiable provenance (for example delivery receipts plus candidate ancestry), not a caller's omission-prone list. Incomplete lineage or report coverage is a release hold requiring explicit inspection and evidence completion. Non-factory changes require an explicit scope/report entry; absence is not proof of no choices.

`release.review` submits the manifest digest, report-set digest and substantive per-choice dispositions (accept, require change, or a reasoned not-applicable disposition tied to excluded scope). A UI may offer review-all of the exact displayed set with explicit confirmation; not a generic “acknowledge report” action. Require-change creates/retains obligations and refuses clearance. Review cannot silently dispose of earlier operator-owned/conflicting questions. Resolve those using their exact obligations first. Report delivery/read receipts never create a review record.

Each included new/revised choice or included feature/revision change invalidates the affected clearance. An unrelated report outside the manifest need not invalidate it. The initial implementation can conservatively require a new complete review record for the changed manifest; do not silently union old reviews into new clearance. Explicit direct operator confirmation of a proven empty, complete report set is possible; missing legacy reports are not an empty set.

For `integrationWorkflows.kind: 'release'`, derive scope on admission and check clearance at answer acceptance and at every mutating `integration.run` dispatch. Preserve candidate/config/result/spending checks already in `runIntegrationStage`; release review is additional. Enqueue permission, scheduled operation authority and today's synthetic `integration.grant` do not imply review. Pass exact review/authority evidence to the adapter and retain it with the receipt. Keep read-only lookup/reconciliation available after dispatch.

For external release commands, the concrete enforcement boundary is a commissioned release adapter invoked as a supervised factory operation with a canonical candidate/scope and current clearance. Move the release mutation into that adapter or arrange an independently enforced release service that consults current clearance and owns execution. A standalone “check clearance” command followed later by arbitrary shell has a time-of-check gap and is advisory only. Do not claim core fences arbitrary shell, forge UI releases or credentials shared by the same OS account. Qualifying an external release integration and granting it execution rights requires project-owned review; this assignment does not install one or change a live release route.

## 8. API, UI, queue and retention

Keep envelope protocol v1 if backward-compatible additive negotiation suffices, but advertise explicit capabilities such as `decisionAuthority.v1`, `standaloneQuestion.v2`, `operatorGrants.v1`, `decisionReports.v1`. Record schema versions are independent of inbox's mutation `version`. Reject unsupported bound-question fields; never downgrade them to informational questions. Old clients can read legacy items and ordinary operations, but cannot issue new authority commands without the capability/required preconditions.

Publication v2 distinguishes `purpose: informational` from `purpose: decision`, with `{decisionId, expectedDecisionVersion, taskId, taskRevision, scopeDigest}` or an atomic creation payload. Decision-bound choices map exact IDs to structured dispositions; “discuss” is explicitly non-resolving. Retain existing two-to-eight bounded choice presentation where useful; new options create a new obligation version, invalidate stale cards/grants and do not merely change labels under old IDs. An informational question answer remains just an answer. Old question publications remain informational and must not masquerade as an enforced operator hold.

Extend service `collection` kinds, `handshake`, snapshot/dashboard summaries and console supported-command/collection allowlists. Add filtered, paginated decision/grant/report views and bounded active-task hold summaries; avoid full historical report scans in routine polling. CLI command help and examples must cover grant references, disposition preconditions, revocation consequences, replay and compatibility. Console journal hashing/forwarding must include authority references, not drop them. On a stale form or project binding change, reject and refresh; never retarget the command.

Inbox displays the durable decision separately from its current card, showing task/revision, scope/options, blocked boundaries, grant coverage and resolution history. Withdrawing a card warns that the obligation remains. Generic to-do resolution must not be offered for decisions. Approval UI distinguishes “approve this brief” from “issue exact batch grant,” “consent to this plan” and “review these release choices.” Defaults never invent an answer; show the exact proposed grant entries before the direct operator issue command.

Queue/Tasks show `decision-held`, `plan-consent-required`, `grant-expired/revoked`, and `release-review-required` with linked IDs and stage-specific eligibility. Stopped/waiting change flows still consume existing change capacity; document/task/maintenance pools retain their existing rules. A decision on a queued task consumes no flow slot. Stop/abandon/restart may release or retain capacity only under today's ownership rules, without clearing its task's hold. Diagnostics must explain a slot held by stopped work and list the independent decision that would still block a replacement. Do not implement a new queue policy in this slice.

Unresolved obligations and all referenced disposition/grant/report/release-review evidence are retention roots, even after expiry or abandonment. Extend archive-retention guards and reference discovery; closed presentation is not deletion eligibility. Backup/restore includes these records, usage counters, command receipts and authority revisions atomically. A restored old snapshot cannot independently authorize uncertain external writes; existing recovery hold and reconciliation remain mandatory.

## 9. Migration, defaults and adoption

1. Ship capability support, docs/help and fixtures first; no live activation as part of implementation. Automatic merge remains at its existing setting and cannot newly qualify until #7/#8 and #2 acceptance pass. Do not enable it by a default or infer permission from adoption.
2. New projects on the completed implementation enforce D3/D4 semantics by default for these protected operations. Operational delegation retains its commissioned policy. No switch may let the orchestrator opt itself back into prose authority.
3. Existing installations adopt through an explicit drained upgrade, backup, migration preview and commissioning. Bump the database schema compatibility boundary when authority records become enforceable: dev.78's equality check must refuse a migrated database. Add an explicit offline migration path before normal `Store` construction; do not make constructor reads silently rewrite an adopter's state. Root owns release compatibility/version changes.
4. Preview enumerates existing approvals, operator questions, ambiguous legacy authority and release adapters needing mapping. Direct-operator approvals with exact existing revision/workflow and reconstructible evidence may be retained with a migration record. Legacy delegated approvals or ambiguous provenance are marked `legacy-unverified` for new protected effects, pending direct ratification or an exact new grant. Do not infer grants from old `onBehalfOf`, task text, chat links or synthetic job grants. Completed historical facts remain unchanged.
5. Existing standalone questions stay schema-v1 informational. The operator/commissioning process explicitly binds known outstanding product decisions to task revisions before automation is qualified; code cannot discover all obligations in prose. Existing flow questions with explicit structured operator-decision meaning can be imported deterministically; ambiguous ones require review. Mark coverage incomplete until this migration inventory is resolved, rather than declaring old silence clear.
6. Pinned active change/integration flows drain under the original executor. Unresolved/uncertain external effects reconcile before activation. The existing carried-over task-question exception requires migration/rebinding with preserved obligations and new versioned cards; otherwise hold it for explicit restart. A prepared old intent is invalidated as not dispatched under controlled migration, never launched with newly assumed authority.
7. Historical reports remain schema-v1/coverage-unknown. Add explicit report/import evidence for included unreleased work before release clearance. New provider schema is pinned per new attempt; old receipts are parsed as historical data and cannot establish new review coverage. No live provider calls are required to migrate authority records.
8. A migrated project starts with an explicit commissioning hold until required legacy mappings/ratifications are complete; display its reasons. Existing configured auto-merge is not relabeled qualified until the new checks pass. Adoption changes are documented and operator initiated, not live policy changes performed by the upstream release. Schema rollback requires restoring the pre-migration backup and reconciling any subsequent effects; never edit version markers to run an old binary against new authority state.

## 11. Strategy consequences and remaining decisions

Findings that refine implementation scope without reopening D3/D4:

- A hold field on an inbox row is insufficient. Add task revision/applicability and retention work before claiming durability.
- Approval authority must include nested restart approval, effective configuration changes and integration admission's synthetic grant. Changing only `operatorAuthority('answer')` leaves bypasses.
- The final engine transaction currently lacks operation-specific decision revalidation. Prepared-intent invalidation and in-flight reconciliation are separate slices, both required before automation.
- Plan review/publication is not plan consent. Required consent needs a distinct canonical binding and build guard, with implications for `followTarget`.
- Release review needs scope provenance and an enforceable adapter boundary, not just report UI. Core support may ship before every adopter's external release path is qualified, but those paths must remain explicitly unqualified.
- Old schema-v1 questions and prose approvals cannot be automatically converted to exact authority. Adoption needs a visible compatibility/ratification inventory and old-binary refusal.

No new operator decision is needed to implement D3/D4's core primitives. Recommended implementation choices above (conservative grant expiry, exact consent rebinding, direct-only release review initially) should receive independent design review; they do not authorize live changes. Operator decisions remain installation-specific: which legacy ambiguous decisions map to which task scope; exact grants/answers; which projects require plan consent; release scope/adapter and its execution authorization; D2's target/protection/document-workflow choices; and explicit automation activation. Stronger human authentication or malicious-agent isolation would require a separate boundary design and approval, not a stronger claim about this implementation.

Validation for this assignment is document-only: audited named code paths against the stated baseline, checked local Markdown targets and whitespace, and verified that the commit contains only this design document. Runtime tests, new fixtures, independent design review, implementation, migration and release qualification remain outstanding.
