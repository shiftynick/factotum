# Local shared console

This dependency-free server runs on Node.js 24 or newer. Each project remains authoritative for its workflow and validates every command. The console queries only explicitly registered Unix sockets and never opens project state databases.

```js
import { registerProject, startConsole } from './console.mjs';

await registerProject('/absolute/private/console-state', {
  socketPath: '/absolute/private/project-state/service.sock',
});
const consoleServer = await startConsole({
  stateDir: '/absolute/private/console-state',
  port: 0,
});
console.log(consoleServer.url);
// await consoleServer.close();
```

`registerProject` validates protocol version 1 and the snapshot, command and commandStatus capabilities. It generates an immutable binding ID and rejects duplicate active project IDs, service IDs and endpoints. `unregisterProject(stateDir, projectId)` hides a project while retaining old binding and command identities. A replacement registration generates a new binding ID. The instance also exposes `registerProject`, `unregisterProject` and `reconcile` methods.

The private `console.sqlite` database stores the registry and a command journal using full synchronous SQLite transactions. Protect and back up the containing state directory. Journal entries contain identities and a digest, without the executable payload. Receipt recovery queries the original endpoint and verifies both its project and service identities, including after unregistration. A missing receipt stays unknown; no automatic retry submits an action. Concurrent duplicate commands dispatch at most once from the console, while the canonical project command store must independently deduplicate.

The browser receives no socket paths. It uses one loopback origin, an HttpOnly SameSite session cookie and a CSRF header. Binding to a non-loopback address is rejected. This serves one trusted local operator; same-account processes are within the trust boundary. Restarting the console creates a new browser session; reload the page to establish it.

## Operator interface

The browser application is plain ES modules (`ui.mjs` and `ui/*.mjs`) and one stylesheet, served from a fixed allowlist. It needs no build step or dependency. A sidebar selects **All projects** or one project; a select replaces it on narrow screens. Views:

- **Overview** — all projects: reachability, open decisions, active flows, unresolved commands, a card per project and a combined *Needs attention* list. One project: state, work in progress with workflow step progress, recent finishes and activity, attention items, pause/resume admission and a confirmed *stop all* scoped to that project. When doctor has not passed for the current configuration, the state reads *Commissioning required* and a notice at the top links to **Run doctor** in Settings → Status, saying whether a requested run is queued, running or failed. The *Open inbox items* count is open questions and notices plus open to-dos, the same number as the sidebar and Inbox badges.
- **Inbox** — open, resolved or all decisions, plus **to-dos**: obligations still owed after a flow (post-merge steps from the brief, closing the source task, failed cleanup or label updates), each resolved as done, could not be done or deferred, with evidence. Open to-dos count in the Inbox badge. Every item names its project, flow, step and expiry. A resolved item keeps its own status badge (answered, withdrawn…); only an open question past its expiry is badged *Expired*. Answers need an explicit confirmation that names the target project; a refused answer to a question settled meanwhile says what the project now records. An open merge question has a **Candidate** section: the pull request, the candidate commit, its base, the review verdict with the findings count by severity, the gate checks and any fast checks (a result recorded for another commit is marked as such), and a link to the changes on the forge. Text the project adds to the question is shown above it unchanged.
- **Timeline** — an Active panel listing running and stopped work one row per flow, then the project timeline for the last 6 h, 12 h, 24 h or 3 days. It shows change slots, planning slots and any task or maintenance lanes, with bars coloured by what each flow was doing; an events lane (merges, failures, stops, questions, upgrades, configuration updates); tiles for merges, plans, completions and idle slot time; and machine charts (CPU and disk wait, memory and swap) from the host samples the operations loop records every two minutes. Selecting a bar, marker or open item opens that flow's detail.
- **Tasks** — issue-source refresh and last observation, paginated task briefs and source state, revisions and approval history, Approve/Start/Queue/Revoke/Edit actions, task detail and flow links. Approval alone does not begin delivery. Older Plan deep links remain Tasks aliases.
- **Queue** — the complete ordered queue, priority and pin drafts, reorder/dequeue with explicit save, dispatch order, a banner only when the queue can't move on its own (with Dispatch now when automatic admission is off), Started from the queue, and, for a selected task, why it has not started yet. Concurrent queue metadata/order changes reject stale saves; hidden task rows are preserved.
- **Scheduled** — tasks with a not-before time, recurring tasks, scheduled tasks and maintenance schedules, soonest first, with Run now, Pause/Resume or Disable/Enable, Edit time for tasks, the last report of a scheduled task, and **Add a maintenance schedule**.
- **History** — all supported record kinds, including operational history, newest or oldest first, with page size, *Load more*, search and status filters over loaded records, and a drill-down panel with the raw record as a secondary view.
- **Stats** — by day for the last 7 or 30 days, or by week for 12 weeks. Each card has a headline for the window and a bar per period; faded bars rest on fewer than five samples, and clicking a bar lists the flows behind it. Sections: throughput and speed (changes, documents and tasks finished, failures, start of work to merge split by where the time went, time in the queue); quality of first attempts (first-review pass rate, one-build merges, review and build rounds, stops, orchestrator involvement, replans, planned against unplanned); checks (time and failures per change, slowest checks, main verification history with merges since the last green); decisions (your and the orchestrator's response times, expired questions); failures and stops; the list-price estimate (list-price cost per change and per period by role, and tokens, also stacked by model; prices from the provider, or from `stats.pricing` in Settings → Policy); models (steps, duration, failures, tokens and estimate per model); tasks (added, completed, open now, age of approved work, merges by area); maintenance by operation. *All projects* compares the last 7 days side by side.
- **Health** — main health; anything that needs recovery (a recovery hold, an uncertain step, a spending hold), shown only when present; **Knowledge upkeep**, when upkeep is on, something is suspended or a candidate is listed: each suspension with its rule and reason and the form that lifts it (yours alone); the open docs follow-up the factory made, waiting for your approval or approved, with when it expires unapproved; the open upkeep candidates, shown as text with who wrote them, their source flows and when each expires, with *Decline* and *Dealt with another way* (none is accepted by hand: the factory makes docs follow-ups itself); candidates with a task, with *Decline, and close its task*; and closed candidates, with *Reopen*; and audit findings: open and tasked ones with *Create a task from this finding* (which records the task against the finding), *Decline* and *Dealt with another way*, and recently closed ones with *Reopen*. Every finding form names the finding version it showed, so a finding that changed meanwhile is refused. Overview and Timeline link here when recovery is needed. Post-merge obligations are Inbox to-dos; retrospectives, context given to agents, rule proposals, obligations and regression reports for a flow are in its detail; notification deliveries and other logs are in History.
- **Settings** — in sections. **Status**: delivery or rehearsal, whether doctor passed for this configuration, **Run doctor**, and how configuration changes work. **Policy**: every setting with its effective value and whether it's the default, grouped; live settings have **Change** and **Reset to default** (no drain, no doctor), others are marked *config file*. **Models**: editable model defaults grouped by workflow, provider/model/effort controls and reset to the project default; provider-role configuration is shown below. New flows pin the selected routes, shown in flow detail. **Repository and checks**: repository, gate and main check commands (read-only) and governing context. **Workflows**: how a task's workflow is chosen and each workflow's kind and steps. **Advanced**: registration, resources, raw settings. **This browser**: display preferences and unsent drafts. Maintenance schedules are managed on the Scheduled tab.
- **Receipts** — the console command journal and canonical receipts, filterable by status.

**Detail modal.** Selecting a flow or task anywhere opens its detail in a modal over the current page: the per-flow execution timeline (workflow steps, decision and resource waits, recorded events, attempt receipts and logs), summary, controls, decisions, retrospective and events for a flow, or the brief, approval and actions for a task. An attempt whose step ran and reported a failure (a failed fast check or gate check) is drawn as failed; its view lists the failed checks with the rules each enforces and their diagnostics. Only evidence files the step can have are offered (no provider logs for a check). The summary labels the workspace branch, the target head it was created from and the candidate commit, and shows a stop reason only while the flow is stopped. Its **Flow slot** line says, as the project derives it, whether the flow is working, parked on an answer (within the parked limit, or beyond it and so keeping its slot), answered and waiting for a slot (with its position) or for a place in its category, or stopped, and whether it holds a slot. Every flow a hold or slot reason names is a link to its detail. Choosing an attempt replaces the address rather than adding a history entry, so browser Back closes the detail from any attempt. A grouped timeline marker's list closes with Escape (focus returns to its count; in the detail modal the first Escape closes only the list, wherever focus is, and the next one the modal), a click outside it or any navigation. **Decisions** lists each answer with who gave it (the operator, or the orchestrator on the operator's behalf with the instruction or relayed words), when, its note, and for a merge or accepted outcome who signed off on which commit. Times everywhere name their zone; timestamps embedded in recorded text are shown in the same zone. The address carries `?flow=<flowId>` (with `&attempt=<attemptId>`) or `?task=<taskId>`, so it can be shared; **Copy link** copies it, and closing returns to the page. On Tasks, `?task` selects the task inline.

Routes are hash deep links such as `#/p/<projectId>/history?flow=<flowId>&attempt=<attemptId>`; the last route is remembered locally. A link to an unregistered project never falls back to another project.

Each form keeps its draft text, command identity, project, registry binding and displayed subject version in session storage, so drafts survive refresh, navigation and reload. A draft whose binding has been replaced cannot be sent; a draft whose subject changed must be explicitly retargeted. A submitted draft whose outcome is unknown stays locked until the journal shows its receipt; if the console has no journal entry, it was never dispatched and may be sent again. Automatic refresh pauses rendering while you type and offers *Show new data*. Action closures capture the original project, binding and subject version; a selection change cannot retarget an existing action. Read failures are isolated with bounded transport timeouts and at most eight simultaneous project reads. Projects with unsupported protocols are explicitly incompatible. The initial protocol supports version 1 only; future supported versions must be negotiated in the transport layer.

Schedule cadence and enablement can be changed through the existing canonical schedule commands. Configuration changes, commissioning, uncertain-effect reconciliation and restore release remain CLI operations so the operator inspects the complete evidence and executable configuration locally.

Run qualification tests with:

```sh
node --test tests/console-server.test.mjs tests/console-details.test.mjs tests/console-views.test.mjs
```

Project detail reads use `/api/project/:projectId/flows/:flowId`, `/api/project/:projectId/collections/:kind` and `/api/project/:projectId/artifacts/:attemptId`. Every route requires the immutable `bindingId` query parameter, a valid browser session and the same loopback origin. Collections use bounded numeric `cursor`/`limit` and an optional `order` of `asc` or `desc`; artifact names are a static allowlist. Collection kinds also include `command`, `retrospective` and `context`. Flow details add the flow's waits, context deliveries, retrospective and attempt lifecycle events. Browser input cannot configure an endpoint or arbitrary file path. The console validates returned project and subject identities and forwards only the defined response envelope. Project services must redact secrets from their nested public projections and evidence. Source and trace content is rendered only as text.

Project snapshots add read-only `settings` (no credentials, executable argv or private paths), `stats` (observed statistics with sample counts and coverage), recent `waits`, and per-task `planningReasons`/`planReadiness` hints. These are presentation; canonical project validation still rejects stale authority. Unknown command outcomes hold further UI commands for that project until receipt reconciliation; they are never silently retried.

Task, schedule and queue edits use advertised canonical preconditions. Older project services without them remain readable but these edits are disabled. See UI buildout and validation (`docs/ui-buildout.md` in the Factotum reference).
