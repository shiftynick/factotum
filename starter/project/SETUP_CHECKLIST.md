# Project setup checklist

Decide these before the first real task. Each takes a minute now and saves a stall later. Settings marked *live* can change later from the console without draining work; the rest change with `config update`.

## Who decides

- [ ] **Merges.** `policy.mergeDecisionRole`: `operator` (you answer every merge question) or `orchestrator` (it decides ordinary-risk merges; strict work and adopted pull requests stay with you, and an adopted pull request's merge question is refused to the orchestrator even on your instruction). Not the same as `autoMerge`.
- [ ] **Deploy and spending approvals.** `policy.delegateIntegrationDecisions`: whether the orchestrator may answer them on your recorded instruction. Strict-review sign-off always stays with you.
- [ ] **What the orchestrator may do for you.** `policy.delegatedOperations` (*live*): every delegable operation by default; narrow it if you want.
- [ ] **Who deploys, and how.** Deploys happen outside flows: by you, by the orchestrator in a task workflow, or by an integration workflow. Never from inside a change flow.

## How work flows

- [ ] **Automatic queue.** `policy.autoQueue` and `policy.queueOnApproval` (*live*): whether approved work starts on its own.
- [ ] **Capacity.** `policy.maxFlows`, `policy.maxDocumentFlows`, `policy.maxTaskFlows` (*live*). A change or document flow waiting on an answer holds no slot, up to `policy.maxParkedFlows` (default 3, *live*; 0 makes every waiting flow hold its slot), so one open question does not stall the queue; its paths still keep overlapping work out. A task's declared `paths` keep overlapping work apart at admission. They are not enforced on the candidate, but checks receive them (`FACTOTUM_TASK_PATHS`, `FACTOTUM_TASK_PATHS_FILE`) and the reviewer is told which changed files fall outside them and to treat those as findings unless the plan justifies them. Before raising `maxFlows` above 1, decide whether that is enough or add a fast check that fails on out-of-path files (the starter example has one, off by default). See declared paths (`docs/adoption.md` in the Factotum reference).
- [ ] **Workflows.** Which work is code (`change.standard`), documents (`change.document`, review only, no check gate), or carried out by someone (`task.orchestrator`, `task.operator`), and the labels that select each. See project workflows (`docs/project-workflows.md` in the Factotum reference).
- [ ] **Planning.** `policy.planning`: plan and review the plan before building (default on).
- [ ] **Models.** `providers`: the template plans and builds with Claude Opus 5.5 and reviews with GPT-6.1 Sol (Codex). Same-family review is allowed. List every model a task may choose in each role's `allowedModels` (the template lists Claude Fable 5.2 for the most important or complex work); a task picks one with `task.models`, and anything outside the list is a configuration change. Defaults per step are *live* (Settings → Models).

## The repository

- [ ] **Your own repository-wide checks.** Exclude the installed files (the install prefix, for example `tools/factotum/`, or `factory/`, `project/`, `VERSION` and `compatibility.json` for a root installation) and `factotum.lock.json` from linters, formatters, type checkers, test discovery and pattern, licence or naming scanners, on the installation branch before it merges. A project script that walks the tree itself and has no ignore list needs a path filter in its own code; an install prefix outside the folders it walks avoids that. Never change managed files to satisfy a local rule: doctor reports that as drift. Examples for common tools are in adoption (`docs/adoption.md#keep-project-wide-tooling-off-the-installed-files` in the Factotum reference).
- [ ] **Direct commits to main.** People committing straight to the target branch is fine: a running change carries on if none of its planned paths changed, and replans (with a fresh budget) if one did. Set `policy.followTarget: false` to have it stop instead.
- [ ] **Target branch names.** `repository.target` and every workflow `target` must be at most 200 characters of letters, digits, `.`, `_`, `/` and `-`, start with a letter or digit, and contain no `..` (for example `main`, `next`, `release/2026.11`). Configuration validation and doctor refuse other names.
- [ ] **More than one target branch.** If some work merges into another branch (for example website changes into `next`), give that workflow a `target`, route it by label, and set `repository.syncTargets` to keep the branches in step. See target branches (`docs/project-workflows.md#target-branches` in the Factotum reference).
- [ ] **Merged branches.** The factory never deletes remote branches, so every delivered flow leaves a `factotum/…` branch on GitHub. Turn on the repository setting *Automatically delete head branches*, or plan to delete them.
- [ ] **Adopted pull requests.** `repository.adoptionNotice` (default on): when the factory adopts an outside pull request it comments once on it with a link to the replacement. Set `false` to stay silent there. See adoption (`docs/adoption.md#task-to-delivery-commissioning` in the Factotum reference).
- [ ] **History.** Merge and squash commits are titled `<task title> (#<PR>)`, with the task ID and flow ID in the message; `repository.mergeMethod: "rebase"` keeps the builder's commits instead. See merge method (`docs/integrations/github.md#merge-method-and-preserved-history` in the Factotum reference).
- [ ] **Branch protection.** If the target requires a status check, it should be `factotum/gate` (`repository.checkContext`). Set `checkContext` to the status name your protection requires; it is posted by `repository.account` once the gate's checks pass. If a required Actions check reads that status when the PR opens, set `repository.rerunFailedChecks`. Document workflows publish no gate status, so a branch that requires it refuses their merges; use a change workflow for documents there.
- [ ] **Checks.** `checks` (the change gate) and `mainChecks` (main verification): real commands, with timeouts that fit.
- [ ] **Main-check tiers.** If the full baseline is too slow to run after every merge, mark the slow checks `"tier": "scheduled"` and schedule a full `main.verify` (for example daily). Merges then run only the rest. A scheduled failure stops admission until a full verification passes; scheduled evidence older than `policy.scheduledHealthMaxAgeMs` (default 26 hours) also stops it. Avoid putting the same check in both the gate (`checks`) and the scheduled tier: a direct push that breaks it stays invisible until the next full run while every flow's gate fails on it. See main-check tiers (`docs/operations.md#main-check-tiers-after-every-merge-or-scheduled-only` in the Factotum reference).
- [ ] **Rules a script can check.** If reviews keep sending work back over a mechanical rule (a step not run or not updated, a missing test or changelog entry), move it into `fastChecks`: a cheap project script that runs on the built candidate before review and sends a violation straight back to the builder. List the rule in the check's `rules` so reviewers are told not to raise it. Start from `project/integrations/fast-check.example.mjs`. See fast checks (`docs/project-workflows.md#fast-checks-before-review` in the Factotum reference).
- [ ] **Governing context.** `context.files`: the rules and guides every model step reads. A change to one of them makes a running change replan.
- [ ] **Knowledge upkeep (optional, off).** `upkeep.mode` is `off` in the template. To see how often a merge leaves a doc or a rule to look at, list your docs in `upkeep.docs.include` (there is no default; keep dated records such as changelogs in `exclude`), run `config update` and doctor, then set `upkeep.mode` to `observe`. `observe` only records what it finds: no candidate and no task. After about 20 runs you may set `propose`: the docs corrections it keeps become docs follow-up tasks that run only after you approve them (at most 2 a day and 6 a week). With a workflow catalog, set `upkeep.docs.workflow` or a selection rule for the category `knowledge-upkeep` that reaches a change or document workflow. When a doc or a rule refers to what a merge touched, it asks a model once, at most 30 times a day: `providers.upkeep`, or the reviewer's model as it is when you turn upkeep on (later reviewer changes do not move it). Only the operator changes these settings; a delegate can turn the mode off. See knowledge upkeep (`docs/operations.md#knowledge-upkeep` in the Factotum reference).

## What agents can and can't reach

- [ ] **Original requests recorded as provenance.** Briefs written from an operator request carry `originalRequest` with the operator's verbatim words, source and date; incident, schedule and review tasks record that origin without an operator quotation. Nobody, human or agent, treats a recorded request as approval: approve the exact task revision separately.
- [ ] **No network in builders.** Model steps run without network access. Data a task needs must already be in the checkout, or be declared in the brief's `inputs` so the task waits until it exists and the factory copies it into the worktree.
- [ ] **Helper scripts agents run.** Readiness checks, classifiers and generators that planners or builders run spawn child processes with stdin ignored (in Node, `stdio: ['ignore', 'pipe', 'pipe']`); some provider sandboxes refuse a piped child stdin. See providers (`docs/integrations/providers.md` in the Factotum reference).
- [ ] **Offline data.** Decide where it lives (for example a git-ignored `data/` directory) and add a note to a governing context file.
- [ ] **Design changes.** If someone should see a change before it merges, configure `preview` (a command that writes screenshots, and the paths it applies to); the images appear on the merge question. See project workflows (`docs/project-workflows.md#preview-before-merge` in the Factotum reference).

## Running it

- [ ] **One console.** Register the project with the machine's existing shared console (`factotum-console.service`) rather than starting another, so every project shows in one place.
- [ ] **Configuration file.** Keep it outside the repository checkout, in a private directory (mode 0600), and pass that path to `init` and `config update`. Tracked, it puts the account and private paths in Git; untracked in the checkout, it makes doctor refuse the checkout. See where it lives (`docs/adoption.md#copy-and-configure` in the Factotum reference).
- [ ] **Doctor.** Run it after every `config update`: from the console (Settings → Status → Run doctor), with `doctor.request`, or from the CLI. Re-checking a configuration that already passed needs the runner stopped. Doctor needs your checkout clean and with no commits that are not on remote main. Behind is fine (doctor warns how far), unless the commits it lacks change the installed core (`factory/`, `VERSION` and `compatibility.json`, all under the install prefix if `factotum.lock.json` records one, for example `tools/factotum/factory/`), `factotum.lock.json` or a file the configuration names in a command (checks, preview, scheduled tasks, source and integration adapters, workspace setup; see running (`docs/running.md#configure-and-commission-delivery` in the Factotum reference) for what doctor can and cannot find): then run `git pull --ff-only` in it (with work drained when the installed core changed). Workflow definitions only warn; pull before `config update` when a merge changed one. Keep secrets, including the notification delivery file, out of governing context: the model is sent context as it is. See running (`docs/running.md#configure-and-commission-delivery` in the Factotum reference).
- [ ] **Live settings survive `config update`.** A setting changed in the console is kept when the file is applied; run `config show` before editing the file, or pass `--replace-live`.
- [ ] **Upgrades.** They need a drained project. `upgrade apply --when-drained` pauses new work, waits and applies on its own.
- [ ] **Notifications.** `notifications.level` (*live*): `essential` (default), `actionable` (omit proven clean delivery/target-sync summaries), or `all`, and where they are delivered. Questions, failures and obligations remain visible under `actionable`; pending deliveries are filtered at their next dispatch.
- [ ] **Notification wiring.** For a T3 orchestrator, follow the T3 setup steps (`docs/integrations/t3.md#setup-step-by-step` in the Factotum reference), and install the handling guide and state filter before turning delivery on. The delivery file must stay a private 0600 file; if it breaks, delivery pauses (shown in `status` and the console) until it is fixed. Turning delivery on delivers only items still open. The T3 ask prompt stays off until the operator has confirmed they see its prompts. Then, recommended: a triage proxy thread (`docs/integrations/t3.md#triage-proxy-thread-recommended` in the Factotum reference) that receives the webhook and the timer checks and wakes the orchestrator only when it must act (copy `integrations/t3-triage.example.md` and `integrations/triage.example.mjs`; set `notifications.level` to `actionable` first). Report its forwarded, absorbed and missed counts upstream.
- [ ] **Orchestrator handoff.** `notifications.handoffAfterDeliveries` (*live*, default 100; 0 never asks) and `notifications.handoffRepeatDeliveries` (*live*, default 25). Have the orchestrator bind its session with `orchestrator.session` when it starts, and write down in its handling guide how it hands off.
- [ ] **List prices.** `stats.pricing` (*live*), if you want the Stats subscription estimate for providers that don't report a price.
